## #389: the cancel fix, the snapper, and `domain/wayhome/`

### The cancel fix (#382 M1), `routing/BRouterTrailRouter.kt`

**What the code does (read).** `runEngine` (`:121-142`) takes the process-wide `ONE_ROUTE_AT_A_TIME` mutex inside `withContext(dispatcher)`, builds the engine on `dispatcher`, then `runToEnd` (`:169-178`) launches `engine.doRun(maxRunningTimeMillis)` as an `async` on `ENGINE_RUNS` — a single daemon thread, `brouter-engine` (`:208-210`) — and `await`s it. On `CancellationException` it calls `engine.terminate()`, then `withContext(NonCancellable) { run.join() }`, then rethrows. The mutex is released by `withLock`'s `finally` after the rethrow, so **the lock frees only once `doRun` has returned**, which includes BRouter's own `finally` that releases the static `ProfileCache` and closes `nodesCache` (`third_party/brouter/.../RoutingEngine.java:332-339`). That is the right order, and the reason it matters is in that `finally`: the cache is static and shared.

**Races, deadlocks, leaked threads (read, with inference marked).**
- No deadlock: `runToEnd` is only ever called under the mutex, so at most one `doRun` is ever queued on the single engine thread; it can never wait behind another.
- No leaked thread: one process-lifetime daemon thread, created at first use, never one per route. The cancelled `doRun` finishes on it and the thread goes idle.
- A cancel that lands between acquiring the lock and `await` still works: `async` starts eagerly, `await` throws at once (the caller is already cancelled), `terminate()` sets the volatile flag before or during the search, and `join` waits. Inferred from coroutine semantics, not run.
- Cancel is correctly not logged: `catch (e: CancellationException) { throw e }` (`:127-128`) sits before `catch (e: Exception)`. `kotlinx.coroutines.CancellationException` is a typealias of the `java.util.concurrent` one, so the catch is the right type.
- **The cancel's latency is bounded but not small.** BRouter reads `terminated` in exactly three places — `RoutingEngine.java:1722`, `:1752`, `:1975` — all inside the search; waypoint matching and file reads never read it, and `maxRunningTime` is also only checked inside the search loop (`:1979-1984`). So a cancel during a cold `.rd5` open or the matching waits for that phase to finish, with no timeout of its own. Hazel disclosed this; confirmed from source. Not a leak; see L-389-3.
- `doRun` swallows what the search throws (`:318-326`), so `run.await()` returns normally after a terminate and the result is discarded; `getFoundTrack()` is never read on the cancel path. Correct.

**The changed threading contract.** The search now runs on `brouter-engine`, not on `dispatcher`; only construction (which parses the profile, `RoutingEngine.java:133`) stays on `dispatcher`. This is an improvement — a 30 s search no longer blocks a `Dispatchers.Default` worker — and it is what makes the cancel audible on a one-thread dispatcher, as the class doc says (`:47-58`). The existing test "the engine runs on the router's own thread" (`BRouterTrailRouterTest.kt:183-199`) still passes because the missing-profile failure is thrown in the constructor, on `dispatcher`; its name now overstates what it proves. See L-389-4.

**M-389-1. The cancel test pins `terminate()`, not the join-before-release.** `BRouterTrailRouterCancelTest.kt:40-77` asserts the engine was terminated, the cancel returned in under 2 s, the next route is found, and nothing was logged. The fake search exits within 5 ms of `terminate()` (`:56`), so a build with the line `withContext(NonCancellable) { run.join() }` (`BRouterTrailRouter.kt:175`) deleted passes this test unchanged: terminate still happens, the next route still succeeds because the fake is already gone. Hazel's revert check 1 deleted only `engine.terminate()` (confirmed: `way-home-revert-1` is exactly that one line). **Failure path:** a later edit drops or moves the join; the lock then frees while the cancelled engine is still inside BRouter's `finally`, and the next engine's `ProfileCache.parseProfile` races the first's `releaseProfile` on the static cache (`RoutingEngine.java:133`, `:332`), with two engines' memory overlapping — the bound the class doc (`:47-58`) says the join exists to hold. **Fix (test only, about eight lines):** have the fake hold its loop for a fixed time *after* `isTerminated` turns true (say 300 ms), set a `stopped` flag as the last line of the fake's `doRun`, and assert right after `cancelAndJoin()` that `stopped` is true and that the cancel took at least that long. Revert check: delete the join line; the new assertion is the one that fails.

### `TrailSnapper`'s two methods

`TrailSnapper.kt` (48 lines, `domain/routing/`) is the owned interface; `BRouterTrailSnapper.kt:27-31` maps `SNAP` to `firstRoutePoint(point, point)` and `FULL_ROUTE` to `firstRoutePoint(point, toward)`. `firstRoutePoint` (`BRouterTrailRouter.kt:89-103`) shares `runEngine` — same lock, same cancel, same failure names — and differs from `route` only in accepting a one-node track as an answer, which is pinned on the real engine by `BRouterTrailSnapperTest.kt:48-62` (a trail node snaps to itself within 1 m; the off-trail point snaps to the same point 34.3 m away by both methods) and `:65-70` (the snap is where the router's own route from there starts). The claim that BRouter returns the matched point for a point-to-itself request is a fixture observation, not a BRouter guarantee; the test exists so an engine upgrade that changes it fails loudly. Good.

`findTrailJoin` (`TrailJoins.kt:74-99`) depends on BRouter reporting a no-way-near point as `EndOutsideData(START)` for *both* methods — if a SNAP ever reported END, the scan would stop instead of continuing. `BRouterTrailSnapperTest.kt:73-77` pins START for both. Good.

**L-389-1. `FULL_ROUTE` is unfit as built, and timing cannot rescue it** (Hazel's finding 2, confirmed). The entry scan routes toward `points.last()` (`FindWayHomeUseCase.kt:68`). A walker more than 250 m from any way — the ordinary forager, well off trail — makes every `FULL_ROUTE` test fail `EndOutsideData(END)`, which `findTrailJoin` treats as a stop (`TrailJoins.kt:91`), so the walk is reported `NO_ROUTE_FOUND` ("Couldn't find a trail route") when a perfectly good trail route exists. `FindWayHomeOnBRouterTest` passes only because its walker is 200 m west (`:49`). Also `NoPath` on a scan point is skipped without a log (`TrailJoins.kt:92`), reasonable but FULL_ROUTE-only. **Recommendation for the planner:** the S22 timing decides between two *working* methods; as built there is one. Either ship SNAP or change FULL_ROUTE's `toward` to a point known to be on the network before timing it. No code change needed in #389 since nothing selects a method in production.

**M-389-2. The length check fires falsely on a short trail part, and the false message is an instruction** (Hazel's finding 4, weighed; realistic). Entry and leave are the first and last tested points within 25 m of a trail. A walker who *crosses* a trail on the way out — or walks along one for 30 m — has entry and leave a few tens of metres apart along the track. The trail part is then the engine's route between two matched points near the crossing (0–30 m) **plus two joints of up to 25 m each** (`FindWayHomeUseCase.kt:88-89`), so `trailMeters` can be 50–80 m against a `trackBetween` of 20–50 m, and `> 1.5×` fires. The walker then reads "This route leaves your downloaded area. Download a larger area to route there." — false, and it tells them to go download something. The owner's "Don't make me think" names exactly this (a state the user could misread as broken) as the worst case. Hazel declined to guard it as speculative; it is derivable from the geometry and the 25 m figure, not from missing data. **This is an owner/planner decision, not a coder's**, so I grade it M as "rule it before part 2 wires the use case", and it can merge now if that is recorded. Options to put to the owner: (a) leave the joints out of the ratio (compare `route.lengthMetres` alone); (b) an absolute floor — only apply the ratio when `trackBetween` is over N m, or require `trailMeters > 1.5 × trackBetween + N`; (c) when the trail part is shorter than some M m, return `TrackOnly(null)` — the track is the way home and there is nothing to say. Any of these is a few lines plus one test; the figures are provisional like the others.
