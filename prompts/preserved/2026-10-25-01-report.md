## 1. Verify before building

**The file and the call.** On pre-main the call is at `app/src/main/java/com/zynergylabs/forager/app/ui/map/MapForecastCells.kt:58`: `style.getSourceAs<GeoJsonSource>(field.sourceId)`. It sits inside the `LaunchedEffect` at line 28, which is keyed on `state.loadedStyle`, the feed's store, week and groups, and `state.cameraIdleCount`. Line 29 takes `style` from `state.loadedStyle`. The effect runs on the main thread, on Compose's `AndroidUiDispatcher`, which matches the S22 stack in `crash-0147.txt`.

**Who calls it.** `MapForecastCells` has one caller, `SightingsMap.kt:645`. The effect relaunches whenever one of its keys changes.

**Where `cameraIdleCount` changes.** It is incremented by the camera-idle listener at `MapListeners.kt:177`. The feed keys change when the forecast host changes.

**Where `loadedStyle` changes.** It is written in one place only: the `setStyle` callback at `MapStyleReload.kt:158`.

**Confirmed from MapLibre's code** (13.5.0, read with javap from the pinned AAR):
- `MapLibreMap.setStyle(Builder, OnStyleLoaded)` calls `clear()` on the current style before it builds the new one.
- `Style.clear()` sets `fullyLoaded = false`.
- `Style.getSourceAs` calls `validateState`, which throws `IllegalStateException("Calling %s when a newer style is loading/has loaded.")` whenever `fullyLoaded` is false.
- The callback is called later, from `notifyStyleLoaded`.

**The cause, from the code.**
- From the moment `MapStyleReload.kt:117` calls `setStyle` until its callback sets the new style at line 158, `state.loadedStyle` still holds the old style object, and MapLibre has already cleared it.
- Any launch of the cells effect in that gap reads the cleared style at line 58 and throws.
- It is a stale style read: the cause the dispatch named, so I did not stop.

**Confirmed vs inferred.**
- **Confirmed:**
  - the clear-then-callback order in MapLibre;
  - that `loadedStyle` is not cleared or replaced until the callback;
  - that the cleared state throws the S22's exact message. A test shows it on a real `Style` object.
  - On the S22 with the fix, the guard fired in 15 of 34 style changes. So the effect does run in that gap on a real phone.
- **Inferred, not seen:** which key relaunches the effect in the gap.
  - Production has no suspension point before line 58. The only store is `AbsentForecastCellStore` (`ForecastCells.kt:235`), which returns without suspending. So it is a relaunch, not a resume across the gap.
  - My best reading is a camera idle while the location follower moves the camera (`cameraIdleCount`). The guard fired mostly while returning (15 of 21 changes) and never in 13 switches made with the Layers sheet left open and no navigation. Two things differ between those groups: navigation was on, and the sheet was closed. I could not separate them.
  - Each firing logged 1 to 3 lines within about 5 ms, so more than one relaunch happens per gap. I could not determine why.
  - The `StandaloneCoroutine{Cancelling}` in the device stack is the failing coroutine's own state once it has thrown. It is not evidence that something else cancelled it.

## 2. Other layers that read `state.loadedStyle` the same way
I left all of these unfixed, because none was seen crashing. Each reads `state.loadedStyle` in an effect without checking `isFullyLoaded`, so each is exposed to the same gap if one of its keys changes or its collector emits while a style is loading. All line numbers are on pre-main `c83a06722`.

## 3. What was built (PR #397)
**Commits:**
- `2d352b69b`, the fail-first. Line 58's read moves, unchanged, into `pushForecastCells(style, sourceId, cells): Boolean` in the same file, returning true. The commit also adds the fixture and the test.
- `d46f6626e`, the fix. `pushForecastCells` checks `style.isFullyLoaded` first. On a replaced style it logs `W SightingsMap: The <source> source was not read: a newer style is loading. The cells are drawn again when it finishes.` and returns false. The effect then returns before the legend callbacks.

**No other behaviour changes.**
- The skipped run is the one that crashed before. Nothing is drawn on a cleared style, and the legend callbacks are not called from that run.
- The new style's callback changes `loadedStyle`, a key of the effect, and that run draws the cells. The redraw is inferred from the keys: with the absent store there were no cells to see on the phone.
- If the new style fails to load, `loadedStyle` stays stale. The effect then logs once per relaunch, where before it crashed once.

**Files.**
- `MapForecastCells.kt`: 71 to 96 lines.
- `app/src/test/.../ui/map/MapForecastCellsStaleStyleTest.kt`: new, 3 tests.
- `app/src/test/java/org/maplibre/android/maps/StyleLifecycleFixture.kt`: new. It builds a real `Style` and calls the SDK's package-private `onDidFinishLoadingStyle` and `clear` on it, with an inert proxy `NativeMap`.

None of these is in PR #394, #395 or #396.

**What the test can and cannot prove.**
- **It can prove** that a style in the state MapLibre leaves an old style in makes the push log and stop, instead of throwing.
- **It cannot prove** that the gap happens. A real MapView cannot be built under Robolectric (`MapListeners.kt` notes this), and no test constructs `SightingsMapState`. So the timing is device-only by construction, and the S22 check below covers it.
- **The test does not go through the composable.** It calls `pushForecastCells`, the function at the crash site, directly.
