## Defects back to Hazel

### D1. The per-process token is one step too loose: a same-process activity destroy clears the ViewModels but restores the memory [read]

- The guard (MapCameraMemoryRecreation.kt:36-41, :72-74) says: a value saved in this process restores. Its premise (doc comment :26-31) is that in the same process `RoutePlottingViewModel.openCount` (RoutePlottingViewModel.kt:205) and the search serial still count on. That premise holds for a configuration change (the font and night-mode cases dispatched) but not for every same-process restore.
- Android destroys a backgrounded activity without a configuration change under memory pressure, and always under the developer option "Don't keep activities". Then `onSaveInstanceState`'s Bundle comes back, but `ComponentActivity`'s ON_DESTROY observer clears the ViewModelStore when `isChangingConfigurations()` is false: activity-1.13.0 bytecode from the Gradle cache, `ComponentActivity._init_$lambda$2`, `ON_DESTROY` then `isChangingConfigurations:()Z` then `getViewModelStore` (javap lines 1582-1591 of my dump) [observed]. All three ViewModels are activity-scoped `by viewModels` (MainActivity.kt:121, :199, :213).
- So in that case the memory returns with `appliedCameraRequestId = saved-route-<trip>-<n>` and `appliedSearchFrameId = k` while a fresh RoutePlottingViewModel counts from 0 and a fresh AvailabilityViewModel's serial restarts. Effects: the n-th route opened for that same trip, and the k-th search, are not framed (`shouldApplyCameraRequest`, `searchFrameMove`, MapCameraMoves.kt:85, :103 compare ids only). It is exactly the regression Hazel's token was added to prevent for a process restore, reached by a different door. The restored camera itself is harmless there: its `appliedTarget` is the old region, so the region move runs for the new default region (MapDataRefresh.kt:127).
- Likelihood: low on modern Android (whole-process kills are the norm), certain with the developer option on. It would not show in Hazel's S22 steps.
- **Fix:** tie the token to the ViewModel the ids come from, not the process: e.g. a `val instanceToken = UUID.randomUUID().toString()` on `RoutePlottingViewModel` (or on `AvailabilityViewModel`, since both die together) passed into `rememberMapCameraMemory(token)`, so `mapCameraMemorySaver(token)` is built from it. The existing `mapCameraMemorySaver(token)` seam already takes the token; `MapCameraMemoryAcrossRecreation` (the top-level val) would go. **Test:** in `KeepFollowOnRecreateTests`, the ViewModels are built outside the activity, so a case can swap in a fresh `RoutePlottingViewModel` (and view model) before `recreate()` and assert that the first route opened afterwards is framed (`applied` gains the new id) and that the camera is a fresh map's (regionCamera). The saver test "a value saved by another process restores nothing" becomes "a value saved under another ViewModel's token restores nothing".
- The larger alternative, holding `MapCameraMemory` in an activity-scoped ViewModel (no saver, consistent with the ids by construction), is a planner's call and not for tonight.

### O1. Panned away while navigating, then a recreation: the map now stays panned (Hazel's flag) [read]

My read: accept; it also matches coming back from another tab, which already works this way. If the owner wants the navigating case to re-follow on a recreation regardless, that is a one-line exception in the restore (follow when a navigation view is active) and a changed test, not a redesign.

## Notes (no change needed)

- **Saver mechanics** [read]: `rememberSaveable` registers a provider that reads the plain fields at save time, so the last idle camera is what is saved even though `saved` is not Compose state. `SavedMapCameraMemory`/`SavedCamera` are `Serializable` data classes of primitives, a `Triple` and a `Pair` (both Serializable); the saved value never crosses an app version (same process), so no serialVersionUID concern. Size: on the order of 1 KB serialized [unverified estimate], far under the Binder limit. A restore returning `null` (other token) makes `rememberSaveable` run `init` for a fresh memory, as the saver test shows.
