## Change

1. **Fonts are no longer fetched from MapLibre's demo server** (`BasemapStyles.kt:341`, `GLYPHS_URL_TEMPLATE = "https://demotiles.maplibre.org/font/{fontstack}/{range}.pbf"`, used for the app's own area-marker labels, `AREA_MARKER_FONT_STACK = "Open Sans Semibold"`). Juniper's research (`docs/audits/2026-10-18-map-services-policy-and-cost-research.md`) shows the demo host is "Dev only". Two routes; verify which works and report before building:
   - **(a)** Bundle the glyph files in the app (for example `asset://` glyphs, if the pinned MapLibre supports them). There is then no server at all, offline included.
   - **(b)** Serve them from the existing mapping Worker (`forager-pmtiles…workers.dev`). The owner keeps the mapping service on that account, separate from zynergy-labs (-1272).

   Prefer (a) if it works. Either way, the font's OFL licence ships with it, and the credits screen lists it where it already lists Open Sans.
2. **No library-default User-Agent, ever** (`ForagerApplication.kt:94-103`, `installMapHttpClientAtStart`). Today, if installing the map's HTTP client fails, tiles go out with MapLibre's default User-Agent, which OpenStreetMap's policy says "will be blocked". Find a way for the app's User-Agent to reach every tile request even on that path. If none exists, the fallback must not send tile requests to OpenStreetMap or OpenTopoMap with a library User-Agent. That would be a behaviour choice (for example, the map shows offline regions only, with a message), so **report the options and stop**.
3. **OpenTopoMap's full credit** (`Basemap.kt:113-124`). Today the attribution reads "© OpenStreetMap, SRTM, OpenTopoMap (CC-BY-SA)", shortened on purpose so it wouldn't wrap to two lines over the map. OpenTopoMap's page asks for "Kartendaten: © OpenStreetMap-Mitwirkende, SRTM | Kartendarstellung: © OpenTopoMap (CC-BY-SA)" (map data: © OpenStreetMap contributors, SRTM | map style: © OpenTopoMap (CC-BY-SA)). Use the full English form, "© OpenStreetMap contributors, SRTM | © OpenTopoMap (CC-BY-SA)" at least, and report whether it wraps on the S22 portrait caption. If it wraps, give the options; the caption layout is the owner's call.

## Amendment 1 (RECORD -1283, -1284): a failed map start-up shows a message, not a crash

**Authorisation:** the owner, "Go on the fix" (-1284), for the behaviour ruled in -1283 (2).

**The case** (inferred from code by Hazel and read by the planner; not seen on a phone):
- `MapLibreInitializer.initialize` logs and rethrows (`MapLibreInitializer.kt:42-49` on map-launch-fixes).
- `SightingsMap.kt:322-326` calls `initializeMapLibre(context)` inside `remember {}`, with nothing to catch it.
- So a start-up failure probably throws during composition and closes the app. This was already true on pre-main.

**Behaviour, as the owner confirmed it:** Maps > the map can't start > in the map's place: "The map couldn't start." and a "Try again" button > tap > the start-up is retried > on success the map loads; on failure the message stays.
- The tabs, the icon bar and the rest of the screen stay usable. Nothing closes.
- Each failure is logged, as now.
- The text is exactly "The map couldn't start." and "Try again", from `strings.xml`.
- The message area covers no map, so it is not map chrome and its surface may be solid.

**Verify first** (report briefly in the completion report, and stop only on a Stop below):

**Change:** a new path. A start-up failure becomes UI state in the map's place, not an exception in composition. Don't thread conditionals through the working map code. Prefer one small wrapper that the map composables share.

**Evidence:**
