# Report on dispatch 2026-10-26-01: why three MapCreditCaption tests run out of memory

The step 7 coder (Opus), 2026-10-26. This is a diagnosis only. Nothing was fixed, no test was touched, and no CI setting was changed. Everything here comes from CI logs and JUnit XML read through the GitHub API, plus the bytecode of Gradle 9.7.0 and Robolectric 4.16.1 read with `javap`, plus the sources of Compose ui-graphics 1.12.0. I ran no Gradle locally and used no device. The branch is cut from pre-main at `10142c1d2`.

## The answer in brief

- **What fails.** The whole unit suite runs in **one test JVM**. Gradle caps that JVM at **512 MB of heap** because the build sets no limit of its own. The three caption tests are suites 662 to 664 of 744 in that JVM.
- **What they allocate.** Each one captures the whole screen: 360×640 dp at xxhdpi, so 1080×1920 px. Each then copies it into an `IntArray` of 2,073,600 ints, which is **8.3 MB** of Java heap in a single allocation.
- **Why it fails sometimes.** On some runs that allocation does not fit, so the heap is already close to full before the caption tests start.
  - The allocation is only the trigger. The cause is what fills the heap earlier.
  - What fills it was not measured. Without a heap dump it cannot be.
  - The strongest candidate is that Robolectric keeps every test sandbox it has built alive for the whole JVM. Its cache holds three times the number of supported SDKs, and this suite builds at least six different kinds.
- **Since when.** No out-of-memory error appears in any CI run before **2026-10-24 14:53 UTC**. From then on it happened on 3 runs out of roughly 55 full runs, and it was always the same three tests.

**Which worker.** Every run read has a single test worker.
- The suites' XML timestamps never overlap: 0 overlapping pairs across 744 suites in each run.
- Every suite reports the same hostname.
- The build sets no `maxParallelForks` and no `forkEvery`. Neither appears in `app/build.gradle.kts`, and its only `Test` block (:647-654) sets a system property. Gradle's defaults are 1 fork and no forking per class.

**The heap limit.** 512 MB.
- The build sets no `maxHeapSize` and no `-Xmx` for tests.
- `org.gradle.jvmargs=-Xmx2048m` in `gradle.properties:1` is the Gradle daemon's own heap, not the test worker's.
- Gradle 9.7.0's `DefaultWorkerProcessBuilder` sets `512m` when no maximum heap is given. Confirmed in its bytecode (`javap -c`, offsets 326 to 337: `getMaxHeapSize`, `ifnonnull`, `ldc "512m"`, `setMaxHeapSize`).
- That this is the path test workers take is how Gradle builds its forked workers. It is inferred and was not seen on a runner.

**What ran before.** The same 661 suites, in the same order, in both failing and both green pre-main-line runs. The ten just before #662 are the MapChrome and location tests (LiveLocationPuckSwapTest to MapChromeColourTokenTest), identical in all four runs.

**The caption tests' own allocation, or heap filled earlier?** The failing allocation is the caption tests' own. Their own size is not the problem; the heap they meet is.
- **The failing frame.** NoOutlineDay's trace is `ImageBitmapKt.toPixelMap(ImageBitmap.kt:124)`, then `toPixelMap$default(:114)`, then `MapCreditCaptionNoOutlineTest.kt:67`.
  - In ui-graphics 1.12.0's source, the only large allocation on that path is the default buffer `IntArray(width * height)` plus the `readPixels` copy into it. That is 8.3 MB at 1080×1920.
  - The line numbers in the published sources jar do not line up exactly with the trace (:124 there is `return PixelMap(...)`). So the frame is pinned to `toPixelMap`, not to one line.
- **No stack on the second and third failures.** In both pre-main-line failures, the next two OutOfMemoryErrors carry no stack trace at all. The JVM throws a preallocated error without a stack when the heap is so full it cannot allocate a new one. That is inferred from how HotSpot behaves; it is a sign of a heap at its limit, not one large over-ask.
- **It recovers.** Touch's second test, which captures nothing, passes in every run, and so do the 80 suites after it. The pressure lasts about 12 s and then goes. The heap was close to full at that moment, not filled for good by that point.
- **No slowdown earlier.** Comparing 40258542687 with 40261211097 suite by suite, the failing run is no slower in any block of 50 suites before #651: the ratios run 0.63 to 1.08. Only the three caption suites slow down, about 2× while they thrash. The same-commit pair (attempts 1 and 2) runs 1.06 to 1.56× slower all the way through, as a slower machine would. So timing shows no gradual creep, and that is the opposite of what a steady leak would look like.

## 2. Who allocates what

**The three tests.** `MapCreditCaptionNoOutlineTest.kt` (Day and Night) and `MapCreditCaptionTouchTest.kt`. All run with `@Config(sdk = [36], qualifiers = "w360dp-h640dp-xxhdpi")` and `@GraphicsMode(NATIVE)`.
- Each fills the screen, captures the whole root with `onRoot().captureToImage()`, and reads it whole with `toPixelMap()` (NoOutline :67; Touch :103 and :108).
- They then read a handful of pixels: three edges and one point for NoOutline, the corners for Touch.
- The capture bitmap is 1080×1920 ARGB.
  - Under native graphics the capture is a real Android bitmap. Whether its pixels sit in native memory or on the Java heap under Robolectric was not measured.
  - The `IntArray` is on the Java heap for certain: 8,294,400 bytes.
  - These sizes are computed from the qualifiers, not measured on a run.
- **Nothing in the tests is held after they end.** No companion object, no static and no cached bitmap. The image is a local, and the compose rule disposes of its content.

**Other whole-screen captures.**
- 18 test files use `captureToImage` and 11 use `toPixelMap`.
- In the failing run, the image-reading suites that ran earlier passed: at #361, #486, #527 and #554 to #557. So did those after: #669 and #735.
- None of them failed in any run scanned. Only these three ever have.
- Why these three and not the others is not determined. Their position, after 661 suites, is the only thing that marks them out. The other capture tests use different screen sizes (not compared).

**Held for the whole JVM: Robolectric's sandboxes.** A candidate, not measured.
- Robolectric 4.16.1's `SandboxManager` keeps sandboxes in a `LinkedHashMap` capped at `getSupportedSdks().size() * 3` entries (`CACHE_SIZE_FACTOR = 3`; bytecode at offsets 15 to 36).
- A sandbox is keyed by SDK, instrumentation config (custom shadows change it), resources mode, looper mode and graphics mode (`SandboxManager$SandboxKey`'s fields).
- In this suite: `sdk = [36]` 468 times, plus sdks 27, 28, 30 and 33 in 10 places; 146 `GraphicsMode.Mode.NATIVE`; 5 custom-shadow configs.
- Mapping run 40258542687's suites to keys (a regex over the test sources that mapped 466 of 744 suites) shows a new key first appearing at:

  | Suite | Key |
  |---|---|
  | #1 | sdk 36, legacy graphics |
  | #10 | sdk 30 |
  | #11 | no sdk given |
  | #252 | sdk 36, native graphics |
  | #566 | sdk 36 with a custom shadow |
  | #609 | sdk 28 |

- So at least five or six sandboxes are alive by #609, and none is evicted, because the cap is far above six.
- Each sandbox is its own class loader over an instrumented Android framework, with its own resources and static state. How much heap each one holds is not measured here.
- Whether the "no sdk given" classes share the sdk 36 sandbox (targetSdk is 37) is not determined.

**Also held for the whole JVM: BRouter's profile cache.** Smaller, and a candidate only.
- The vendored `btools.router.ProfileCache` keeps a static one-slot cache of the last parsed profile (`ProfileCache.java:26`). Its expression contexts are sized from `memoryclass` 64 × 512 (`ProfileCache.java:88`, `RoutingContext.java:54`).
- The router tests are plain JVM tests (no Robolectric runner), so this cache lives in the app class loader until the JVM ends. Not measured.
- BRouter came in with #382 (`54f4d56c4`) on 2026-10-23, the day before the first failure. That timing is a correlation only: about 50 full runs passed with it in.

## 4. Options for a fix (none built; each is the owner's choice)

1. **Look before choosing: a heap dump on the next out-of-memory error.**
   - Change: a diagnostic branch whose test task gets `-XX:+HeapDumpOnOutOfMemoryError` and a step that uploads the dump. Or a test listener that logs used heap after each suite, to see the curve.
   - Gives: what actually fills the heap (sandboxes, BRouter, Compose, something else).
   - Risk: it touches the test JVM's flags, so it is a CI change the dispatch rules out, and needs the owner's word. At a 4 to 5 percent rate it may need several runs to catch one. The dump is about 0.5 GB.
2. **Give the test JVM more heap** (`maxHeapSize = "1g"` or `"2g"` in the `Test` block).
   - Change: one line, and the 512 MB default is gone.
   - Gives: the margin back at once. GitHub's runners have far more memory than that (their size was not checked here).
   - Risk: it hides the growth instead of explaining it. If it is a leak, it comes back later at a higher size. Local Robolectric runs would use the same higher limit.
   - A heap change, for the owner.
3. **A fresh JVM every N test classes** (`forkEvery`).
   - Change: the Robolectric sandboxes and anything static are dropped every N classes.
   - Gives: a hard bound on the retention, whatever it turns out to be.
   - Risk: each new JVM pays the Robolectric start-up again, roughly tens of seconds per fork (not measured). With N = 150 that is 5 forks, perhaps 1 to 3 minutes added. A test that passes only because of what ran before it in the same JVM would show up.
   - A fork change, for the owner.
4. **Two JVMs side by side** (`maxParallelForks = 2`).
   - Change: the classes are split between two workers, each with its own 512 MB.
   - Gives: about half the retention in each JVM, and probably a shorter suite.
   - Risk: twice the memory on the runner, and any test that writes a shared file can collide. None is known; there are 744 suites, and not all were checked.
   - A fork change, for the owner.
5. **Read only the pixels the tests need.**
   - Change: `toPixelMap(startX, startY, width, height)` around the points they read, or capture the caption node rather than the whole root.
   - Gives: the 8.3 MB allocation drops to a few kilobytes, and the same pixels are still asserted.
   - Risk: it is a test change. It must leave each assertion as strong as it is, and its own revert check would show that. It also moves the problem rather than solving it: the heap stays as full, and the next large allocation after #661 meets it.
   - Not a silencing, but it touches tests the owner has ruled on (dispatch 2026-10-13-02), so it is theirs to allow.
6. **Fewer sandboxes.**
   - Change: run the handful of sdk 27/28/30/33 and custom-shadow classes on the shared configuration.
   - Risk: those tests exist to test those SDKs and shadows, so this loses coverage. **Not recommended.**

My reading, for the owner: option 1 first, because it is the only one that finds out what the heap holds. Then option 2 or 3 depending on what it shows. Option 2 if nothing grows without bound. Option 3 if the sandboxes or a static cache account for it. Option 5 is worth doing on its own merits, since these three tests read a few points out of a whole screen, but not as the fix.

## Disclosures

### Confirmed vs inferred
**Confirmed:**
- One test JVM per run: no overlapping suite timestamps, one hostname, no fork settings in the build.
- Gradle 9.7.0 gives a worker 512 MB when none is set (bytecode).
- The same three tests are the only ones ever to fail with OutOfMemoryError, in the three runs found, at the same position (#662 to #664).
- The same commit passed on re-run.
- The failing frame is inside `toPixelMap`, called from the test.
- Robolectric's sandbox cache size and key (bytecode).
- The suite's configuration counts (git grep).
- BRouter's static profile cache (source).
- No OutOfMemoryError in any readable failed attempt before 2026-10-24.

**Inferred:**
- That test workers take the `DefaultWorkerProcessBuilder` path.
- That the heap was close to full rather than the request being too large.
- That stack-less errors mean a preallocated OOM.
- That the sandboxes and the BRouter cache are what fill the heap.
- The per-sandbox cost.
- The fork start-up cost.
- The bitmap sizes, computed from the qualifiers.

### Could not determine
- What actually fills the heap at #662. That needs a heap dump or a heap log (option 1).
- How much each Robolectric sandbox holds.
- Whether native-graphics bitmaps are on the Java heap.
- The runner's memory.
- Whether the no-sdk classes share the sdk 36 sandbox.
- The 9 unreadable logs (2026-09-03, 2026-10-17, 2026-10-18).
- Why only these three tests and not the other whole-screen captures.
- Which single commit, if any, tipped it. No bisection was run.

### Premises that were wrong
- None in the dispatch.
- -1615's "pass on main 177215135" holds for its run 40104009411. Its "heap pressure from dev's extra cases" is consistent with what is here, but still inferred.
- The ImageBitmap.kt line differs between dev (:119) and pre-main (:124). So the dev branch's ui-graphics resolves to another version, or the frame's line comes from a different binary than the sources jar read here. Not followed up.
