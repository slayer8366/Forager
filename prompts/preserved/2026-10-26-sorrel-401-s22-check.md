## 4. The three caveats, from the code

### 4.1 Caveat 1: both triples came from the app's own no-signal switch, not a hand tap

**Same code either way (read).** There is one style-swap effect, `MapStyleReload.kt:61`, keyed on `basemap, useOfflineTiles, nightMode, nightModeLoaded, ownStreet`; its comment at `:69` says `useOfflineTiles` "is also on for OSM or Topo with no signal (NoSignalTrailMap.kt)". The no-signal rule (`NoSignalTrailMap.kt:59`, `drawsFromDownloads`) flips that key; a basemap chip or the Night Maps checkbox flips another. All reach the same `map.setStyle(builder)` at `:117` and the same callback that sets `loadedStyle` at `:158`. `PendingLocate` sees only `isFullyLoaded` (`MapStyleReads.kt:27`, `MapLocationDot.kt:99-100, 106`). Which key changed is invisible to the guarded path. So the trigger is a limit on the sample's resemblance to a hand-made change, not on which code ran.

**Is the locate button covered during a hand-made change? Yes, on this screen (read, with one inference).**
- Basemap: `MapLayersSheet` is a `ModalBottomSheet` (`MapLayersSheet.kt:261`); "a tap applies it and the sheet stays open … it closes on a swipe, Back or a tap outside" (`:215-218`); the scrim is Material3's default at 0.32 alpha (`:253-255`). The style change starts on the chip tap, while the sheet is still up; a tap where the locate button sits lands on the scrim and dismisses the sheet. The earliest a finger reaches the button is after the dismiss animation. I did not read Material3's animation duration; that it is longer than the 41-175 ms gap measured here is inferred.
- Night Maps: it is "Settings' checkbox" (`MapIconBar.kt:193-195`; `AvailabilitySettingsRows.kt:57`), reached through the Tools drawer, a `ModalNavigationDrawer` whose scrim is `Color.Transparent` precisely so that it still "takes the tap that closes the drawer" (`AvailabilityScreenDrawerHost.kt:68-85`, read). Hazel's own script needed Back and then a tap outside before locate (`toggles.sh`, the even branch). That Settings is a page inside that drawer is inferred from her tap sequence and the file name `AvailabilitySettingsPages.kt`; I did not read the drawer's page host.
- Two fingers do not help: the scrim is a full-screen target in its own window (inferred from the Material3 behaviour the drawer host's comment describes; not read).

**But "unreachable" is a measurement, not a property (inferred).** Topo and OSM styles are built as JSON locally (`MapStyleSource.Json` → `fromJson`, `MapStyleReload.kt:113`); Trail online and the offline style load by URI (`:114`, `:125-126`). Hazel's D gaps are against the downloaded store (64-175 ms). A URI style over a slow link, or a cold store, takes as long as the fetch does — which is why my 2.6 said to widen the gap that way. Over such a load a hand-made change can outlast a sheet's dismiss, and a locate tap can land inside it. That case was not run (A was online, but its gaps cannot be measured: the tap times are on the host clock). It does not change the code that runs.

**Judgement:** caveat 1 is a stated limit, not a gap in the check. The automatic switch is the field case this path was built for (-1634: "Do it when the map is ready … so the walker does not tap again") and the one a walker can actually produce by hand on the Maps tab.

### 4.2 Caveat 2: both came after the way home had ended; 0 of 36 while returning

**This one is by construction, and my 2.6 item 3 was wrong to ask for it while returning.** `CompactMapIconCluster.kt:61-64` (read):

```kotlin
onLocateMe = {
    // Ruling D: while navigating, locate brings the navigation view back, as
    // "Return to Route" does; plain tracking would drop the compass follow.
    if (isNavigating) onReturnToRoute() else onResumeTracking()
```

`onResumeTracking` is `{ resumeTrackingRequestId++ }` (`AvailabilityCompactMapUi.kt:534`), the only key of the locate effect that reaches `PendingLocate` (`MapLocationDot.kt:95`). `onReturnToRoute` is `{ navigationFollowBroken = false; navigationViewRequestId++ }` (`AvailabilityScreen.kt:862-865`), which keys `MapNavigationView`'s effect (`MapNavigationView.kt:31`, `restoreRequestId`), not the locate effect. So while the way home is showing, the locate button never touches `PendingLocate`; its taps go to the navigation view's own guarded effect, which skips in the gap ("The navigation view skipped", `:35`) and relaunches on `loadedStyle` with `following` already true. So: Hazel's 0 of 36 while returning could not have been anything else, and her two hits after the arrival (recording still on, which `events.log` shows ran until 03:22:32) are the only state on this screen in which the remembered-locate path is reachable from the locate button. "After the way home ended" does not exercise *the same* code as while returning; it exercises the code #401 added, and returning exercises the navigation view's guard, which 2.6.1's clusters already showed firing (the seventh line in each). Caveat 2 is not a limit on the evidence; it is my condition that needed correcting. I record the correction here rather than editing the earlier review.

### 4.3 Caveat 3: following afterwards not shown

**What the triple proves (read).** `MapLocationDot.kt:105-109`: `if (pendingLocate.onStyle(styleCurrent = true)) locate(map, style)`. `onStyle` clears `pending`, logs "carried out", returns true (`MapStyleReads.kt:83-88`). So the line proves the tap was remembered, consumed exactly once, and `locate()` was reached. `locate()`'s activated branch (`:83-86`: `markAppMove`, `plainNudge.beforeLocate()`, `cameraMode = CameraMode.TRACKING`) logs nothing; only the unactivated branch logs "activated by locate" (`:90`), and the style callback had already activated the component synchronously at `MapStyleReload.kt:165-171` with `restoreCameraMode = previousCameraMode`, so that branch is the expected one and the 0 count is right.

**Why no "tracking changed" line follows, and what would (read from bytecode).** The app's listener logs every `onCameraTrackingChanged` (`NavigationView.kt:412-414`), and it was attached (`listenTo` at `MapStyleReload.kt:172`, once per component, `NavigationView.kt:405-409`). But MapLibre 13.5.0's `LocationCameraController.setCameraMode(int, Location, long, Double, Double, Double, OnLocationCameraTransitionListener)` begins `getfield cameraMode; if_icmpne 22` and, when the mode is unchanged, calls only `onLocationCameraTransitionFinished` and returns; `notifyCameraTrackingChangeListener` is at offset 53, past that branch (`javap -c` on the pinned runtime jar). After leg 1 the mode was 24 = `TRACKING` ("navigation left: mode=24" at 02:44:42.079; `CameraMode.TRACKING = 24`, javap), the callback restored 24, and `locate()` set 24 again: a no-op by the SDK's own first instruction, so no line, and no camera move to see. The log cannot distinguish "locate() ran" from "locate() did not" in that state. That is caveat 3 exactly, with its cause.

**What closes it:** one hit where the mode at the tap is not `TRACKING` — a pan first (mode 8), then the remembered tap — after which "tracking changed to 24: expected=null, byTheApp=false" must follow "carried out" (the activated branch is not wrapped in `byTheApp`, `MapLocationDot.kt:86`), and a screenshot 2 s later shows the dot centred. Hazel's last 27 cycles did pan first (`nosignal_locate.py`, "pan before wifi off", from 02:51:42 on) and got 0 hits; the 4 hits-eligible taps before that did not pan. So the shape of the closing run exists in her script already; it has simply not landed yet.

## 5. Verdict

**Met with stated limits.** Items 1, 2 and 4 are met on my recount and my look at the screenshot. Item 3's triple is exactly what was asked and appears twice; of its three caveats, 1 is a limit on sample realism with the same code either way, 2 is my condition's error rather than the run's (the path is unreachable from the button while returning, by `CompactMapIconCluster.kt:64`), and 3 is a real, explained gap in what the log can show: the camera-mode set is unobservable when the mode is already `TRACKING`.

What is unverified after this run, in the order I would close it:

1. **Smallest: a remembered locate with following broken first.** Not navigating, recording on or off (the path does not read it), pan the map, then land a locate tap inside a no-signal switch; the proof is the triple followed by "tracking changed to 24: expected=null, byTheApp=false" and the dot centred in a screenshot 2 s later. Hazel's `nosignal_locate.py` with its pan already does this; it needs enough cycles for one hit, at her observed 2 hits in 72 timed taps (0 in the 27 that panned). The offline store's 64-175 ms gap with an adb tap landing 0.01 s after the log line is the whole difficulty; a delay swept 0.00 to 0.08 s would spread the taps across the gap rather than at its front. This is the one run I would ask for before merge if the owner wants the camera move itself seen; I would not hold the merge on it, since the dispatch's own ruling was that the tap is remembered and runs once, which is shown.
2. **A hand-made change over a slow URI style** (Trail online on a throttled link, or a cold store), locate tapped the moment the sheet is gone: closes the "unreachable by hand" question as a measurement. Optional; the code path is the same.
3. **The phone-side APK hash**, recorded next time as the `adb shell sha256sum` of `pm path`'s file beside the artifact's. Not a doubt about this run; a gap in what the record can show.

Nothing here re-opens the code verdict of my earlier review (mergeable on the code). The merge was waiting on the evidence being filed and meeting 2.6; it is filed (the two comments), and meets 2.6 as read above, with item 3 read as "reachable only when not navigating", which is the code's reading and not Hazel's choice.
