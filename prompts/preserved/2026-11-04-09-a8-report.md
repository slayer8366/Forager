Dispatch 2026-11-04-09, A8: the facts on what downloading an older area again changes for the user. No words for the notice. Read at pre-main 949ad8183, which has not moved. Branch drop-off-map-copy is cut and I'm building now.

HOW A USER "DOWNLOADS AGAIN"
- [read] An area that is already downloaded has no "Download again" button. It shows only when `!region.isDownloaded` (OfflineRegionsList.kt:249-250), and AvailabilityViewModelOfflineMaps.kt:40-41 returns early for a downloaded row.
- So following the notice means a new download over the same area. It gets a new id and a new row, and the old area stays unless the user deletes it.
- [read] The new download is built against trail-v4 (`offlineDownloadStyleUrl()`, TrailStyle.kt:84; MapLibreOfflineMapRepository.kt:139-146).

WHAT CHANGES
1. **The notice.** The new area's row has none, because its style URL is trail-v4 (TrailStyle.kt:111-114). If the old area is kept, its row still shows the notice.
2. **The style used when the map draws from downloads.** It changes for every area on the phone, not only the one downloaded again.
   - [read] When the map draws from downloads, it loads the newest Trail Map style that any area holds (TrailStyle.kt:102-103, read fresh at each style load through MapLibreOfflineMapRepository.kt:300-311 and MapStyleReload.kt:82; then BasemapStyles.kt:315-327).
   - [inferred] On the S22 that is street-v3 today. One trail-v4 area makes it trail-v4.
   - [read] TrailStyle.kt:99-100 says the older areas then draw in v4 too, because they use the same basemap tile addresses. They hold none of v4's hill-shading tiles.
   - [read] The map draws from downloads only in three cases (NoSignalTrailMap.kt:59-66): "Use offline tiles" is on; OpenStreetMap or Topographical is chosen and there is no signal; or Trail Map's style has failed with no stand-in map.
   - [read] A Trail Map user outside those cases already sees trail-v4, signal or not, downloads or not (BasemapStyles.kt:276-279). For that user, this item changes nothing.
3. **What v4 adds to the drawing.** [read, server/pmtiles-worker/src/street-style-v3.json against trail-style-v4.json]
   - 182 layers against 97.
   - Sprite v6 in place of v5 (the orchard, vineyard and nursery patterns).
   - A new hill-shading source at relief/{z}/{x}/{y}.png, zoom 5-11. The download covers zooms 10-15, so it stores relief at zooms 10-11 for the new area only.
4. **The trail route data is fetched again, fresh, for the new id.**
   - [read] MapLibreOfflineMapRepository.kt:193-196 calls `routes.fetchFor(newId, …)`, which asks the server (RegionRouteFolders.kt:42-58).
   - [read] That client has no HTTP cache (ApiClients.kt:23-37).
   - [observed, logcat-s13.txt:69024-69162] Test s13's download asked for area.json and then the .rd5 squares, and each answered 200.
   - [read] The old area's routes, once stored, are never fetched again (RegionRouteData.kt:167-171).
   - So downloading again is today the one action that refreshes an area's trail routes. Whether the server's route data has changed since the S22's areas were stored is not determined.
5. **The row itself.** It shows a new download date. Its size and tile count are MapLibre's for the new area, now including the relief tiles. The tile budget counts the new area by its estimate (OfflineTileBudget.kt:20-23), so keeping the old area as well counts both.

WHAT DOES NOT CHANGE
1. **The basemap tiles: roads, buildings, water, land use, fences.**
   - [taken from the 2026-11-04-08 report, section 2, which read MapLibre's source] Any tile already stored with data is reused and never revalidated (offline_download.cpp:477-514; offline_database.cpp:591-614).
   - [read] Both styles use the same basemap source, `…/us.json`.
   - [observed, logcat-s13.txt] Test s13's download made 17 map requests, all reference-trails and all 204 (no data), and none for us/.
   - So the map's data is not refreshed, and today the fence mark does not arrive this way.
2. **The trail overlay tiles.** [read] They use the same address in v3 and v4 (`reference-trails/{z}/{x}/{y}.mvt`, zoom 10-15). Stored tiles with data are reused. Only tiles stored empty (204) are asked for again, as in Test s13.
3. **The fonts.** [read] The glyph address and the three named font stacks are the same in both styles, so the same stored fonts serve.
4. **The style document and sprite.** [observed] Test s13 asked for neither. They were already on the phone from viewing the map online, so they were reused.
   - [inferred] A phone that has never drawn trail-v4 online would fetch them in the download.
   - [not read] Whether MapLibre's download reuses a stored sprite or font exactly as it reuses a tile. I take that from the 2026-11-04-08 report's general rule and Test s13's request log, not from MapLibre's source.

AFTER THIS DISPATCH
- The street drop-off's map data arrives with signal whether or not the area is downloaded again. Downloading again is no longer needed for it.
- [design, Phase 1 section 7] Downloading again creates a new id. At the download's end (P2), that id's copy pass fetches again the unmarked tiles the download reused: about one more pass of requests.
- Online viewing refreshes the tiles it draws exactly as before (2026-11-04-08 report, section 4).

IN SHORT: what downloading an older area again actually does for the user today is:
- clear its notice;
- switch the style used when the map draws from downloads to v4, for every area;
- store the hill shading for that area;
- fetch its trail routes again.

It does not update the map's own data. MapLibre's store is not touched by this dispatch, so that stays true after it.
