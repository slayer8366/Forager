## 1. The cause: confirmed

Read with `javap -p -c` from the pinned 13.5.0 AAR, not from Hazel's extraction:

- `MapLibreMap.setStyle(Style$Builder, Style$OnStyleLoaded)`: stores the callback, calls `locationComponent.onStartLoadingMap()`, then **`if (style != null) style.clear()`**, then `style = builder.build(nativeMapView)`, then `setStyleUri`/`setStyleJson`. The clear is synchronous, before anything of the new style exists.
- `Style.clear()`: first instruction is `fullyLoaded = false`; it then `setDetached()`s every layer and source and empties the three maps.
- `Style.validateState(String)`: `if (!fullyLoaded) throw new IllegalStateException(String.format("Calling %s when a newer style is loading/has loaded.", name))`. `getSourceAs`, `getSource`, `getLayer`, `getLayers`, `addSource`, `addLayerAbove` and `removeImage` all call it first. `addImage(String, Bitmap)` does not. `isFullyLoaded()` returns the field.
- `MapLibreMap.notifyStyleLoaded()`: `style.onDidFinishLoadingStyle()` (sets `fullyLoaded = true`), `locationComponent.onFinishLoadingStyle()`, then `styleLoadedCallback.onStyleLoaded(style)`. So the app's callback runs only after the new style is fully loaded, and the old style has been cleared since `setStyle` returned.
- `MapLibreMap.getStyle()` returns **null** while the current style is not fully loaded (checked: `isFullyLoaded` then `aconst_null; areturn`). Relevant to §6.

In the app, on pre-main `fb692fb57`: `state.loadedStyle` has exactly one writer, `MapStyleReload.kt:158`, inside the `setStyle` callback at `:117` (`git grep 'loadedStyle\s*=[^=]' -- app/src/main`). So from `:117` returning until the callback, `loadedStyle` holds a style whose every getter throws. Confirmed, as Hazel said.

The cells effect (`MapForecastCells.kt:28` on pre-main, `:30` on the PR head) is keyed on `state.cameraIdleCount`, which `MapListeners.kt:177` increments in `map.addOnCameraIdleListener`, a map-level listener that is not tied to a style. Any camera idle in the gap relaunches the effect, which reads `state.loadedStyle` at `:31` and pushed into it at `:58` (old) / `:60` → `:89` (new). The effect runs on Compose's main-thread dispatcher; `setStyle` is called from a `LaunchedEffect` on the same thread. That the effect does run in the gap is not only inferred: the guard fired in 15 of 34 style changes on the S22 (§5).

**One reading Hazel left open that the code supports:** the location follower moves the camera on every fix (the test feeder fed 1 Hz), so a camera idle lands roughly every second while following or returning, which is why the gap was hit on 15 of 21 returning switches and 0 of 13 switches with the Layers sheet open and no navigation. Consistent with both the S22 pattern and Hazel's original four crashes (three while returning, one with no recording after a basemap tap). Inferred from `MapListeners.kt:175-177` and the effect's keys, not observed; I could not separate it from the sheet-closed condition any more than Hazel could.

## 2. The fix: correct, no silent swallow, no race in practice

`pushForecastCells` (`MapForecastCells.kt:84-96` at `d46f6626e`):

- On `!style.isFullyLoaded`: `Log.w(SIGHTINGS_MAP_TAG, …)` and `return false`; the effect does `return@LaunchedEffect` at `:60`, before `onCellsShown` (`:63`) and `onZoomedOutChanged` (`:66`). Logged, not swallowed; nothing is presented as success.
- On a loaded style the body is the moved code, line for line (`getSourceAs`; null → the same warning; else `setGeoJson`; `return true`), with `field.sourceId` → `sourceId`. Diff read; no other change in the file.
- **Redraw:** the effect's first key is `state.loadedStyle`; the callback at `MapStyleReload.kt:158` sets it to the new style, so the effect relaunches and pushes into the new style's empty sources (which `initializeOverlayLayers` at `:133` re-adds). Inferred from the keys, as Hazel says; not observed, because the only store is `AbsentForecastCellStore` (`AppContainer.kt:317`) and there are no cells to see.
- **What the skipped run would have done without the crash:** nothing visible. The cleared style's sources are detached, and `GeoJsonSource.setGeoJson(FeatureCollection)` returns at once when `detached` (javap: first instruction `getfield detached; ifeq; return`). So the only observable change is that the legend callbacks are not called from that run; they are called from the relaunch. The run that is skipped is exactly the one that crashed.
- **Check-then-use race:** `isFullyLoaded` and `getSourceAs` are consecutive calls with no suspension between them (`:85` and `:89`), on the main thread. `fullyLoaded` is written only by `clear()` and `onDidFinishLoadingStyle()`, both reached from `MapLibreMap` methods that MapLibre requires on the main thread (`ThreadUtils.checkThread` on `Source`; the app calls `setStyle` from a `LaunchedEffect`). A clear between the check and the read would need a second thread calling `setStyle`, which nothing in the app does and MapLibre forbids. **No race in practice.** The one suspension in the effect is `feed.store.cells(...)` at `:50`, which runs *before* the push for each field, so a store that really suspends (a future downloaded one) could see the style cleared mid-loop; the guard is checked per field, so field N+1 then logs and stops, and what field N pushed went to a detached source and was dropped. Correct behaviour, and the partial `shown` map is discarded with the early return rather than reported.
- **Failed style load:** if the new style never loads, `loadedStyle` stays stale and every camera idle logs one line per colour field. Hazel disclosed this. Before, the same case crashed once. A `W` line per idle is the right trade; noted as L-397-3 only so nobody reads the log spam as a new defect.

## 3. The test and the fixture

`StyleLifecycleFixture` (`app/src/test/java/org/maplibre/android/maps/StyleLifecycleFixture.kt`) is a **real `org.maplibre.android.maps.Style`**: `Style.Builder().build(NativeMap)`, then the SDK's own package-private `onDidFinishLoadingStyle()` and `clear()`, which is why it sits in MapLibre's package (both are `void name()` with no access modifier in javap). The `NativeMap` is a `java.lang.reflect.Proxy` returning null/false/zero. With an empty builder, `onDidFinishLoadingStyle` adds nothing and `clear()` iterates empty maps, so the proxy is never asked anything that matters; `getSourceAs` on the loaded fixture falls through to `nativeMap.getSource` → null, which is why test 3 sees "not in the loaded style". For the one property under test, `fullyLoaded` and the throw it gates, the fixture is faithful: the state is produced by the SDK's own two methods, in the SDK's own order.

- **Test 1** (the fixture's replaced style throws the S22's exact message) is the positive control: it rules out a fixture that fails for a different reason. Good. It passed in all three runs.
- **Test 2** (replaced style → `false` and the one log line) is the guard. It is the test that went red in the fail-first and the revert.
- **Test 3** (loaded style, no source → `true` and the "not in the loaded style" line) passes before and after the fix (3 tests, 1 failed in both red runs; the other two passed). It guards against the guard over-firing on a loaded style, and it would go red if the condition were inverted, but no run has shown that. Per CLAUDE.md a check that passes identically before and after is to be flagged: flagged, as L-397-2, not as a defect.

**What the test leaves unproven**, as Hazel said and I agree: it calls `pushForecastCells` directly. Not proven by any test: (a) that the effect at `:60` passes `state.loadedStyle` and returns on `false` before the legend callbacks (read at `:60-66`, not executed); (b) that the effect relaunches on the new `loadedStyle` and redraws (inferred from keys); (c) that the gap is reached on a phone (device-only; the S22 check is the evidence); (d) the non-null-source path through `setGeoJson`, which the fixture cannot reach (no source) and which is moved code, unchanged. A Robolectric test through the composable is not available: `MapListeners.kt:170-174`'s own comment and Hazel's report both say a real `MapView` cannot be built there, and no test constructs `SightingsMapState`. I did not find a way round that either.

Fragility note (L-397-1): the fixture depends on two package-private SDK methods and a package-private `Builder.build(NativeMap)`. A MapLibre upgrade that renames or seals them breaks the test at compile time, which is the loud failure, not a silent one.

Hazel's list is complete and correctly ordered; the one correction is that the location-dot row is confirmed, not unverified. Why only the cells effect has crashed so far: its key `cameraIdleCount` changes about once a second under the follower, which is one to two orders of magnitude more often than any other row's keys. The others are the same defect at a lower rate, and the rate is set by what the user is doing, not by the code.

**Shared fix or per-layer guards.** One shared fix is better, and the code offers two shapes without designing either: (a) set `state.loadedStyle = null` at `MapStyleReload.kt:117`, before `map.setStyle`, so every effect keyed on `loadedStyle` relaunches, hits its `?: return`, and its long-lived collectors (the two `snapshotFlow`s in `MapFan.kt`) are cancelled; or (b) read the SDK's `map.style`, which is null while a style is not fully loaded (§1), at the read sites. (a) is one line at the one writer and covers every present and future reader, but it adds one null pass of every `loadedStyle`-keyed effect per style change and so needs its own fail-first and device check; `remember(state.loadedStyle)` at `MapFan.kt:66` would make an extra `FanOutHideGate` for the null, and `MapListeners.kt:189` would skip saving the camera during the load, both harmless on reading but to be checked. Five more copies of #397's guard would be five places to keep right and would not cover the `snapshotFlow` collectors cleanly (a collector that fires once in the gap logs and continues; it should stop). #397's guard stays correct and harmless under either shared fix. **Recommendation:** merge #397 now as the fix for the layer that crashes; dispatch the shared fix as its own item against pre-main with #396 in, with a fail-first for at least `MapDataRefresh.kt:55` (the medium row) and the S22 check repeated with a recording and a route. Not for this PR.
