# What to build

**B1. The Layers sheet.**

- **What it replaces:** `MapModePicker`'s popover (`ui/map/MapChrome.kt:126-193`), on all three hosts: the compact Maps tab's Layers row, the wide layout's `MapModeToggle`, and the Cartography entry map's fullscreen button. The entry map button's existing rule of hiding while offline tiles are on stays as it is.
- **Form:** a Material3 modal bottom sheet. Reuse the pattern and inset handling of J5c's details sheet, and cite it.
- **Content scrolls** in a short landscape window (823×384 dp).
- **Title:** "Layers".
- **Sections**, in this order:
  - **"Map type"**: Street, Topographical and Satellite, one chosen, as today. The basemap choice stays **session-only**, exactly as now (`AvailabilityScreen.kt:828`).
  - **"Overlays"**: one switch per toggleable layer that the host map draws. Labels: "Finds", "Photos", "Waypoints", "Planned trips", "Recording trail", "Tracks", "Offline maps".
- **Colour fields** are listed within Overlays when any exist. Each has its switch, an opacity slider (0 to 100%, the L0a multiplier) and a **drag handle to reorder**. Drag-to-reorder is the convention in backcountry and topographic map apps (prior-art doc, line 11 and "Opacity and drag reordering"). Give each colour row TalkBack custom actions "Move up" and "Move down".
- **Reorder timing:** a reorder takes effect at the next style load, as the owner accepted in terminal `2026-09-27-72`, Deviations 4. Say in the report what the user sees between reordering and that load.
- **One set of stored choices** is shared by both maps. The entry map lists only the layers it draws.
- **Button description:** "Layers: \<basemap\> map. Choose the map type and overlays." The current text's "Night mode on/off" was already untrue, because the picker has no night control. The four test classes that pin the old text (pulse, answer 8) are updated in the same commit and reported by name and count.

**B2. Every saved record on the Maps tab.** Owner: "Also show all finds etc.", "On by default", then "Every saved record".

- **What is drawn**, in compact and wide: every saved (non-draft) find with a location, every track in Records, every album photo with a location, and every offline region. None of it depends on whether a Journal entry keeps it.
- **A new domain use case**, free of Android UI types and tested headless, gathers them into `MapOverlayContent`'s existing record fields, with record ids (`RecordPoint`, `RecordPolyline`, `RecordRegion`).
- **The rules the entry map already applies** also apply here:
  - a track that resolves to zero points gives no polyline;
  - a photo with no coordinate gives nothing.
- **A repository failure** is logged through the app's error log and that kind drawn as absent. It is never silent (CLAUDE.md, Errors), and the other kinds still draw.
- **Freshness:** the data reloads at least whenever the Maps tab is shown. Name your mechanism.
- **Defaults:** each of these overlays is visible by default.
- **The entry map's own data path is untouched.** Its geometry still comes only from `GetCartographyEntryMapDataUseCase`, per that file's rule.
- **No performance work** beyond what correctness needs (CLAUDE.md, Building). The device check will count.

**B3. Persistence across restarts** (owner: "Across app restarts").

- **What is stored:** each toggleable layer's visibility, each colour field's opacity, and the colour-field order.
- **Where:** DataStore, in the existing `map_preferences` file, under keys in the `map.layer` namespace keyed by registry id, for example `map.layer.<id>.visible`, `map.layer.<id>.opacity` and `map.layer_order`.
- **Pattern:** follow `DataStoreMapPreferencesRepository`: a `Result`-returning suspend interface and a per-instance `PreferenceDataStoreFactory.create`. Failures are logged, never swallowed.
- **Defaults** are what the registry and the owner say: toggleable overlays on, and colour fields at 100% in registry order.
- **What is not stored:** the basemap.

- **Collapsed:** it names the active colour layer, or "2 layers".
- **Expanded:** each layer's colour ramp with its end labels, and a "no forecast here" entry. The chip collapses on a second tap.
- **Bounds:** bound it to its content (CLAUDE.md, Surface pitfall: `IntrinsicSize` or equivalent). Real coordinate touches on the map just outside the chip, sampled at several points around its bounds and not at one point, must reach the map.
- **Insets:** its placement depends on real insets that Robolectric reports as zero. Say so and list it as device-only.

**B5. The stored-data interface for forecast cells.**

- **Shape:** a domain interface that returns cells for a set of 1-degree blocks. Each cell is a 0.1-degree polygon carrying the properties named in the plan's forager-forecast section: `group`, `week`, `chance` (0 to 1), `uncertainty_low`, `uncertainty_high`, `applicable`, `drivers` (a list of `{label, value}`), `weather_through` and `model_version`.
- **Parsing and validation** are pure and tested:
  - a malformed feature, or a `chance` outside 0 to 1, is rejected and counted, never clamped;
  - a cell with `applicable` false draws nothing.
- **"No forecast data" is an explicit result.** An absent store returns it; an empty list must not pass as success (CLAUDE.md, Errors: an unsupported capability returns an explicit "unsupported").
- **Map feed:** the map asks the store for the blocks touching the visible area when the camera goes idle. That is the same path a real downloaded store will use. The cell source is re-added after every style reload, basemap change and night-mode change.
- **No downloader, no network.**

- **The generator** is deterministic. It gives cells for any requested blocks, so data exists wherever the phone is. It includes cells with `applicable` false, so "no forecast here" can be seen.
