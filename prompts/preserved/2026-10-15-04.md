Each matched the publisher's SHA-1 (core `73a5452d…`, camera2 `c270a4bc…`). I then read them with `javap`. What that means: these are the published bytes for the pinned version. They are not necessarily the files CI resolved, though the version catalog pins exactly `camerax = "1.6.2"` (READ, `gradle/libs.versions.toml` on `raw-stage2`).

- `ImageCapture` has **no burst API**. Its public methods are the three `takePicture` forms plus output-format and postview accessors. No class in camera-core is named burst, sequence or bracket.
- `TakePictureManagerImpl.issueNextRequest` returns early with "There is already a request in-flight." while a request is capturing. The in-flight request clears only when that request's **capture future** completes (`trackCurrentRequests` → lambda → `mCapturingRequest = null; issueNextRequest()`). Queued `takePicture` calls therefore run **one after another, never pipelined**.
- `CaptureNode.MAX_IMAGES = 4`; the next request also waits if the pipeline holds four unclosed images. Each request has "only one capture stage" (a `CaptureNode` message).
- `Camera2CameraControl` (experimental interop, camera-camera2 1.6.2) offers `addCaptureRequestOptions` / `setCaptureRequestOptions` / `clearCaptureRequestOptions`. That is the route for locking exposure and white balance.

So one frame took about **0.52 s from tap to both images in memory**, 0.38 s of it between submitting the request and the start of exposure. The DNG write and check took about another 0.8 s (inferred).

**INFERRED consequence.** Built on CameraX as it stands, a burst of N frames takes roughly **N × 0.5 s of capture**: about 2 s for 4 frames and about 4 s for 8. ## 4. Burst capture

### 4.1 Frame count, and its operating limit

- **Proposal: N = 4 by default, provisional until Part 0's numbers are in.** The ceiling (the operating limit) is 8, which is the top of the published range: "In practice, we limit our bursts to 2–8 images" (READ, Hasinoff et al. 2016, §3). The floor for an averaged file is 2 merged frames, the reference plus at least one.
- **The gain from N:** averaging N independent frames lowers noise by √N, about 6 dB at 4 frames and 9 dB at 8 (READ, OSCam `frame_average.py` docstring: "SNR improves by about sqrt(N)"). Going from 4 to 8 frames buys about 1.4 times less noise and doubles the wait.
- **The cost of N:** at section 2's rate, about 2 s for 4 frames and 4 s for 8. The owner's choice of wait is D3.
- **What Part 0 decides:** if the measured rate is much faster than 0.5 s per frame, a larger default is cheap; if it is slower, 3 frames may be the honest default.
- The count is a constant in the domain layer with its reasoning in a comment, not a setting (Don't make me think).

### 4.2 Fixed exposure across the burst

- **Lock, then verify.** Before frame 1, lock exposure and white balance: `CONTROL_AE_LOCK = true` and `CONTROL_AWB_LOCK = true` through `Camera2CameraControl.addCaptureRequestOptions` (experimental interop). Clear both after the last frame, including on every failure path, in a `finally`. The opt-ins stay inside `photo/`, as stage 2's do (`CameraXRawCapture.kt` header).
- **Every frame's capture result is checked** for `SENSOR_EXPOSURE_TIME`, `SENSOR_SENSITIVITY` and `CONTROL_POST_RAW_SENSITIVITY_BOOST`. A frame whose values differ from the reference frame's is **excluded and logged**, not rescaled. Rescaling frames of different exposure is HDR's job (a later stage), and CLAUDE.md says not to build correction without data showing the case.
- **Focus:** no AF change in this stage. Each frame's `LENS_FOCUS_DISTANCE` is logged so the device run can show whether continuous AF moves mid-burst. Locking AF is a later decision, only if the data shows it is needed.
- **Fallback if locking doesn't hold on a phone** (frames keep arriving with different exposures): manual exposure, `CONTROL_AE_MODE_OFF` with the reference frame's own exposure time and ISO. Both test phones report MANUAL_SENSOR (-996, -998). This is a **stop-and-ask, not a silent switch**: it changes what the camera does mid-burst.

### 4.3 Capture mechanics

- **A new path.** A new `captureBurst` on the capture-session interface, beside `captureRaw`, and a new `ImageCapture` built like `buildRawJpegImageCapture`. The JPG and RAW paths are untouched (CLAUDE.md, Building). The new enum value means every exhaustive `when (CameraFormat)` must be visited; the coder lists each one, traced to its caller.
- **One reference JPG.** Every frame is RAW+JPEG, because one `ImageCapture` can't change format mid-session without a rebind. Only the reference frame's JPG is kept. The others are closed without being written. Part 0 measures whether that per-frame JPEG costs time. If it does, a RAW-only capture for frames 2 to N is a stop-and-ask (it needs a second use case or a rebind).
- **Reference frame = the first frame** (recommended). It is closest to the moment of the tap, and its JPG is the placeholder, so the preview and the final file show the same moment. Published practice picks "the sharpest frame ... from the first 3 frames" (READ, Hasinoff et al. 2016, §4). That makes the preview JPG match only if that frame's JPG is the one kept, so it is offered as D8 rather than built.
- **Capture results.** `CaptureResultCollector` keeps only the last 32 results, and the preview fills it at frame rate (READ, `CameraXRawCapture.kt:78-101`). A burst that awaits results late would find them evicted. Each frame's result is awaited as that frame arrives, before the next one; the coder checks this against the collector's capacity and states the margin.
- **Frames are copied out and the `ImageProxy` closed at once** (`copyRawPlane`, as stage 2 does), so CameraX's four-image ceiling never stalls the burst.

### 4.4 Memory budget, an explicit operating limit

Per frame at 12 MP: 4080 × 3060 × 2 bytes = **25.0 MB** (S26), 4000 × 3000 × 2 = **24.0 MB** (S22).

**Streaming, never the whole stack.** Each alternate frame is aligned to the reference and added into the accumulators as it arrives, then dropped. This is OSCam's own design: "Memory is bounded to a few full-frame buffers regardless of burst length" (READ, `frame_average.py`, `average_burst` docstring). Peak, at the S26 size:

| Buffer | Size |
|---|---|
| Reference frame (16-bit) | 25 MB |
| Incoming frame (16-bit) | 25 MB |
| Reference and incoming grey pyramids (quarter size, float, 4 levels) | about 27 MB |
| Weighted sum, float32, per photosite | 50 MB |
| Weight sum, float32, per photosite | 50 MB |
| Output plane (16-bit; may reuse the incoming buffer) | 0 to 25 MB |
| Reference JPG bytes | about 4 MB |
| **Peak** | **about 180 to 205 MB** |

- **Limit:** before frame 1, read `Runtime.maxMemory()` minus the memory in use. If that is less than 1.5 × the computed peak for the bound size, the shot takes the single-RAW path with the memory message (section 3.4). The figure is computed, never assumed.
- **The app's heap limit is unknown here.** The manifest has no `largeHeap` (READ, `AndroidManifest.xml` on `raw-stage2`). The S22 and S26 heap limits are a device read (`getprop dalvik.vm.heapgrowthlimit`; device item 2). Asking for `largeHeap`, or moving the accumulators to native memory, is a **stop-and-ask**: the first is an app-wide change, and the second's behaviour under the heap limit is UNVERIFIED here.
- N does not change the peak; it changes only the time.

### 4.5 Time budget (INFERRED from section 2's one observation, for the owner's waiting-time choice)

Tap to saved ≈ N × 0.5 s of capture, plus alignment of the last frame (the others overlap with capture; the per-frame time on a phone is **unknown**, measured in Part 0 and the device run), plus about 1 s to write and check a 12 MP DNG (stage 2 took about 0.8 s; the averaged plane may compress less well, section 5.6). **About 3 to 4 s for 4 frames, and 5 to 6 s for 8.** These estimates rest on one dim-room shot.

### 4.6 Focus stacking later (-1010)

The capture function takes the frame count, and returns frames with their capture results, so a later stage can vary focus per frame. Per-frame request settings are **not** built now (CLAUDE.md: no speculative capability). Alignment works on any two frames of the same size and doesn't assume equal sharpness.

## 5. Alignment and averaging (pure Kotlin, `domain/raw/`, no Android imports)

All of this is domain logic, testable headless (CLAUDE.md, Architecture). The camera adapter fills plain models. The merge returns a `DngImage` for the existing writer or an explicit failure.

### 5.1 What it aligns on: Bayer-quad aware, so the colour pattern is kept

- Each frame is reduced to a **quarter-size grey image by averaging each 2×2 Bayer cell**. Motion is estimated on that image, so every shift is a whole number of cells, an even number of pixels in the RAW. **A shifted red sample always lands on a red site; the CFA phase is preserved by construction.**
- This is the published method: "we circumvent this problem by estimating displacements only up to a multiple of 2 pixels. Displacements subject to this constraint have the convenient property that displaced Bayer samples have coincident colors" (READ, Hasinoff et al. 2016, §4). Also: "the arrangement of color planes in the Bayer image will be preserved after alignment (the value of a blue pixel will never be replaced by the value of a red pixel)" (READ, Monod, Delon & Veit 2021, §3.1).
- Each frame's black level is subtracted per channel before the grey image is made, so a per-frame black shift doesn't read as motion.
- The cell grid starts at the ActiveArea's origin, where `RawFrameMapping.kt` already re-phases the CFA (READ, `:169-174`).

### 5.2 Method options (recommendation: B)

| Option | What it is | For | Against |
|---|---|---|---|
| A. One global shift per frame | one translation per frame, by search on the grey image | simplest, fast | fails with hand rotation, parallax between near and far subjects (a mushroom and its background) and any moving subject; a 0.5 s-per-frame burst will have all three |
| **B. Tile-based coarse-to-fine shifts** (recommended) | the published phone method: a 4-level pyramid of the grey image; at each level the reference is cut into tiles (8 px at the coarsest, 16 px elsewhere), each searched within ±4 px around the coarser level's estimate; L2 distance at coarse levels, L1 at the finest; the coarse estimate is upsampled using the best of the 3 nearest coarse tiles | handles rotation and parallax piecewise; published parameters; runs on phones; preserves the CFA (5.1) | more code; still a translation per tile |
| C. Dense flow or a warp per pixel | a motion vector or a homography per pixel | follows motion exactly | needs resampling between sites, which breaks the Bayer pattern without a demosaic; that is stage 4's territory |

B's parameters are READ from Monod, Delon & Veit 2021, §3.2 and §6.1: factors 2, 4, 4; tiles 8, 16, 16, 16; norms L2, L2, L2, L1; search radius ±4. Sub-pixel refinement between levels (READ, same, §3.3) is optional; the finest level stays whole-cell (5.1). The coder proposes the exact radii and tile size for 12 MP at section 2's rate, where shifts may be larger than the published bursts saw.

### 5.3 Averaging: floating point, levels from the file's tags, never 2^bits

For each frame f and photosite p of CFA channel c:

1. **Normalise to [0, 1] with this frame's own levels:** v = (x − black[f][c]) / (white[f] − black[f][c]), where black is the 4-value per-frame black level (`SENSOR_DYNAMIC_BLACK_LEVEL`, else the static pattern) and white is the frame's white level (`SENSOR_DYNAMIC_WHITE_LEVEL`, else the static one). Both are what `mapRawFrame` already chooses (READ, `RawFrameMapping.kt:91-103`).
   - **Never 2^bits or the 16-bit container's ceiling.** Android data is low-justified: the S22 delivers 0 to 1023 in a 16-bit word (WhiteLevel 1023, -1038). The owner, 2026-09-22, as quoted in the research note: "The 16 bit DNG is a bucket and whatever fills it is what gets filled. 16 bits but it could be 12 bits of data." OSCam's own rule: "White level derives from bit depth in the profile, never from container width" (READ, `PHILOSOPHY.md`, Strict rules). Its 65520 constant is for left-justified data (READ, the research note, "Known gaps" 2). Carrying it over would mis-scale every value.
   - Per frame, because the camera documents that "Camera sensor black levels may vary dramatically for different capture settings" and reports the dynamic level "per frame" (READ, Android `CaptureResult.SENSOR_DYNAMIC_BLACK_LEVEL`).
2. **Exclude clipped samples, as OSCam does:** a sample with x ≥ white[f] is left out of that photosite's sum and its divisor, so the average there is (sum of clean samples) / (count of clean samples), never sum / N. A photosite clipped in **every** frame is written as white (v = 1), never 0 and never the container ceiling. The per-photosite excluded count is kept, so "all clipped" is known rather than inferred. READ, `frame_average.py` `average_burst`: "any raw sample >= the sensor profile's own white level is excluded from `acc` and from that position's own divisor ... A photosite with zero clean samples ... holds white_level itself ... never 0 ... and never the container ceiling 65535".
3. **Accumulate in float32:** Σ w·v and Σ w per photosite, w being the robustness weight of 5.4 (1 for a still scene, which makes this exactly OSCam's average). Float32 holds a sum of up to 8 values in [0, 1] with about 7 significant digits, far below a 16-bit step. Integer accumulation is ruled out: it "loses the gain averaging gives" (READ, the research note, gap 4).
4. **Result:** mean v per photosite. The reference frame always has weight 1 at every photosite it didn't clip, so no photosite is left without a value unless all its samples clipped (handled in step 2).

### 5.4 Motion in the scene: down-weighted, never ghosted

**Recommended: a per-cell robustness weight in the spatial domain.** For each aligned 2×2 cell of an alternate frame, the difference d from the reference cell (per channel, normalised) is compared with the noise expected at that level, σ²(x) = S·x + O from the reference frame's NoiseProfile, the same model the camera documents: "N(x) = sqrt(Sx + O) Where x represents the recorded signal of a CFA channel normalized to the range [0, 1]" (READ, Android `CaptureResult.SENSOR_NOISE_PROFILE`).

The weight is w = σ²·c / (d² + σ²·c), a Wiener-style shrinkage of the published form, with c a tuning constant. It is near 1 where the frames agree within noise and falls toward 0 where something moved, so a moving leaf or a passing insect comes from the reference frame alone. Tile seams are avoided by computing per tile with tiles overlapped by half and blended with the published raised-cosine window, whose half-overlapped copies sum to 1 (READ, Monod, Delon & Veit 2021, §4.4, equations 13-14).

| Option | What happens to a moving subject | Note |
|---|---|---|
| M1. Plain average after alignment (OSCam as is) | ghosts: a see-through double | OSCam assumes "Static specimens only" (READ, `hdr_merge.py` docstring). Fine on a tripod, wrong handheld. |
| **M2. Spatial robustness weight** (recommended) | taken from the reference frame; slightly noisier there | stays a weighted **average** of the samples, so it is still OSCam's method with a weight; testable per photosite |
| M3. The published frequency-domain pairwise merge (2D DFT per tile, Wiener shrinkage per frequency) | taken from the reference per frequency, keeping matching detail | more denoising and more robust to partial misalignment (READ, Monod, Delon & Veit 2021, §4.2), but it is a denoiser rather than an average, and harder to test bit for bit; a candidate for a later stage if M2 shows tile-edge or residual-ghost problems on the phones |

The constant c and the cell-versus-tile granularity are tuned on synthetic bursts (section 7), then confirmed on the phones. The tuning is reported, never hidden.

### 5.5 When alignment fails: an explicit failure, never a silently blurred average

- **Per frame:** after alignment, the fraction of the frame's cells whose weight fell below 0.5 is that frame's mismatch. A frame above a set limit (proposed 50%, tuned on synthetic data and reported) is **dropped from the merge and logged** with its mismatch. Its weight is not merely low: it is out.
- **Per burst:** if fewer than 2 frames remain (the reference plus one), the merge returns `BurstMerge.Failed(reason)`. The shot then saves the **reference frame alone through stage 2's single-RAW path**, with the message in 3.4. It is never written as "averaged".
- **Reported, not hidden:** the merge returns how many frames went in, which were dropped and why, the fraction of down-weighted cells, and the clipped counts. All of it is logged (CLAUDE.md: no silent fallback).

### 5.6 Writing the averaged result through the existing writer

**No contract change is needed for the file itself** (READ, `domain/raw/DngContract.kt` at `d8f0f944`). `DngImage.samples` is unsigned 16-bit in a `ShortArray`, `whiteLevel` takes 1..65535 (READ, `DngImageLimits.kt:30`), `blackLevel` takes floats, and the encoder always codes at precision 16 (READ, `LosslessJpegEncoder.kt:25`), so a full 16-bit plane round-trips losslessly.

Mapping the float mean to 16 bits:
- **New WhiteLevel W′ = 65535.**
- **New BlackLevel B′:** one value for all four channels, set at the same fraction of the range as the reference frame's mean black. On the S22, 64 / 1023 is 6.3%, so B′ ≈ 4,100. This keeps room below black for the shadows' negative noise, which a black of 0 would clip and so brighten the shadows.
- **Each sample:** y = round(B′ + v · (W′ − B′)), clamped to 0..65535. Any clamp is counted and logged.
- On the S22, one 10-bit step becomes about 60 steps, so averaging's extra precision survives the write. That is the owner's "Averaging does expand the data though" (research note).
- **NoiseProfile:** the DNG model is normalised to [0, 1], like the camera's (READ, Android `SENSOR_NOISE_PROFILE`, which refers to the DNG specification's tag). So the scale change leaves it alone, and averaging divides it: S′ = S / N_eff and O′ = O / N_eff, where N_eff is the burst's effective frame count. Proposed: the median over cells of (Σw)² / Σw², reported in the log. Raw editors use NoiseProfile to set their denoising, so leaving the single-frame value in would make them over-smooth a cleaner file (INFERRED).
- **BaselineExposure:** unchanged. DNG brightness is defined after black and white normalisation, which this mapping preserves (INFERRED from the DNG model; the coder confirms against the DNG 1.4 specification and cites the section).
- **From the reference frame, unchanged:** CFA, ActiveArea, colour matrices and calibration, AsShotNeutral (logged if another frame's differs: AWB should be locked), the lens-shading GainMaps, and orientation (from the reference JPG, as stage 2).
- **Size:** the averaged plane carries real information in more low bits, so lossless JPEG will code it larger than a single frame. Upper estimate for the menu: about 2 bytes a pixel (about 24 to 25 MB) plus the JPG. `rawShotFits`'s worst case (4 bytes a pixel, READ `CameraFormat.kt:98-103`) still bounds it, so the low-storage rule needs no change.

**Stop-and-ask items on the writer contract** (none is proposed for building; each needs the planner, and the owner where it changes what a file says):
1. Writing **BaselineNoise** (tag 50731) or any tag recording that the file is an average (a frame count, a processing note). Recommendation: none in stage 3. NoiseProfile already carries the noise, and any free-text tag is something the clean check must then pass.
2. A **floating-point DNG** (DNG 1.4's floating-point sample format, UNVERIFIED from memory) to keep the float mean unquantised. Rejected: the writer and its lossless coding are integer-only, desktop support is less certain (UNVERIFIED), and 16 bits already hold the precision (above).
3. Any change to the 12.6 MP limit. None needed.

## 12. Open decisions for the owner (plain words)

Each has options and a recommendation. Mockups are in the text because option previews don't show on the phone.

**D1. What the new kind is called.**
It is a RAW file made from several shots averaged together: less grain, the same detail, still unprocessed colour.
- **A (recommended): "Averaged RAW"** in the menu, chip reads **AVG**, with a small line under the row: "less grain, hold still". Says what it is in the owner's own word ("frame averaging", -973) and tells the user the one thing they must do.
- B: "Burst RAW", chip **BURST**. Says how it is taken, not what you get.
- C: "Clean RAW", chip **CLEAN**. Says what you get, but "clean" already means "location removed" in this app's messages (-1003), which could confuse.
- D: make RAW itself averaged and drop the single-frame RAW. **Not recommended:** it would reverse -974's "RAW ... outputs an unprocessed RAW".

**D2. Where it sits in the menu.**
- **A (recommended): after RAW:** JPG, RAW, Averaged RAW (and later RAW+ after it). This reads as "more processing as you go down", and keeps -974's order with RAW+ last.
- B: before RAW, so the better-looking option is seen first.

**D3. How long the user holds still (the frame count).** The camera can only take about two shots a second this way (section 2, one measurement). So:
- **A (recommended, provisional until the probe): 4 frames, about 2 s holding still, 3 to 4 s until saved.** Half the grain of a single RAW.
- B: 8 frames, about 4 s holding still, 5 to 6 s until saved. About a third of the grain; more blur from the hand and more frames thrown away.
- C: a faster capture route built outside the camera library the app uses now. Much faster bursts, but a large architectural change. **Not recommended now.** Raise it only if the probe shows the burst is too slow to be useful.
The probe's numbers come back to you before this is fixed.

**D4. What happens if the subject moves (a leaf in wind, an insect).**
- **A (recommended):** the moving part is taken from the first frame only, so it is sharp but a little grainier there; the rest of the photo gets the full averaging. No ghost, no message.
- B: plain averaging everywhere. Smoothest still areas, but moving things look like a see-through double.
- C: if anything moves, give up and save a single RAW with a message. Safe, but most outdoor scenes have some movement, so it would fall back often.

**D5. Does the camera wait while the photo is finished?**
- **A (recommended for this stage):** the camera holds for the few seconds of saving, showing the first frame as the placeholder (-1004). Simple and nothing can be lost.
- B: you can keep shooting at once while it finishes in the background. Faster to use, but needs a background job that can survive the app being closed, and a burst held only in memory would be lost if it is. Better as a later step once the times are known.

**D6. The new messages' wording** (all in the normal colour, -1019):
- "The frames couldn't be lined up, so this photo was saved as a single RAW."
- "There wasn't enough memory to average frames, so this photo was saved as a single RAW."
Recommendation: approve as written, or edit.

**D7. Flash.** A flash would fire once per frame and slow the burst further.
- **A (recommended):** with the capture flash set to On or Auto, Averaged RAW takes a single RAW, with "Flash photos are saved as a single RAW." The torch is fine and still averages.
- B: hide Averaged RAW while the flash is on. That makes the user wonder where it went (Don't make me think).
- C: flash on every frame. Slow, and the flash's brightness can vary frame to frame.

**D8. Which frame the photo is built around.**
- **A (recommended):** the first frame: the moment you pressed, and the placeholder shows exactly that moment.
- B: the sharpest of the first three, as a phone maker's published burst pipeline does. Sometimes sharper, but the photo may be a fraction of a second after the press.

**D9. Which code it builds on.**
- **A (recommended):** wait until stage 2 (PR #227) is merged to main after its remaining phone checks, then branch stage 3 from main. Nothing is built on unmerged work.
- B: branch now from `raw-stage2` (`d8f0f944`), merging main in later.
