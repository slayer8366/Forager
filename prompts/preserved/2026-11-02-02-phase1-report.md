## 2. Where 15.92°N comes from, and whether one source can feed both
**F1. No file in the repository defines 15.92 as a value.** `git grep` finds it only in [observed]:
- Worker comments (`index.ts:292`, :325) and the Worker README (:65);
- known-bugs.md, RECORD and prompts.

There is nothing in app code. `OfflineMapRepository.kt` holds the zoom range, `MIN_ZOOM` 10.0 and `MAX_ZOOM` 15.0 (:170-171), and no latitude [read].

**F2. The Worker's value is the archive's own header.**
- It reads `pHeader.minLat` from the stored `us.pmtiles` header at request time (`index.ts:588`). It compares a tile against it only above the archive's own max zoom, up to 15 (:610-621) [read].
- At the archive's own zooms, a tile south of its data answers 204 for another reason: the archive holds no tile there, and the world fill stops at z8 (:310, :369, :649-659) [read].
- So for downloads, the line is where the archive has data, not a comparison against a number [inferred from the above].
- All four Worker styles draw from `/us.json`, and the app downloads with `TRAIL_STYLE_URL` (`map/TrailStyle.kt:25`, :84) [observed, read].

**F3. The app can't read the bound from anything the Worker serves today.**
- The `/us.json` TileJSON is built from the archive (`index.ts:592-595`). For the Trail Map archive, though, its south bound is replaced with the world archive's minLat while that archive is in the store (:333-346, :604-606) [read].
- That has been live since 10-22. RECORD -1559: "us.json fetched with a fresh query string gives south bound -85.05". RECORD -1609 confirms it again.
- The TileJSON can't carry a custom field either. `getTileJson` "keeps no custom metadata", which is why the reference-trails manifest has its own route (`index.ts:444-449`) [read].
- C2: the warning doesn't read the map library's store, and nothing here needs to.

**F4. The last reading of the bound is older than the current archive.**
- The last reading was 15.92097°, on 10-22, against the October build (`prompts/preserved/2026-10-22-01.md:145`) [read].
- The Trail Map was rebuilt and uploaded on 11-03 (RECORD -2007, from another session's account) [read].
- Nothing records the new archive's south bound [could not determine].

**Options for "one source"** (stop S2; architecture, so the planner's, and the owner's where it changes what a user sees):
- **A. One source: the archive header, published through the Worker.**
  - How: the Worker publishes the Trail Map archive's own bounds on a small route, as it already does for the reference manifest. The app fetches it when Offline Maps opens, keeps the last value, and decides from that.
  - For: it is truly one source and follows every rebuild.
  - Cost:
    - a Worker change and a folder-only Worker release to main (the map side's lane);
    - new app network code behind an owned interface, plus a stored last value.
  - The user-visible gap: on a first open with no signal there is no value, so no line. That gets logged, but a user south of the line, offline, sees no warning.
  - It doesn't fit inside this dispatch's scope.
- **B. A named constant in the app,** with its source recorded beside it (the header reading, its date, the archive build).
  - That is two sources. A rebuild that moves the edge leaves the app wrong, and no test can catch it, because the archive isn't in the repository.
  - It is exactly what the dispatch says not to do: "Find where 15.92 (or the archive's bounds) is defined and whether the app can read it, rather than copying the number."
- **C. A repository file both builds bundle.**
  - The Worker doesn't need it, because it reads the header. Unless the Worker were changed to use the file in place of the header, which changes its behaviour, the file feeds the app only.
  - It is still a copy of the archive's value.

None of the three describes the data's real extent; see section 5.
