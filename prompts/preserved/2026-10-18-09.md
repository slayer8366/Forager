## What to produce

A report, `docs/audits/2026-10-18-ui-split-survey.md`, covering:
1. **The inventory:** every Kotlin file under `app/src/main/java/.../ui/` over 300 lines, with its line count and a one-line plain description of what the user sees it draw or do.
2. **For each file over 600 lines, its natural seams,** each with a line range: the composables, state holders, layout helpers and pure functions that could stand in their own file. For each seam, say:
   - what it depends on;
   - what depends on it;
   - whether it's pure, meaning it could move with no behaviour change;
   - what makes it hard: private state shared across the file, `remember` scopes, `movableContentOf`, or test hooks reaching internals.
3. **The tests:** which test classes reach into each file's internals (`internal` and `@VisibleForTesting` members, test tags), and would have to move or change with a split.
4. **A proposed target layout:** package and file names for the five largest files, each file aimed at about 200 lines. Mark which splits are mechanical (move only) and which need an interface or a state holder first.
5. **Risks, read from this repository's own record:**
   - touch interception over the map (CLAUDE.md);
   - real insets;
   - `movableContentOf` keeping the MapView alive;
   - the poll loop in `TrackRecordingViewModel`;
   - anything else a move could silently change.
6. **An order of work:** small PRs, each a move with no behaviour change, with the test or check that proves each one changed nothing. Name the first three.
7. **The usual sections:** confirmed vs inferred; could not determine; premises that were wrong; decided beyond scope (should be empty).
