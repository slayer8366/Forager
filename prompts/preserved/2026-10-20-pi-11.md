## What to build

- **Before each connection,** `curl_resume` decides which link carries the default route, from
  `/proc/net/route` (`ip route` fails under the unit; pi-09 measured that). It then uses that link's
  floor: Wi-Fi, an interface matching a pinned pattern such as `wl*`, gets `USCA_DOWNLOAD_SPEED_LIMIT_WIFI`
  and `USCA_DOWNLOAD_SPEED_TIME_WIFI`; anything else gets the existing `USCA_DOWNLOAD_SPEED_LIMIT`
  and `USCA_DOWNLOAD_SPEED_TIME`.
- **Deciding per connection, not per run,** matters. The Pi's link has changed mid-download before:
  the Pi's network memory records that a switch stalls curl, and the restart loop is what recovers
  it.
- **Log the link and floor** used on each connection's line.
- **The Wi-Fi numbers.** Start from the 2026-10-18 loop's 700 kB/s over 40 s, which ran on Wi-Fi
  (pi-09 Phase 1). Check them against that run's own log: `journalctl -u forager-usca-fetch-build`
  and `dl.log`, the Wi-Fi stretches.
  - Report how often the floor would trip, and whether it would ever abort a healthy Wi-Fi
    connection.
  - Pin the result in `pins.env` with its source.
  - If the data argues for different numbers, use them and say why.
- **No route at all:** use the conservative floor, and log it. G's network wait should normally
  have caught this first.
