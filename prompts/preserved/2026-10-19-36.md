## What is known (from two of your reports, RECORD -1467 and -1468)
- **It is pre-existing.** Production 3500 (main 19aa1058) and pre-main 5fd0d4f4 behave the same on the S22 with simulated movement:
  - A (still following when leaving): zoom kept, `cover: SHOW`.
  - B (after a flick) and C (after a 30 px nudge): `cover: MOVE_PENDING`, and the map goes to the located region at about zoom 12.
  - On a still phone it never happens, because the target never goes stale.
- **The mechanism you read:**
  - While following, `shouldMoveCameraToTarget` (`MapCameraMoves.kt:41`) is false. The data refresh (`MapDataRefresh.kt:108-120`) skips its move and does not update `lastAppliedCameraTarget`.
  - A locate fix that differs from the one at app open changes the target (`CompactMapDisplayRegion.kt`), so the target goes stale.
  - A gesture ends following. The camera snapshot saves `following = false` with the stale `appliedTarget`.
  - On return, `MapStyleReload.kt:130-134` restores that stale target as `lastAppliedCameraTarget`. The refresh then sees "not following, and the target differs", and moves the camera to the region at `zoomForRadiusKm(15)`.
  - `coverDecision` (`MapReturnCover.kt:62-77`) predicts this with the same test.

## The behaviour to build
Coming back to the Maps tab, from any tab, after any gesture, the map is exactly where the user left it: same centre, same zoom, same bearing. **Only these still move it:**
1. a new search, or a search frame that hasn't been applied yet;
2. a tap on locate;
3. a camera request from elsewhere, such as the Journal's "show on map" or anything that already sends a camera request;
4. a region or focus that genuinely changed while the map was away. Check what can change it in this app besides a locate fix, and list each source.

**The case to remove:** a target that went stale only because the map was following when it changed.
