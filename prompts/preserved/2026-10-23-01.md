## Build

A Worker route that returns the route data for a rectangle: the cells of every square the rectangle touches, cut with the existing cutter and a one-cell margin. It reads squares from R2 by byte range through the run named in `routing/manifest.json`.
- **The response shape** is yours to propose; it must be what dispatch 2026-10-23-02 can store and hand to BRouter. Agree it in the PR, and say it plainly in your report:
  - one cut file per touched square, with BRouter's own file names;
  - a size and a sha256 per file;
  - the run id, so a download records which build its routes came from.
- **Limits:** a maximum rectangle size, as a named operating limit (CLAUDE.md). The default offline area is 8 km in radius, and the largest is 24 km (route-data report, `docs/navigation/2026-10-21-route-data-report.md`). Requests over the limit are refused plainly, never truncated.
- **Errors are explicit,** never an empty success:
  - a missing manifest;
  - a missing square, where the area touches no data;
  - a checksum failure;
  - an area outside coverage.
- **Caching:** cut results are cacheable by URL plus run id. The run id must be part of the key, so a new run never serves stale cuts.
