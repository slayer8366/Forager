# Dispatch 2026-11-05-01, Phase 1 report: the drop-off's reads of the map's offline store while the map writes; the doubled opening; the signal-return pass (Hazel Cairnwright, verify first)

## Summary

- **Why the read fails.** The app and MapLibre each use their own copy of SQLite, in the same process, and the two cannot see each other's file locks.
  - While MapLibre commits, its rollback journal is valid on disk.
  - The app's read-only connection can't see the lock that should mark that journal as in use, so it judges the journal "hot". It may not roll a hot journal back, so it refuses with SQLITE_READONLY_ROLLBACK.
- **When it happens.** MapLibre commits on every tile and resource it reads from its store, not only when it stores something.
  - So refusals cluster when a map view starts.
  - Opening Offline maps and tapping Navigate both start a map view at the same moment they start reading the store.
- **The fix options.** None of them writes to MapLibre's store, so the "every option writes" stop is not hit.
  - A bounded retry clears the refusal.
  - No read-only option inside the app's process can stop MapLibre committing in the middle of a read that has already started. Only reading from a second process, or not reading MapLibre's store at all, does that. Both are architectural, and one departs from an owner ruling.
- **Two findings outside the named symptom need a ruling:**
  - Android's default error handler, which today's open uses, deletes the database file when SQLite reports corruption. Read in AOSP Android 16, not in the phone's own framework.
  - A second reader, `OfflineReliefTileStore`, opens the store the same way.
- **The doubled opening.** One effect in `ui/log/RecordsTab.kt:242-247` reads the live chip rather than its key. That file is not in the dispatch's file list.
- **The signal-return pass** was never reached in session 14. The app declares signal 30 s after the network validates, and the step left Offline maps 5.8 s after validation.
- **One premise is wrong.** Session 14's "second pass 1.4 s later" was not a retry. It was the doubled opening's second launch.

## Mechanism prediction (coder), first

**The read failure (A2)**
1. The app reads `mbgl-offline.db` through Android's SQLite. MapLibre writes it through its own copy of SQLite 3.45.3, linked inside `libmaplibre.so`. Both run in one process.
2. During each MapLibre commit, the journal carries a valid header. The app's connection cannot see MapLibre's lock, so it takes the journal as hot. Being read-only, it may not roll it back, and Android's open fails at its first read of the file.
3. MapLibre commits whenever it reads a tile or resource from its store (it updates `accessed`), and whenever it stores a response. Its commit windows therefore come in runs while a map view starts. That is the moment the copy pass and the way-to begin reading.
4. With a bounded retry, a refused open is tried again after a short wait. A commit window is milliseconds long, so a later attempt normally finds it closed and the read succeeds. A read still refused at the bound goes by trail and is logged, exactly as today.
5. The retry doesn't change what a successful read is exposed to (section 1.5).

**The doubled opening (A3)**
1. When `RecordsTab` first composes with the Tools latch already set, two effects start together.
2. The latch effect selects Offline maps.
3. The selection effect, keyed on the old chip, then reads the live chip, Offline maps, and opens it: call 1.
4. The key change relaunches it: call 2.
5. Once the effect reads its own key, call 1 sees the old chip and does nothing, so there is one opening.

**The signal-return pass (A4)**
- It fires 30 s after the network validates, if Offline maps is still on screen. Session 14's step left before then.

## 1. Why the open fails

### 1.1 What SQLITE_READONLY_ROLLBACK means
- **[read] `rescode.html`, "(776) SQLITE_READONLY_ROLLBACK":** "indicates that a database cannot be opened because it has a hot journal that needs to be rolled back but cannot because the database is readonly."
- **[read] `lockingv3.html` §4.0, when a journal is hot.** A journal is hot if:
  - "It exists, and";
  - "Its size is greater than 512 bytes, and";
  - "The journal header is non-zero and well-formed, and";
  - "Its super-journal exists or the super-journal name is an empty string, and";
  - "There is no RESERVED lock on the corresponding database file."
- **[read] `lockingv3.html` §4.1:** "Before reading from a database file, SQLite always checks to see if that database file has a hot journal". A hot journal is rolled back before the read, which requires writing.

### 1.2 MapLibre's journal mode and locking

**[read] MapLibre brings its own SQLite on Android**
- `platform/android/android.cmake:11` includes `vendor/sqlite.cmake`.
- `vendor/sqlite.cmake:8` builds `mbgl-vendor-sqlite` as a **STATIC** library, from MapLibre's own `vendor/sqlite/src/sqlite3.c` (`:11-14`).
- `android.cmake:111-124` links that library into `mbgl-core`, PRIVATE (`:122`).

**[read, shipped binary] The 13.5.0 arm64 `libmaplibre.so` confirms it**
- Its needed libraries are `libEGL`, `libGLESv3`, `libandroid`, `libjnigraphics`, `liblog`, `libz`, `libm`, `libdl` and `libc`. There is no `libsqlite.so`.
- It has **0** undefined and **0** exported `sqlite3_` dynamic symbols.
- It carries the SQLite source id `2024-04-15 13:34:05 8653b758…`, which `chronology.html` dates to **3.45.3**.

**[read] How MapLibre opens and sets up its store**
- It opens with `sqlite3_open_v2(filename, &db, flags | SQLITE_OPEN_URI, nullptr)` (`sqlite3.cpp:138`). That is the default VFS.
- It opens read-write-create, with a busy timeout of `Milliseconds::max()`, and runs `PRAGMA foreign_keys = ON` (`offline_database.cpp:55-58`).
- `PRAGMA journal_mode = DELETE` and `PRAGMA synchronous = FULL` are set only when it creates the schema (`:183-184`) or migrates to version 5 (`:209-210`).
- At version 6, the "Happy path" (`:80-82`), it sets neither, so SQLite's defaults apply:
  - "The DELETE journaling mode is the default" (`pragma.html`, journal_mode); only WAL "is persistent".
  - "The default synchronous setting is full" (`atomiccommit.html` §6.2).

**[observed] The end-s14 copy is a rollback-journal store at version 6**
- Header bytes 18-19 are `1 1`. By `fileformat2.html`, that is "1 for legacy; 2 for WAL".
- `user_version` is 6 and `auto_vacuum` is 2.
- So the phone's MapLibre takes the version-6 path: DELETE journal, synchronous FULL, normal locking.

**[read] MapLibre writes when it reads from its store**
- Every tile read first runs `UPDATE tiles SET accessed = ?1 …` (`offline_database.cpp:514-535`).
- Every resource read first runs `UPDATE resources SET accessed = ?1 WHERE url = ?2` (`:363-369`).
- Stored responses are INSERTs and UPDATEs (`:436-512`, `:625-693`).

### 1.3 Why a read-only connection meets a "hot" journal while MapLibre writes

**[read] In a normal arrangement it never would**
- A committing writer first takes a pending and then an exclusive lock (`atomiccommit.html` §3.8). A pending lock "prevents new shared locks from being established".
- A reader that can see those locks is refused its SHARED lock with SQLITE_BUSY (`lockingv3.html` §4.1, step 1).
- Before the commit, the writer's RESERVED lock makes the journal "not hot" (§4.0).
- Either way, the reader is never shown a hot journal.

**[read] Here the reader and the writer are two copies of SQLite in one process**
- **`howtocorrupt.html` §2.3, "Multiple copies of SQLite linked into the same application":** "Database connections opened using one copy of the SQLite library will be unaware of database connections opened using the other copy, and will be unable to work around the POSIX advisory locking quirks."
- **§2.2:** "any thread in the same process with a file descriptor that is holding a POSIX advisory lock can override that lock using a different file descriptor", and "the close() system call will cancel all POSIX advisory locks on the same file for all threads and all file descriptors in the process."
- **[inferred]** So Android's copy, opening read-only, sees a valid journal and no lock it can recognise. By §4.0 that journal is hot, and the read-only connection refuses with 776.
  - This fits all three observations. I did not read SQLite's unix locking source, which is not in the permitted sources.

**[observed, scratch experiment: stock SQLite 3.46.1, synthetic data, no repository code]**
- A writer began a transaction and updated a row, with `journal_mode=DELETE` and `synchronous=OFF`. Its `-journal` was then on disk.
- At that moment:
  - **A.** A read-only reader in another process, which can see the writer's lock, read normally: `1|3000`.
  - **B.** A second read-only connection on the same library in the same process read normally: `(1, 3000)`.
  - **C.** The database and journal were copied to another folder, where no lock holder exists. The command-line shell's reader got: "attempt to write a readonly database (8)".
  - **D.** The same copied pair, read through the library binding, got: `attempt to write a readonly database code 776 SQLITE_READONLY_ROLLBACK`. This is the phone's error.
  - The copied journal was still present afterwards: the read-only reader never rolls it back.
- So the only difference between a normal read and 776 is whether the writer's lock can be seen.

**[observed, same scratch, writer at the default synchronous FULL, MapLibre's setting]**
- Mid-transaction, the journal begins with eight zero bytes (`00 00 00 00 00 00 00 00`). The copied pair was *not* hot: readers C and D read normally.
- `fileformat2.html` §3: "A rollback journal is only considered to be valid if it exists and contains a valid header". The header string is `d9 d5 05 f9 20 a1 63 d7`, which the unsynced run did write.
- `atomiccommit.html` §6.2: the journal is flushed before commit, "and only then is the page count in the header changed".
- **[inferred]** So MapLibre's journal looks hot only during the commit itself (`atomiccommit.html` §3.7-3.11):
  - the journal is flushed;
  - the exclusive lock is taken;
  - the database pages are written and flushed;
  - the journal is deleted.
  That is exactly the stretch when MapLibre is changing the database file.

### 1.5 What a read that succeeds is not protected from, and a latent delete

**[inferred, from 1.3] The invisibility runs both ways**
- MapLibre's copy cannot see the app's SHARED lock either. So MapLibre can commit while the app is in the middle of a read.
- `lockingv3.html` §3.0's guarantee does not hold here: "no other thread or process is allowed to write to the database file while one or more SHARED locks are active".
- A read that overlaps a commit can see some old and some new pages. The result could be:
  - bytes that don't decode: by trail, logged, today's path;
  - wrong bytes;
  - an SQLITE_CORRUPT report.
- **[observed]** None has been seen: 0 lines matching "Corruption reported", "deleting the database file" or "SQLITE_CORRUPT" in either session's log.

**[read, AOSP Android 16 bytecode] What a corruption report does to today's open**
- `openDatabase(String, CursorFactory, int)` passes a null handler to the four-argument overload.
- The `SQLiteDatabase` constructor then installs `new DefaultDatabaseErrorHandler()`.
- Corruption reaches that handler:
  - from `SQLiteDatabase.open()`, which logs "Database corruption detected in open()", calls `onCorruption()` and tries again;
  - from `SQLiteQuery` and `SQLiteStatement`, which both call `onCorruption()` on `SQLiteDatabaseCorruptException`.
- `DefaultDatabaseErrorHandler.onCorruption` logs "Corruption reported by sqlite on database: ", then `deleteDatabaseFile(path)`. That logs "deleting the database file: " and calls `SQLiteDatabase.deleteDatabase(File, false)`.
- So on AOSP, one corruption report on the app's **read-only** connection deletes `mbgl-offline.db`, and every offline area with it.
- Today's open is that open: `MapLibreOfflineBasemap.kt:56`, and `OfflineReliefTileStore.kt:47` and `:73`.
- **[could not determine]** whether the phone's vendor framework keeps this handler.

## 3. The fix options (none chosen)

**3.1 Retry the read-only open with a bounded wait** (in `MapLibreOfflineBasemap.read`)
- **Can it write to MapLibre's store?** Never. It is the same `OPEN_READONLY` open. A read-only connection cannot roll a journal back: that refusal is what 776 is, and scratch C and D left the journal in place.
- **What it does:**
  - on `SQLiteReadOnlyDatabaseException` from the read-only open, it waits, opens again, up to a bound, and logs;
  - then it fails as today;
  - on a read-only connection to a rollback-journal file, 776 is the code that occurs [inferred].
- **Cost:**
  - about 30 to 40 lines in a small new file beside the reader;
  - its limits with reasons, as `DropOffMapLimits.kt` (37 lines) does;
  - the numbers are an operating limit for the planner, not a measurement. For example, 5 attempts at 50, 100, 200 and 400 ms, under 0.8 s in all;
  - one immediate retry is not enough, because windows come in runs [inferred].
- **What the user notices:**
  - normally nothing;
  - at worst, Navigate's card waits up to the bound before it settles;
  - past the bound: by trail, logged, as today;
  - a genuinely hot journal (MapLibre stopped mid-commit) costs each read the full bound, until MapLibre rolls it back [inferred].
- **What it leaves:** the exposure in 1.5, unchanged, neither better nor worse.

**3.2 The app's own error handler on the same open** (the four-argument `openDatabase`, which exists in AOSP 16)
- **Can it write to MapLibre's store?** Never. It removes the one path by which today's read can delete MapLibre's store (1.5).
- **Cost:**
  - a few lines;
  - a JVM test with a store SQLite reports as corrupt. Predicted today: the file is deleted under Robolectric's AOSP framework (to be shown failing first). After: the read fails, logged, and the file is still there.
- **What the user notices:** nothing, except that in the case it guards, their offline maps survive.
- **Limits:** it is not a fix for the refusal alone. It goes beside any option. The same applies to `OfflineReliefTileStore`.

**3.3 A different open: the URI parameters `immutable=1` or `nolock=1`**
- **[read] `uri.html`, immutable:** SQLite "skips all file locking and change detection … If this query parameter … asserts that a database file is immutable and that file changes anyhow, then SQLite might return incorrect query results and/or SQLITE_CORRUPT errors."
- **[read] `uri.html`, nolock:** it "disables all calls to the xLock, xUnlock, and xCheckReservedLock methods … If two or more database connections try to interact with the same SQLite database and one or more of those connections has enabled 'nolock', then database corruption can result."
- **Can either write to MapLibre's store?** Neither writes. But neither is safe while MapLibre writes, by SQLite's own documentation:
  - with `immutable`, the reader ignores the journal and can read half-committed pages. A CORRUPT report on Android's default handler is 1.5's delete;
  - with `nolock`, I expect the same refusal, since a reader that skips the lock check still sees a valid journal [inferred].
- **[could not determine]** whether Android's `SQLiteDatabase` passes an SQLite URI through on the phone.

**3.4 Read through MapLibre's own API**
- **[read, `javap` of the 13.5.0 classes]** Nothing returns stored bytes:
  - `OfflineManager`: regions; reset, pack, invalidate and clear of the ambient cache; cache size; tile limit; automatic pack; `putResourceWithUrl`;
  - `OfflineRegion`: status, delete, invalidate, metadata;
  - `FileSource`: paths, API key and URL, and a resource transform, which only rewrites URLs.
- **[read, binary]** No `sqlite3_` symbol is exported, so the app cannot use MapLibre's copy of SQLite either.
- **[inferred]** The live map's feature queries read only tiles loaded for the screen, not the area tiles the copy pass and the way-to need.
- **Verdict:** not available at 13.5.0.

**3.5 Read from a second app process** (for example, a small provider in its own process that opens the store read-only and returns tiles)
- **Why it differs [inferred from docs, and scratch A]:**
  - POSIX advisory locks do separate processes;
  - the reader would see MapLibre's commit locks: refused with SQLITE_BUSY, then waiting on Android's busy timeout, which I have not read;
  - MapLibre would see the reader's SHARED lock and wait for it; its timeout is unlimited (`offline_database.cpp:57`);
  - it is the only option I found that restores SQLite's own protection between the two.
- **Can it write to MapLibre's store?** Never, if that process opens the store read-only and never starts MapLibre.
  - Today the app starts MapLibre in every process (`MapLibreStorage.kt:20-22`), and MapLibre opens its store read-write (`offline_database.cpp:55-56`). That would have to be guarded, or the second process becomes a second writer.
- **Cost:** high.
  - a new process, with its memory and cold start;
  - tile bytes passed between processes;
  - a manifest change and a process-aware application start;
  - mostly device-only to test;
  - a reader that holds its lock too long stalls MapLibre's writes indefinitely, and with them the map's own caching.
- **What the user notices:** nothing normally; perhaps a short delay on the first read after that process starts.
- **Verdict:** architectural, so a stop.

**3.6 Don't read MapLibre's store for the drop-off** (the app's copy holds every tile the drop-off needs, and the way-to reads the copy alone)
- **Can it write to MapLibre's store?** Never.
- **It conflicts with two rulings:**
  - P3 (RECORD -2110): MapLibre's marked tile first;
  - the owner's A7: "Only when missing (Recommended)" (`DropOffMapFetch.kt:31`).
- **Other consequences:**
  - the template is still read from MapLibre's store, once per pass;
  - the copy's freshness becomes S3's question again;
  - more tiles are fetched (5 more on the S22; the whole cover in general).
- **Verdict:** owner-level, so a stop.

**3.7 Read only when the map is quiet** (for example, after the map reports it is idle)
- **Can it write to MapLibre's store?** Never.
- **Limits:** only partial. MapLibre stores network answers at any time, and nothing protects a read already under way. It is weak.

**Rejected, each a stop:**
- **opening writable:** it would roll back MapLibre's live commit (`lockingv3.html` §4.1, steps 3 to 6);
- **changing MapLibre's configuration:** its journal mode to WAL, its read-only mode (`offline_database.cpp:46-52`, `:1490-1499`), or turning its network off. WAL's shared index relies on the same locks, so it would not help anyway [inferred];
- **copying the store and reading the copy:** `howtocorrupt.html` §1.2, "The backup copy then might contain some old and some new content, and thus be corrupt."

## 6. The signal-return pass

**[read] How the trigger works**
- `OfflineRegionsList.kt:91-103`: the list remembers having seen no signal *while it was composed*. When the app's no-signal state turns false, it calls `onSignalReturned` once. It never calls it at first composition.
- That leads to `AvailabilityViewModelOfflineMaps.kt:80-85`, which runs the route fetch and the drop-off passes.
- The ViewModel and the list read the same state (`MainActivity.kt:108`, `:119`, `:410`).
- That state turns to signal only after **30 s** of validated network (`NetworkSignal.kt:33`, `:57`; logged at `NoSignalTrailMap.kt:144-150`).

## Premises that were wrong

1. **"A second pass 1.4 s later worked"** (A2; RECORD -2116). Nothing in the code retries a failed pass.
   - That pass was the doubled opening's second launch, released by the drop-off lock. Its first request was at 04:21:51.881, 148 ms after the first launch's last refusal.
   - No other trigger could start it: first composition never fires the signal trigger, no download completed, and no "Try again" was shown [inferred].
2. **A4: "Signal returning while Offline maps was open started no pass in about 15 s."** By the app's own signal, it had not returned while the list was open. The app declared signal 24.3 s after Back.
3. **RECORD -2116's inference that "MapLibre was mid-write, which a read-only connection can't roll back"** is right as far as it goes. But a journal whose writer's lock can be seen is not hot (`lockingv3.html` §4.0). It looked hot only because the two SQLite copies can't see each other's locks. So a read that succeeds is not protected either.
4. **"Why `PRAGMA cache_size`"** assumes the statement matters. It is a vendor step of the phone's open, absent from AOSP Android 16, and any first read fails the same way. On the JVM it won't be the failing statement.
5. **Item 2's "every MapLibre write, or only some":** MapLibre also writes when it reads, and only the commit part of each write is a window.
6. **The dispatch's file list:** the doubled opening's cause is in `ui/log/RecordsTab.kt`, not in the two files it names.
7. **A code comment, not the dispatch:** `MapLibreOfflineBasemap.kt:17-18`'s "Nothing is written" holds for SQL. It does not hold for Android's default handler, which deletes the file on a corruption report (AOSP 16).
