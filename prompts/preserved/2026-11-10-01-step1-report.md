### Verify first 2: what a root `404.html` does on Pages

**The documented mechanism.** Cloudflare's "Serving Pages" docs (updated 2026-10-10) say that without a top-level `404.html`, Pages treats the project as a single-page app and serves `/` for every unmatched path. That is today's behaviour. With the file present, Pages serves the nearest `404.html` up the directory tree, with status 404.

So the file switches the **whole site's** not-found mode, not one path.

**Paths that work today, and why they stay the same.** Each one in the dispatch's list is matched by a file, a redirect or a function route before the not-found handling runs. The middleware passes the status through unchanged (`_middleware.js:65-69`).

**The forecast demo:**
- **A missing tile is not handled like an empty one.** `tileBytes` (`app.js:83-91`) throws on `!resp.ok` and on any non-PNG type. A missing tile already throws today ("not a PNG", on the HTML 200) and will throw "HTTP 404" after. In both cases the tile draws nothing, and a tap shows "Could not read the value here", whereas an empty tile shows "No data here". `pilot.js:82-90` behaves the same way.
- **The page can't actually request a missing tile.** I computed the tiles inside the source bounds (`app.js:231-232`) using MapLibre's own rule and compared them with the repo. Each of the four layers needs 570 tiles and has 570: none missing, none extra.
- The vendored fonts are complete: four font stacks with 256 ranges each.
- So the demo's behaviour does not change.
