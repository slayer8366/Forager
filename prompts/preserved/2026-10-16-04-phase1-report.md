## Phase 1 report: dispatch 2026-10-16-04, the lens chooser on engine A

**Summary.** The lens chooser can be built, but several premises in the step path don't hold as written. The biggest:
- The DNG "default-crop tags" don't do what -1104 expects in any editor I could check.

### 1. ForagerDngWriter (read)
- **ActiveArea:** written, but only when the camera reports a pre-correction active array (`DngFileWriter.kt:204`). Its value comes from `RawFrameMapping.kt:104-117`: (0, 0, h, w) when the frame is exactly that rectangle, otherwise the rectangle's own offset.
- **Not written:** DefaultCropOrigin, DefaultCropSize, DefaultScale, BestQualityScale and DefaultUserCrop. They are absent from the tag list (`DngFileWriter.kt:28-64`) and from `entriesFor` (`:164-208`).
- **What readers assume when they are absent** (DNG 1.7.1.0 spec, read): crop origin 0,0; crop size ImageWidth x ImageLength; scale 1.0. The file says DNG 1.4 (`:184`).
- **The check:** `DngCheck` only refuses forbidden tags (`DngCheck.kt:12-16, 54-55`), so new tags would pass it.
- **A src/main change is unavoidable.** `DngImage` has no crop field (`DngContract.kt:24-40`). That file's header says "Not to be changed here without the planner" (`DngContract.kt:5-6`).

### 2. Which editors honour the crop tags
Each item is marked by how I verified it.

- **DNG spec (read, 1.7.1.0):**
  - DefaultCropOrigin and DefaultCropSize are meant for "extra pixels around the edges of the final image" that "help prevent interpolation artifacts".
  - DefaultUserCrop (tag 51125, added in DNG 1.4) is a crop in 0..1 coordinates whose default "correspond[s] exactly to the default crop rectangle".
  - So a zoom crop matches DefaultUserCrop's meaning, not DefaultCrop's.
- **LibRaw (read, source at master, 0.22.0):**
  - It parses both tags (`tiff.cpp:1369-1418`) into `raw_inset_crops[0]` and `[1]` (`identify.cpp:1435-1470`).
  - The user crop is used only if the DefaultCrop pair is in the same IFD.
  - Neither is applied unless the app calls `adjust_to_raw_inset_crop` (API docs). By default that call ignores any crop tighter than 0.55 of width or height, so a 2x crop (0.5) would be ignored.
- **darktable (read, rawspeed `DngDecoder.cpp` and darktable master):**
  - DefaultCrop is applied as a hard cut at decode (`DngDecoder.cpp:535-577`). Inside darktable the full frame can't be recovered.
  - DefaultUserCrop only pre-fills the crop module's values with the module left switched off (`exif.cc:927-956`, `crop.c:891-914`). The photo opens uncropped, and the crop is there if the user turns the module on.
- **RawTherapee (read, dev at `b2ee504`, 2026-10-13):** a grep of all of `rtengine/` and `rtgui/` finds no DefaultCrop, DefaultUserCrop, 50719, 51125 or inset-crop use. It ignores both tags.
- **A widely used commercial editor (Adobe's): unverified.** I found no Adobe documentation, only forum posts, which the dispatch excludes.

**Stop: a premise is wrong.** "Editors that honour the tags open it cropped, and the full frame stays recoverable" holds in none of the editors I checked:
- With DefaultCrop: opens cropped in darktable but can't be recovered there; ignored by LibRaw-based apps unless they opt in; ignored by RawTherapee.
- With DefaultUserCrop (plus DefaultCrop set to the full frame): recoverable everywhere, but no checked editor opens it cropped. darktable offers it as the crop's starting value.

The owner needs to pick one.

### 3. How engine A switches lens and crops (read, plus platform docs)
**Today:** only the RAW stream is a physical stream (camera 5). The preview and JPG are logical streams (`Camera2PlatformCamera.kt:325-333`). No zoom or crop is set anywhere in engine A.

**Does it reconfigure each time?** Yes. A stream's physical camera is fixed when the session is built (`outputsFor` → `createSession`, `:301-305`). The documented API changes a physical stream's camera only at session creation; that it can't change on a live session is inferred.

**Can one session hold several lenses?**
- The platform guarantees nothing: "Combinations of logical and physical streams, or physical streams from different physical cameras are not guaranteed" (LOGICAL_MULTI_CAMERA notes, read). Each combination has to be asked for.
- What is guaranteed: hidden physical cameras' standard stream sets "must be supported through the logical camera using physical streams". The RAW table includes preview + JPEG MAXIMUM + RAW MAXIMUM (`CameraDevice.java` RAW table, read).
- Cameras 5, 6 and 7 are hidden and list RAW on both phones (reach.jsonl). So preview + JPG + RAW, all on one lens, is documented-safe for 5/6/7.
- Camera 2 (the ultra-wide) is listed directly, so through camera 0 it needs the query. The probe did reach it that way.

**How to crop the preview for zoom:**
- The platform's crop region applies to physical streams only through per-lens request settings, and only if the phone lists the crop key for them. That list wasn't logged, so I could not determine it. One `adb shell dumpsys media.camera` on each phone would answer.
- Otherwise the logical zoom setting gives physical streams a view "not smaller than" what is asked, which is not exact.
- Fallback: scale the viewfinder's own display (a view transform). It works, but at 2x the picture is visibly softer.

**Does a crop region apply to the JPG and enlarge it? (read)** Yes: "Output streams use this rectangle … then scaling the sensor input to match the output's configured resolution." RAW is "not croppable unless supported" (the CROPPED_RAW option).

**But the S22's two telephotos (and the S26's 3x) have 3648x2736 sensors.** A physical JPEG's guaranteed size is that lens's own maximum. Whether those lenses list a 4000x3000 JPEG wasn't logged, so I could not determine it. If not, the choices are:
- (a) enlarge the JPG in software, which means decode, crop, scale and re-encode, a second JPEG generation, an estimated 0.3 to 0.6 s;
- (b) save 3648x2736.

**Stop.**

**Logical zoom instead (HAL picks the lens):** the phone chooses differently from the owner's rule. In -1079 the S26 stayed on camera 6 from 3x to 5x and moved to camera 7 only near 9.9x. The JPG and RAW could then come from different lenses (engine already logs `raw_sensor_mismatch`, `PlatformCameraEngine.kt:592-594`). I don't recommend it.

**Switch latency, estimate only:**
- S26: about 0.45 to 0.55 s of frozen or blank picture per switch. This is -1098's 507 to 581 ms first frame minus 50 to 60 ms of camera open.
- S22: about 0.8 s (-1101: 1,029 ms minus 253 ms).
- A pinch that crosses a lens boundary would blank mid-gesture.

**Stop: behaviour the step path doesn't cover:** what the row and picture show during a switch, and whether the shutter waits.

### 6. Stage 3 bursts and zoom (inferred, nothing built)
- One burst is one session, so every frame comes from the same lens; a lens change mid-burst is impossible.
- The zoom should be frozen at the shutter press, so every frame carries the same crop.
- For RAW the crop is only a tag, so the merge runs on the full uncropped image and the crop tag goes on the merged file. The crop is applied after the merge, and the margin helps frame alignment.
- Per-lens frame rates differ (23 to 30 fps, -1095 and -1101), and exposure is locked on the chosen lens.
- No zoomed JPG burst is implied.
