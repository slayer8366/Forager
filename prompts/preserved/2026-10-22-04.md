# Dispatch 2026-10-22-04: a deploy button for the tile Worker

**Coder:** Hazel. **Planner:** Rowan. **Owner's go:** asked "How should server deploys work from now on?", the owner chose "A: deploy button (Recommended)": "A GitHub job deploys the tested server file only when started; you say 'deploy', I start it. One-time setup: a limited Cloudflare token added as a GitHub secret. A small Hazel dispatch builds the job." In the planner's window, 2026-10-22.
**Base assumed:** origin/pre-main at 563e9b756 or later. Verify it.

**Why:** GitHub is disconnected from Cloudflare's own builds (RECORD -1560), so every Worker change is a hand paste of the `pmtiles-worker-dist` artifact.

**Build:** a new workflow file, separate from `ci.yml`, that deploys `server/pmtiles-worker` to Cloudflare **only when started by hand** (`workflow_dispatch`). No push, PR or schedule trigger, ever.
- **Inputs:** the git ref to deploy, defaulting to pre-main.
- **It deploys exactly what CI tested:** it builds and runs the Worker tests on that ref first, and deploys only if they pass. Say how you guarantee it's the same bundle the tests ran on.
- **Deploy:** `wrangler deploy` with the pinned wrangler from the lockfile, using a repository secret `CLOUDFLARE_API_TOKEN`. The account id is already in `wrangler.toml`.
- **The log prints** the deployed version id, the bundle's sha256 and the ref.
- **Concurrency:** one deploy at a time. A second start waits; it never cancels a running one.

**Verify first and report, then STOP before merging anything:**
1. **What `wrangler deploy` overwrites.** Does it replace bindings and variables set by hand in the dashboard and missing from `wrangler.toml`, for example PUBLIC_HOSTNAME, CACHE_CONTROL or PMTILES_PATH? Read wrangler's own docs or code at the pinned version: `keep_vars` and similar. Then write the owner a checklist of what to compare in the dashboard (Settings › Variables and Bindings) before the first run.
2. **The least token permission** that `wrangler deploy` needs for this Worker with its R2 binding, read from Cloudflare's or wrangler's docs. Write the owner's token steps:
   - which template or custom permissions;
   - account scope limited to the one account;
   - an expiry, if you recommend one.
3. **Anything in the deploy that differs from today's hand paste:** compatibility date, minify, observability.

**Not in scope:**
- running the deploy;
- creating the secret;
- any change to `ci.yml` or to Worker behaviour.

If the workflow can't be tested without the secret, say what was and wasn't tested. A run without the secret should fail clearly at the deploy step, after the tests, and that's a fair test.

**Deliver:** a PR into pre-main, with the owner's setup steps and the dashboard checklist in its body. Report with the completion-report skill, and give your model.
