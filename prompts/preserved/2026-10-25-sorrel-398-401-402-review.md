### 1.1 The 90° test can never subtract

`metersPastLineStart` (WayHomeProgress.kt:163-173 at `da3cc4911`) returns `GeoDistance.metersBetween(start, current)` when the dot product of the first stretch (node 0 to the first node more than 0.5 m from it) and the vector to the fix is `<= 0.0`, and `0.0` otherwise. A haversine distance is non-negative, so the term is `>= 0` on both branches. The vectors are in metres on a flat projection about `start.lat` (`GeoDistance.metersPerDegree`, GeoDistance.kt:177-179, the same projection `OffTrackJudge.metersToLine` uses), so the sign test is the angle test it claims to be. The epsilon handles a repeated first point, which would otherwise make the stretch a zero vector and the dot product 0 for every fix, reading everyone as past; with only one distinct node the function returns 0. Confirmed by the replica as well: 30,246 grid points within 70 m of six lines' starts, 0 negative values (section 1.5).

The term is added at :146 only when `figureIndex == 0`. A fix beside the start at exactly 90° (the -1634 cases, 35 m and 49.9 m square) has dot product 0 and so adds the distance, which is what -1634 ruled ("Add it, never short").

### 3.3 A consequence for the owner (402-1, Medium)

Read from `WayHomeWatch.judgeStray` (WayHomeWatch.kt:148-168) and `OffTrackJudge.next` (OffTrackJudge.kt:96-113) together with this change. A re-route starts when a gated fix is more than `WAY_HOME_STRAY_METERS` (50 m) from the line, once per stray, re-armed below 45 m. The new line's dotted part runs from the newest stored point back along the stray, and under #402 that part counts as on course. The off-track alert needs the walker more than 40 m (plus accuracy) from the path and every counted line for 15 s and three readings.

So on a way home along trails, a walker who strays steadily is 40 m off at some moment, 50 m off about 10 s later at walking pace, and re-routed then; the new dotted part reaches back to near their position, the judge's on-course branch runs, the hold clears (`:106-107`), and the alert does not fire. If they keep going, the same happens at the next 50 m. The alert fires only if a re-route does not come: a stray that keeps 40 to 50 m off for 15 s, a re-route that fell back to the track (`reroutingEnded`), or the stored track lagging the walker by enough that the dotted part's end is itself more than 40 m behind them (the flush lag -1636 describes, up to about 42 m, which dispatch 2026-10-25-10 is to close). Before #402, with #399 alone, that steady stray alerted once at 15 s.

This is what the ruling says, "following any line the app draws never raises the alert", applied to a walker who is always near the line just drawn for them. It is a consequence of the ruling, not a defect in the code, and the re-route is itself a signal on the map. But it does mean the off-track alert on a trail way home becomes rare, and after -10 lands, rarer. The owner should hear it in those terms before the S22 check, so the check does not file "no alert while straying" as a bug or as a pass without a ruling.

### 3.4 The coder's track-only case: real, and older than this PR

`routeHome` (RouteHome.kt:149-189) builds the track-only line from `track.points`, the whole stored track, from the most recent stored point back to the start (`:153, :158, :171`), so after Return it includes every stored stray. `ReturnWatch.startReturn` snapshots `pathAtReturn = keptPoints.toList()` (`:207`) and the judge is built on that (`:278`); `shownTrailOf` returns null for a track-only way home (`line == null`), so nothing after Return is counted. A walker who strays after Return on a track-only way home and follows the dotted track line back is therefore more than 40 m from everything counted, and gets the alert while on the drawn line, just as 399-1 described for the trail case. **Real**, and present on every return before step 7, since the track was the only way home then.

What makes it different from 399-1, and why it is the owner's call rather than a one-line follow-up: the re-route's `trackBack` is a snapshot, fixed when the line is shown, so counting it leaves the alert able to fire when the walker leaves *that* line. The track-only line is rebuilt from the live stored track on every tick, so counting it as drawn would count the walker's own last points and the alert could never fire. The shape that matches 399-1 would be to count the track line as it stood at some fixed moment (the first fix of the stray, say), which is a design, not a fix. Not for this PR; the coder was right to stop at it.
