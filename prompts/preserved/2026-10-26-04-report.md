# Report on dispatch 2026-10-26-04: what fills the test JVM's heap

Hazel Cairnwright (coder, Opus), 2026-10-26. This is a measurement only. Nothing was fixed, and no branch that merges was changed. The diagnostic branch is `caption-oom-diag` (`235b01250`, `0e5226c3f`), cut from pre-main `10142c1d2`. It was never opened as a PR. Its CI ran through "Run this branch" (workflow_dispatch). No Gradle ran on the laptop and no device was used. The heap limit was not changed.

Sizes are in MiB (2^20 bytes). The test JVM's limit is 512 MiB.

## The answer in brief

- **The heap is full before the caption tests start, and it stays full.** After a full GC, the live heap is 490 MiB at classes 660 and 665. That leaves about 22 MiB of the 512 MiB limit. It stays between 488 and 494 MiB from class 625 to the last class, 746. It does not drain after the caption tests.
- **It fills in steps, not as a steady leak.**
  - 103 MiB at class 5.
  - 296 MiB by class 35.
  - About 395 MiB by class 600.
  - 492 MiB by class 630.
  - Flat after that (+0.8 MiB over the last 115 classes).
- **The largest single holder is Robolectric's own resource code (suspect 1, but not exactly its sandbox cache).** It keeps one decompressed framework resource table per Android SDK the suite uses, in static registries that live for the whole JVM. The tables come to 127.1 MiB. Four of the five belong to SDKs (27, 28, 30, 33) used by only six test classes.
- **The routing engine's profile cache (suspect 2) is not it.** It retains 0.7 MiB.
- **Two more holders came up that neither suspect covers:**
  - A Robolectric text-layout shadow's static registry: 40.0 MiB.
  - 38 app `Application` object graphs kept alive by statics: 49.6 MiB together. 23 of them are first reached through a test-only collector leak on a Kotlin `object`'s flow (`NoBackBy.shown`).

## 4. Which suspect

- **Suspect 1, Robolectric held for the whole run: yes, but wider than the sandbox cache.**
  - The sandboxes are alive and never evicted. They hold the line-break registry (40.0 MiB) and the `Application` graphs (49.6 MiB).
  - The largest holder, the per-SDK framework resource tables (127.1 MiB), sits in Robolectric statics loaded by the app class loader, not in any sandbox.
  - Evicting sandboxes would therefore not free those tables. That is inferred from where the classes live (the GC-root path ends at `AppClassLoader`); it was not tested.
  - A new JVM would free them.
- **Suspect 2, the routing engine's cache: no.** 0.7 MiB.
- **Not in either suspect:** the test-only `NoBackBy` collector leak, the JDK's open-jar directories (41.2 MiB, mostly the android-all jars, one per SDK), and the `MethodType` table (22.7 MiB).

Per SDK, the four non-36 SDKs cost at least 132.8 MiB in tables and jar directories:

| SDK | Table + jar directory | Classes using it |
|---|---|---|
| 33 | 45.5 MiB | 2 (`AlertDeliveryOutcomeTest`, `AndroidAlertDeliveryTest`; three methods) |
| 30 | 38.4 MiB | 2 (`AndroidAlertDeliveryTest`, `BackByAlertDeliveryTest`) |

They also cost whatever their sandboxes hold, not mapped. Six test classes in all use them, out of 746 (one class uses both 30 and 33), and that is more than a quarter of the live heap.

## 5. Options for a fix (none built; the owner's choice)

1. **Raise the test heap to 1 GiB** (`maxHeapSize = "1g"`).
   - Cost: one line. A heap-limit change, so the owner's.
   - Gives: headroom goes from about 22 MiB to about 534 MiB. The live set is flat after class 630, so the margin is stable today. It would absorb roughly ten more SDK-sized steps.
   - Risk: it hides the next step instead of showing it. Local Robolectric runs use the same limit. The runner's memory was not checked.
2. **Run the six non-36-SDK classes in their own test JVM**: a second `Test` task with a filter, or a category.
   - Gives: about 133 MiB of tables and jar directories, plus their sandboxes, leave the main JVM, and no coverage is lost.
   - Cost: one more JVM start. In this run the worker started at 04:15:05.6 and the first class (4.4 s, including the first sandbox) began 0.6 s later. A new sandbox costs 1 to 2 s on a warm runner (classes 8, 10 and 11).
   - The CI's summary step reads only `test-results/testDebugUnitTest/`, so it and the report upload would need to read the second task's results as well. That makes it a CI change too.
   - Risk: a class list that must be kept up to date. A new non-36 class added to the main task would bring its table back.
3. **A fresh JVM every N classes** (`forkEvery`).
   - Gives: everything above is dropped at each fork, including the line-break registry and the `Application` graphs.
   - Cost: about 5 s of start-up plus JIT warm-up per fork. Estimated from the timings above, not measured. With N = 100, that is 8 forks, perhaps a minute.
   - Risk: a test that depends on run order would show up. Each fork that meets a non-36 class reloads its table.
4. **Two JVMs side by side** (`maxParallelForks = 2`).
   - Each JVM still loads whatever SDKs land in it. The split is not under our control, so the saving is unpredictable. Not recommended over 2 or 3.
5. **Stop the `NoBackBy` collector leak.** For example, tests that build `TrackRecordingViewModel` pass their own `BackByControl`, or `NoBackBy` becomes a per-ViewModel instance.
   - Measured saving on its own: about 0.3 MiB, because the `Application`s have other roots.
   - Worth doing for hygiene, not as the fix. The production default is not used (factory line 35), so a test-side change would do.
6. **Read only the pixels the caption tests need** (from the earlier report). Removes the 7.9 MiB request but leaves the heap at 490 MiB for the next large allocation.
7. **Upstream.** The line-break registry and the native resource registries never release their entries. That is Robolectric's to change, and would be a report to them. Not priced.

My reading for the owner: option 2 addresses the largest holder at its cause with no coverage loss. Option 1 is the cheapest margin. Option 3 bounds everything at a time cost. Options 5 and 6 are hygiene.
