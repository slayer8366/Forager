## Mechanism prediction (coder), first

1. **Opening Offline maps with signal starts a copy pass for every listed downloaded area.**
   - The pass does not use the route fetch's selection. On the S22 that selection takes neither area, because both areas' routes are already stored.
   - The pass runs once per opening and never loops.
2. **The pass works out which tiles are wanted, per area.**
   - It starts from the area's zoom-15 tiles: the cover of the same rectangle MapLibre downloaded.
   - It drops every tile MapLibre's store already holds with the barrier mark.
   - It drops every tile the app's copy already holds.

3. **Each wanted tile is fetched from the server's basemap tile URL, within an explicit operating limit.**

4. **The way-to reads through a new layered `OfflineBasemap`, per tile:**

## 2. Where and how the copy is stored

**Proposed: files beside the route data, one folder per area, not Room.** The path is `files/offline_basemap/<area id>/15-<x>-<y>.mvt`. Each file holds the tile's gzip body as served, so the reader's existing unwrapping applies (`StoredTiles.kt:28-31`), plus an empty marker for a 204. No Room version is needed, so none is claimed. `ForagerDatabase` stays at 23 [read, `ForagerDatabase.kt:214`].

- **Against "Room for data that relates; DataStore for flat settings".**
  - The copy is asked only two things: "this tile, any area" and "what does area N hold".
  - A folder answers both. Nothing joins, filters or references it.
  - It is bulk binary data, not a setting, so DataStore does not fit either.
- **The precedent is the route store.** [read] `RegionRouteStore.kt:13-22` records the same choice for route files. Its reasons all carry over:
  - no second record that could disagree with the disk;
  - the journal backup copies `offline_regions` rows without files (`JournalTables.kt:45`);
  - no migration number to claim.
- **Backup.** [read] Under `files/`, every backup and device-transfer domain is excluded whole (`res/xml/data_extraction_rules.xml`; `RegionRouteFolders.kt:86-88`).
- **`files/`, not the cache.** [inferred] Android may clear the cache by itself. Offline in the field the copy could not be fetched back. `MapLibreStorage.kt:7-10` records the same reason for MapLibre's store.
- **The folder's life mirrors the route store's** [read, `RegionRouteStore.kt:24-28`, `:34-35`, `:122-137`]:
  - each tile is written to a temporary name and renamed into place, so a reader sees it whole or absent;
  - an in-process "being fetched" set keeps one writer per area;
  - a delete renames the folder aside first;
  - orphans are cleaned against the kept ids.
- **A "whole" record is the one record the folder keeps.** When a pass ends with nothing wanted, it writes a small `whole` record. Later openings then make no request and no MapLibre read for that area. The folder never holds the whole cover, because tiles MapLibre holds marked are skipped, so without the record each opening would re-read those MapLibre tiles.
- **Per area, not one shared folder.** Deleting an area is one folder, as with routes. The cost is duplicates: 4 of the S22's 600 distinct wanted tiles are wanted by both areas [observed]. A shared folder would remove the duplicates, but every delete would need "is this tile in another area's cover?". That is not worth it at this scale.

**Request rate, with a proposed operating limit.**
- [read] MapLibre's own client allows 20 requests per host (`MapHttpClient.kt:22-23`, `:30`). That is a capacity, not a safe limit.
- [read] **The server has no limit on tile requests.** Its two rate limits are declared for route data only (`server/pmtiles-worker/wrangler.toml:38-66`) and checked only in the routing handler (`src/routing/handler.ts:246-253`). Every tile path is answered without them (`src/index.ts:495-502` sends only `/routing/` there).
- [read] So **known bug 17** (30 route requests a minute per shared address, `docs/process/known-bugs.md:41`) does not apply to tiles.
- **Proposed limits** (numbers for the planner to accept; each a stated limit, not a measured one):
  - at most **4 requests in flight**;
  - at most **10 started per second**, so the S22's 604 take at least about 61 s;
  - **one pass per trigger**, never a loop;
  - **stop the pass at the first connection failure**;
  - **stop after 3 server errors in a row** (a 5xx, 429 or unexpected 404);
  - **refuse an area whose cover is over 4,000 z15 tiles**, logged. 3,844 is the largest real one, so anything over 4,000 is a bad row.
  - **read at most 512 KiB of one tile body**. The largest raw tile seen is 62 KB.
- **The tile budget.**
  - Proposed: the copy is **not counted** against `TILE_COUNT_LIMIT` (6000, `OfflineMapRepository.kt:135`). It is a second copy of z15 tiles that budget already counts, and so already bounded by it.
  - The budget is a number the user sees ("832 / 6000" in -2103), so this is listed as S2.
- **The client.**
  - Proposed: the app's JSON client, `ApiClients.httpClient` (`ApiClients.kt:23-37`: the app's User-Agent, 15 s timeouts), as the route folders already use it (`AppContainer.kt:330-336`).

- **The template.** Taken from MapLibre's stored basemap TileJSON (the same one the reader keys on). If that store holds none, nothing is fetched, and that is logged.

## 4. The freshness rule

**What the server gives.**
- [read] The Worker sets only `Cache-Control` on tiles (`src/index.ts`, `cacheableResponse`, around `:567`). It has no ETag and no conditional handling.
- [observed, 3 cache hits] The platform's edge cache adds `last-modified` to a cached answer, equal to `date` minus `age` (09:31:33 − 19,243 s = 04:10:50). The cache miss (the sparse tile) carried none.
- That explains the earlier report's open question about Last-Modified. It dates the edge cache, not the content.
- [observed, 1 request] `If-Modified-Since` with that exact time got a **full 200 with all 30,708 B**, not a 304.
- So no validator carries content identity, and any refresh costs the whole tile.

**Proposed rule: by the mark and completeness, not by age.** It works the way the route fetch decides what it fetches [read, `RegionRouteData.kt:167-171`: stored routes are never fetched again].
- A tile is wanted while it is in the area's cover, MapLibre's copy of it lacks the mark (or holds no data), and the app's copy holds neither a marked tile nor an empty answer for it.
- An area is whole when nothing is wanted. It is then never fetched again.
- **Every outcome is logged:**

| Case | What happens |
|---|---|
| No signal at the opening | Nothing is fetched. One log line per opening says so; today's route fetch returns silently there (`AvailabilityViewModelOfflineMaps.kt:60`). |
| Failed fetch: connection loss mid-pass | The pass stops and logs "K of N stored; stopped: <reason>". |
| Failed fetch: three server errors in a row | The pass stops and logs the same. |
| Partial pass | Every tile already written is kept, each whole. The rest stay wanted for the next opening. The way-to uses the copy wherever it has a marked tile. A reach that still touches a tile no store holds marked goes by trail, logged, as 2026-11-04-04 A4 rules ("any nearby tile"). |
| A 200 without the mark, a body that does not decode, or one over the size limit | Not stored, counted in the pass's log line, stays wanted. |
| A 204 | Recorded as empty, so it is not asked for again. It reads as "not held", which falls through to MapLibre's NULL row, a missing tile as today. |

- **The alternative, by age** (for example, re-fetch any copy older than N days): every refresh is a full re-download of the area's wanted tiles (604 on the S22). It needs a number. Not proposed; listed as S3.
- [inferred] A future data patch that adds a new mark would change the "marked" test in code. Not built: no data shows the case yet (CLAUDE.md, Building).

## 5. The read order

**Proposed: the layered `OfflineBasemap`, per tile.**
1. MapLibre's tile. A read failure is the whole read's failure, as today.
2. If it decodes and carries the mark: MapLibre's. This is today's behaviour, kept wherever it already works.
3. If it does not decode: MapLibre's bytes. `ReadNearbyMapData` then fails on them exactly as today (`NearbyMapData.kt:119-125`; by trail, logged, `WayToEnds.kt:159`).
4. If it is absent, or decodes without the mark: the copy's tile, if it is present, decodes and carries the mark. A copy file that does not decode is logged, removed so it is wanted again, and skipped.
5. Otherwise MapLibre's bytes or null: exactly today's.

`tileJson()` stays MapLibre's. That is today's, and nothing reads the schema.

**Where they disagree:**
- **MapLibre unmarked, copy marked:** the copy is read. This is the case the dispatch exists for.
- **Both marked:** cannot happen, because the pass skips tiles MapLibre holds marked. If it did, MapLibre's would win: it is what online viewing keeps fresh (report §4) and what the way-to reads today.
- **MapLibre marked, copy absent:** MapLibre's, as today.

**This differs from the dispatch's "copy first, then MapLibre's".** Copy-first would read data frozen at copy time, ignoring tiles online viewing has refreshed since. It would also need every tile copied, including new areas' already-marked ones. Listed as P3 for the planner to accept or reject.

**A3's fallback is unchanged where neither holds the mark.**
- [read] Step 5 returns exactly what `MapLibreOfflineBasemap.tile` returns today.
- So `ReadNearbyMapData` produces the same `NotInTileSet` reason (`NearbyMapData.kt:130`). `StreetDropOffEnds.read` sends the end by trail (`WayToEnds.kt:160`), and the use case logs it once per end (`FindWayToWaypointUseCase.kt:94`, `:164-166`).
- A tile neither holds stays missing (`NearbyMapData.kt:115-118`), as today.
- **A reading of A3 to confirm (P4).** Its first clause, "where the app's copy doesn't hold a tile … goes by trail", read literally would send an end by trail where MapLibre's tile is marked. That would be a regression for every area downloaded since the fence data. I read A3 as "where no marked tile is available".

**Double decode** [inferred]: MapLibre's tiles in a reach (4 to 9 per end) are decoded once here and once in the reader. That is a few milliseconds.
