## 1. M-396-1 (the owner, -1617: "Fall back to your track")

**The ruling:** once re-routing has ended for a return (a second stray, or a fallback), the HUD shows the track home and its distance, as sundown does, never "Unable to calculate route". Test first, through the tick. Revert check.

**The fix** (`TrackRecordingRouteTicks.kt:102-114` at the head): the tick now computes the walker's place first (`wayHomeProgress(trackId) ?: placeOnWayHome(line, here, null, previousHopBand)`), and uses `wayHomeAhead` only when that place `is WayHomeProgress.Placed`; otherwise, including `OffLine`, it calls `findRouteHome(track, …)`, the track home, exactly as before Return and as the track-only fallback does. Before the fix `OffLine` went into `wayHomeAhead`, which returns `RouteHome.Withheld(OFF_ROUTE, FAR)` (`WayHomeAhead.kt:27`), the "Unable to calculate route" state.

**Read against each way the walker can be off the line:**
- *Second stray, re-routing spent* (`judgeStray`, `WayHomeWatch.kt:139-158`: `!armed`, or `reroutingEnded`): `onFix` sets `progress = OffLine` (`:128-134`); the tick reads it through `progressFor` and shows the track. Sundown reads the same `OffLine` as `null` from `wayHomeFor` and uses the track (`SundownWatch.kt:296-297`). HUD and sundown now agree, which is what the step path's "the HUD distance and sundown use the route shown, app-wide" wants.
- *Between 45 and 50 m coming back* (L-395-4's hysteresis, `WayHomeWatch.kt:124-127`): stays `OffLine`, so the track; back under 45 m, `Placed`, so the way home again. Consistent with sundown, which has the same band.
- *Try again* (`TrackRecordingViewModel.kt:795-797` → `updateRouteHome`): now recomputes the track home; it can no longer land on "Unable to calculate route" for the way home, so the button has no withheld way-home state left to act on.
- *Arrival, Stop, second Return:* unchanged from the first review (section 2 there); the fix touches only which branch the tick takes.

**The test** (`TrackRecordingWayHomeTest.kt`, "off the way home by more than 50 m the HUD shows the track home, not Unable to calculate route"): real entry point (`startReturn()`, a fix through the tracker, the poll advanced 15 s, then `retryRoute()`), asserts `routeHome is RouteHome.Ahead` with `generation == 0L`, the track's generation (`RouteHome.kt:46`, a way home's is the watch's and never 0). It runs inside `runRecordingTest`, which stops every recording in a `finally` (the stall rule). Two notes, neither a defect: the test's stray is judged by the tick's own `placeOnWayHome` fallback, because no service feeds `WayHomeWatch.onFix` in a ViewModel test; the production path (`onFix` → `progressFor`) reaches the same branch by the same `is Placed` test. And the assertion follows a `retryRoute()` call, so it covers the Try-again path as well as the tick; both are `updateRouteHome`, the tick ran twice in the 15 s advance (`ROUTE_TICK_MILLIS = 5_000L`, `TrackRecordingViewModel.kt:861`), and the fail-first run shows the assertion bites (section 3).

**Hazel's own call: the track also shows while a re-route is being worked out.** See O-396-10 under Findings. The mechanics, from the code: a re-route does not publish a `null` result (only `firstOfReturn` does, `WayHomeWatch.kt:165`), so during the re-route `shown.line` is still the **old** line, and the walker is by definition more than 50 m from it, so `progress` is `OffLine` and the tick now shows the track. Before the fix the same span showed `Withheld(OFF_ROUTE, FAR)`: `nextRouteLine` keeps the old line **faded** (`RouteLine.kt:60`, `aheadIsCurrent = false`) and the HUD reads "Unable to calculate route" with Try again. After the fix: the track's line replaces the old line as the line at Return (`RouteLine.kt:53-54`, generation 0 differs from the old generation), with the track's distance in the HUD, until the new way home publishes and replaces it again (new generation). So the walker sees, through one re-route: old trail line → **the track, solid, with its figure** → new trail line; before, they saw: old trail line, faded, with "Unable to calculate route" → new trail line. This is not covered by any test (the new test ends the re-route before asserting nothing; no test asserts the state with a search in flight). By reading only.

## Findings

No Blocking. No new Medium.

- **O-396-10 (for the owner, not a defect) — The track also shows while a re-route is being worked out.** Hazel's call, disclosed in the PR comment ("decided beyond the item's words; the track shows meanwhile, as at Return"). The ruling (-1617) says "once re-routing has ended"; the code shows the track for the in-flight span too (section 1, last paragraph). **What the walker sees, before and after:** during the seconds a re-route takes (unmeasured; the timing run is pending, and a cold `.rd5` open is in it), the old trail line used to stay drawn but faded with "Unable to calculate route" and a Try again button; it now becomes the track's solid line with the track's distance, then the new trail line. **My read:** the call fits the step path ("it re-routes once, silently": a withheld HUD with a button is not silent) and both CLAUDE.md principles the dispatch names ("Don't make me think"; no state the walker could misread as broken, which "Unable to calculate route" during a working re-route is), and it is the same sequence the owner already accepted at Return (track at once, swap when ready). It also makes the HUD agree with sundown in that span, which already fell back to the track. Against it: the map line flips twice through a re-route (trail → track → trail), and the greyed walked part resets to the track's and back; whether that reads as a flicker on a phone is device-only. **Not mine to decide**: the owner should rule, with the S22 frame-by-frame recording in front of them (device step 3). Either ruling is a one-line change (`progress is Placed` versus a check on whether a job is in flight) and does not block the merge.
- **L-396-11 — The tick's own placement no longer carries the far band across off-line, where the watch's does.** When `progressFor` is `null` (right after a publish, before the next service fix), the tick places itself with `previousHopBand` from `state.routeHome` (`TrackRecordingRouteTicks.kt:93-97`). Before the fix that was `Withheld(FAR)` → `FAR`, so `placeOnWayHome` kept the hysteresis (`WayHomeProgress.kt:137`); now it is the track route's band (`NONE` or `COUNTED`), so a walker at 47 m re-places at once in that one tick, where the watch would hold `OffLine` until 45 m (L-395-4). Momentary (the next fix restores the watch's placement) and in the safe direction (a placement, with the 50 m figure reach, never short). Record; no change asked.
- **L-396-12 — The in-flight span has no test.** The new HUD test completes the search before it asserts; nothing asserts `routeHome` with a re-route's search pending. If the owner keeps Hazel's call, a one-case test (second stray, answer withheld, assert the track's generation) would pin it; if the owner reverses it, the same test pins the other branch. Either way, after the ruling.
- **L-396-13 — The HUD test says "through the tick" and asserts after `retryRoute()`.** Both are `updateRouteHome`; the tick had run in the 15 s advance; the fail-first run proves the assertion bites. Cosmetic: drop the `retryRoute()` line or name the test for both paths. No action needed before merge.
