## Mechanism prediction, written before computing

A pure move of this shape can fail in four places: a line dropped or duplicated in the copy; a `remember` or effect that changes slot order or key; a State read that moves into a different restart scope and goes stale or stops recomposing; and a same-typed argument swapped in a long call. My prediction: the copy is whole (the coder's own table is detailed), the slot order holds because each moved group is one unconditional call at the old line, and the frame call is unswapped because every argument is passed by the parameter's own name. Two things I expected to find that are not in the PR body: `rememberDrawerState` is itself a `rememberSaveable`, so more saveable keys move than the four the body counts; and bound property references as delegates (`by holder::x`) are fresh objects each composition, so lambdas that capture them stop being memoisable, which can only cost recomposition, not behaviour. Scored at the end.

## 5. Recomposition scopes and stale captures (inferred, from reads of the code)

The question is whether any State read moved into a restart scope where a change would no longer reach its reader, or where a captured value could go stale.

- **Body reads stay in the body.** `selectedTab`, `compactTab`, `mapTaxonFilter`, `isDrawerOpen`, `toolsReturn`, `chosenMapMode` and the rest are read in the body through delegates onto the same State objects, so the body's scope subscribes as before (e.g. `isMapsTabShown = compactTab == CompactTab.MAP`, `AvailabilityScreen.kt:514`; `mapMode = chosenMapMode ?: ...`, `:291`).

Only `rememberScreenMapLocals` reads anything at composition time (`uiState.liveFix` etc., plain fields of a data-class parameter, and `rememberShownPosition`'s `produceState`, `MapPosition.kt:51-56`), the same reads the body made at `old:945-953`.
- **The three effect composables hold no composition-time State read.** `ToolsDrawerFollowsFlag` reads `isDrawerOpen` as a `Boolean` parameter computed in the body (`AvailabilityScreen.kt:367`); `ToolsDrawerFollowsSettledClose` and `ToolsOfflineMapsReturnWatch` declare delegates and read them only inside the coroutine or the `snapshotFlow` block (`ScreenToolsDrawer.kt:153-154`, `ScreenToolsOfflineMapsReturn.kt:70-77`). Those coroutines capture the holder instance of the composition that launched them; the holder is rebuilt each composition, but every instance wraps the same remembered `MutableState` objects, so a read through an old instance is a live read. This is exactly the case Stage G's wrap-never-copy rule exists for, and it holds here.
- **The frame's reads moved from the lambda's scope to `AvailabilityScreenFrameCall`'s scope.** The old lambda read `showDecimalDegrees`, `navigationFollowBroken`, `navigationViewRequestId`, `navigationZoomPending`, `mapWaypointReopen`, `recordsWaypointReopen` at composition time (`old:839-851`); the frame call reads the same States at `AvailabilityScreenFrameCall.kt:203-217` through delegates onto the same objects. A change to any of them now invalidates the frame call's scope instead of the lambda's; either way the next thing composed is `CompactMainScaffold` with the new value. The frame call's holder parameters are unstable classes, so it is never skipped when the lambda recomposes, and the lambda is re-created on every body recomposition as it was before (it captures body locals). Nothing the frame reads can be stale: the values the body computes per composition (`mapRenderMode`, `mapWaypoints`, `target`, `basemap`, `mapMode`, ...) are passed as parameters captured by the lambda at that composition, which is what the lambda did before; the States are read live.
- **`ToolsDrawerFollowsFlag` reads the flag as a parameter, not as State inside the effect.** `old:490-491` keyed on `isDrawerOpen` and then read `isDrawerOpen` again inside the coroutine; the new effect keys on the parameter and tests the parameter (`ScreenToolsDrawer.kt:114-115`). At launch the two are equal (the effect launches in the apply phase of the composition that read the key, and it is the first effect in the body, so no earlier effect can have written the flag); on any later change the key changes and the effect relaunches with the new value. Same behaviour; a different mechanism, recorded as N-417-3.
