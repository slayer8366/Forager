## Amendment 3: downloads pause instead of failing, and get their own lane

**Pause (option D), read.** `MapLibreOfflineMapRepository.kt:373-441`. `onError` (`:415-431`) maps `REASON_CONNECTION` and `REASON_SERVER` to `Pausable` (`downloadErrorKind`, `:449-452`; constants confirmed against `OfflineRegionError` bytecode) and everything else to `Final`. The first pausable error starts a pause with `giveUpAtMs = now + 5 min` and posts the `giveUp` runnable on a main-looper `Handler` (`:422`); later pausable errors are `StillPaused` and do not restart the clock (`DownloadPause.kt:35`); progress (`completed` strictly greater than at pause start) ends it and removes the runnable (`:404-408`). The give-up runnable calls `fail()` which resumes the continuation with the fixed-text `IOException` as before (`:383-394`), so the caller's `deleteSuspend()` and the ViewModel's "Couldn't download offline maps." are unchanged (`:166-169`; `AvailabilityOfflineMaps.kt:237-241`). `Final` errors fail at once (`:426-429`). Pure rules in `DownloadPause` are tested at `DownloadPauseTest.kt` (5 tests), red at b56239b55.

Threading: MapLibre's `OfflineRegion` constructs its `Handler` on `Looper.getMainLooper()` and posts both `onStatusChanged` and `onError` through it (bytecode: `<init>` offsets 9-12; `setObserver$1` posts via `Handler.post`), so `pause`, `completed` and `lastPauseError` are touched on one thread, as the comment at `:377-379` claims. `Handler.removeCallbacks` from `invokeOnCancellation` (`:399`) is safe off-thread. The timer uses `uptimeMillis` (Handler) against a clock on `elapsedRealtime` (`DownloadPause`): elapsed never advances less than uptime, so the runnable cannot fire with `giveUpDue` false; after deep sleep it fires late, not early. No hang path found.

**Own lane (option A), read and partly verified against bytecode.** `MapRequestUsage.kt`: `UsageMarkingModuleProvider` wraps MapLibre's `ModuleProvider` (`:36-39`), `UsageMarkingHttpRequest` sets a `ThreadLocal` around the delegate's `executeRequest` (`:42-61`), `UsageTaggingCallFactory.newCall` reads it and adds a typed tag (`:67-72`). The finally releases the gate only if a hold was taken (`:95-97`). ## Findings

No Blocking. No M.

**L-a. `onStatusChanged` has no `isActive` guard; harmless today by Handler ordering only.** `MapLibreOfflineMapRepository.kt:401-412`: `onProgress(...)` and `onPauseChanged(false)` run even after `fail()` has resumed the continuation, while `onError` returns early at `:416`. Failure path: give-up fires at 5:00, `fail()` resumes with the exception; signal returns at 5:01 and the engine's next status post calls `showProgress`, which writes `Downloading(628, 1608)` (`AvailabilityOfflineMaps.kt:254`) over whatever is there. Today that is benign: the ViewModel writes `Failed` only after `download()` returns, which is after `deleteSuspend()` completes, and the status posts and the delete callback share one main Handler in posting order (bytecode: `deliverMessages()` reads only `state` and `isDeliveringInactiveMessages`, not `isDeleted`; `delete()` sets `isDeleted` and calls native) — so `Failed` lands last. **Inferred**: that nothing is posted after the native delete's callback. The order is nowhere stated, and the pre-PR code had the same shape, which is why this is Low. Fix is one line: `if (!continuation.isActive) return` at the top of `onStatusChanged`, or `showProgress` writing only when the status is already `Downloading`.

**L-b. The pause line says "no signal" for a server error with signal up.** `downloadErrorKind` (`:449-452`) makes `REASON_SERVER` pausable; `onPauseChanged(true)` fires on the first such error (`:423`); the row then reads "Paused · no signal · continues by itself" (`OfflineMapsSideBySide.kt:164`). Failure path: on Wi-Fi, the Worker returns one 503; the row says "no signal" until the next resource completes. On a fast download that is milliseconds; on a slow one, seconds of a wrong reason. The owner chose the text for the no-signal case; whether a 5xx should show it, or show nothing, is the owner's call, not Hazel's — recorded here, not graded higher.

**L-c. PR description is stale.** It describes Amendment 1 only: "Offline-area downloads are held the same way (the owner: 'pause and continue')", 10 interceptor tests, 5425 suite. At head, downloads are never held (`TileRetryInterceptor.kt:29-33`), there are 13 interceptor tests, and six more test classes exist. Failure path: a later reader (the promotion's UX auditor, or a bisect) takes the body as the design and looks for a hold that is not there. Update before merge or in the merge commit.

**L-d. `a pause that runs out ends in the usual error` passes identically before and after the production change.** `DownloadPausedShownTest.kt:124-134` asserts "Couldn't download offline maps." displayed and the pause line absent. It was green at f2c612b0c (run 40063844620 lists only the other two as failing), before the production commit c3d06b2f1 — CLAUDE.md's "a check that passes identically before and after a code change is suspect". It cannot fail on the Amendment 4 code at all: `Failed` replaces `Downloading` (`AvailabilityOfflineMaps.kt:240`), so the paused flag has nowhere to survive. Keep it as a regression guard if wanted, but it should be named as one (a comment), not counted as coverage of the give-up.

**L-e. The L1 fix has no test, and one is cheap.** `TileRetryInterceptor.kt:115-119`. A `FakeNetwork.awaitValidated` that throws `InterruptedException`, asserting `InterruptedIOException` from `execute()` and `Thread.interrupted()` true afterwards, is about ten lines in the existing test class (the same shape would cover `waitFor` at `:130-134`, also untested). Failure path: a later refactor of `waitForNetwork` drops the catch; OkHttp's thread is interrupted on dispatcher shutdown; the interceptor throws a bare `InterruptedException` through an `IOException`-typed chain. Rare, and the harm is a logged crash in a dying process, hence Low.

**L-f. The L4 body-closed test was never seen red, as far as I can tell.** `discard()` existed before the test (`git diff 5032e1734 origin/tile-retry` on the interceptor shows no change to it), and the test is not among b56239b55's failures. It would fail without `discard()`, read from the code, but the project's standard is a revert check with a build log read first. **Unverified** whether Hazel ran one; the Amendment 3 report may say.

## Hazel's three untested items, weighed

1. **Download observer's pause wiring has no JVM test.** `OfflineRegion` is `public final class` (javap), and `downloadToCompletionSuspend` is a private extension on it, so a JVM test needs Robolectric plus MapLibre's native library, which this project does not load in tests. The rule itself is tested (`DownloadPauseTest`), the UI is tested through the real screen, and the wiring between them was run on the S22 (Amendment 3 report accepted by the planner: Wi-Fi off 1–2 min mid-download, finished untapped). Acceptable as-is; the one line L-a asks for sits in exactly this untested wiring, which is the argument for adding it now.
2. **The 5-minute give-up was not run on a phone.** Code path read: Handler-posted runnable → `giveUpDue` → `fail()` → existing delete and "Couldn't download" path. No hang path; the one ordering subtlety is L-a and is benign. Acceptable for merge; a device step with a debug-shortened limit would close it after the promotion.
3. **L1 has no test.** L-e. Acceptable for merge.
