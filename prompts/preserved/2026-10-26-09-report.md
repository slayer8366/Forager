# Report on dispatch 2026-10-26-09: why MushroomLogViewModelWiringTest failed on pre-main after #409

Hazel Cairnwright (coder, Opus), 2026-10-26, about 07:30 UTC. Diagnosis only: nothing was fixed, and the test was not changed, silenced or re-run to get a pass. The dispatch is at `prompts/preserved/2026-10-26-09.md` on `records-after-173` (e230117b6). This branch, `wiring-test-report`, is cut from that commit.

## Answer

**#409 did not cause it.** The test has a timing race of its own, and it is older than #409. The find-delete test fails on 1 to 3 runs in 200, and the photo-delete test beside it has the same race. The failing run on 2a14533a3 was that race firing, and it would have fired just as often on c3e132a54 without #409.

**The mechanism**, read from the code and confirmed by a probe:

1. The test waits for the database row to be gone, at `MushroomLogViewModelWiringTest.kt:77`. It then drains the main looper once (`:78`) and asserts once (`:80`).
2. The app removes the find from the Maps tab's snapshot only after `deleteEntry(entry.id)` returns in the Journal ViewModel's coroutine:
   - the delete call is at `MushroomLogPendingDeletes.kt:145`;
   - the coroutine starts at `:143`, inside the editing lock at `:144`;
   - `onFindDeleted(entry.id)` is at `:148`;
   - that call reaches `AvailabilityMapDisplay.onFindDeleted`, which edits the snapshot.
3. The rest of that coroutine (the code after `deleteEntry` returns) is posted to the main looper only after Room's write transaction has committed (`MushroomLogDao.kt:93`, `deleteEntryAndCrossRefs`, `@Transaction`).
4. So there is a short gap. The test thread can already see the row gone, but the code that calls `onFindDeleted` has not been posted yet. If the test's one `idle()` runs in that gap, the queue is empty, and the assertion sees the find still in the snapshot.
5. The photo test has the same shape. Its wait is at `:95`, the idle at `:96` and the assertion at `:98`. On the app side, `onPhotoDeleted` is at `MushroomLogPendingDeletes.kt:264`, after `deleteGalleryPhoto` at `:259`.

The production wiring is fine. On every failure, the hook ran 0 to 1 ms after the assertion (evidence below).

**Answering the dispatch's step 1 candidates against #409's diff** (c3e132a54..2a14533a3):
- **An extra state emission:** #409 adds one collector in `init`, on the waypoint id (`AvailabilityViewModel.kt`, the `collectLatest` added after `loadWaypointNavigation()`). With no navigation, the id is null. `AvailabilityWaypointLine.follow(null, …)` makes one atomic `_uiState.update` that sets `waypointStraightLine = null`, and returns. Every write goes through `MutableStateFlow.update`, so it cannot overwrite `mapRecords`.
- **A reload racing the delete:** there is no such reload in this test. The only callers of `loadMapRecords` are `onMapShown` (`AvailabilityMapDisplay.kt:53`), the `trackEnds` collector (`AvailabilityViewModel.kt:387`, fed by the default `MutableStateFlow(null)` that the fixture does not override) and `reloadAfterRestore`. The test calls none of them after the delete. The probe agrees: no failure was a reload over the delete.
- **The fixture's defaults:** #409 adds `readWaypoint` (stores nothing) and `currentTime` (system clock) to `mapLayersViewModel`. Neither one runs in this test, because no waypoint is navigated to.

## Reproduction on CI

Both runs were filtered "Run this branch" runs (workflow_dispatch). The filter was `WiringReproVerbatimTest; WiringReproProbeTest; MushroomLogViewModelWiringTest`. Each branch adds one scratch file, `app/src/test/java/com/zynergylabs/forager/app/WiringTestReproProbe.kt`, and **does not touch the test**. That file holds two classes:

- **`WiringReproVerbatimTest`** calls the test's two delete methods unchanged, 300 times each, through a parameterised Robolectric runner.
- **`WiringReproProbeTest`** is a copy of the find-delete body, run 300 times. At the point where the original asserts, it records two things:
  - whether the main looper had queued work before and after the `idle()`;
  - if the find is still in the snapshot, whether it leaves later. "LATE" means it leaves by itself; "STUCK" means it never leaves in 10 s, which would point to a reload over the delete.

**What these counts licence:**
- **Both runs are valid.** Each total of 905 equals 600 + 300 + 5, the classes and repeat counts asked for. Neither build log has a compile error (no `e: ` lines), and both test tasks built and ran fresh on a clean CI machine, so neither result is stale.
- **The failure is a race.** It is not deterministic: 299 of 300 repeats pass.
- **#409 is not the cause.** Pooled across all three counters, the rate is 4 / 903 with #409 and 12 / 903 without it. If #409 were the cause, the build without it would not fail 12 times.
- **The difference between the two builds is not a #409 effect.** It is within what two runs on different CI machines vary by, so I read nothing into it in either direction.
- **The probe rules out the STUCK path** in all 6 of its failures.
- **Why 300 repeats was enough:** at the rate the history implies (below, roughly 1 to 2% of full runs), 300 repeats was expected to show several failures if the race was real. It showed 1 to 5 per counter on both bases. A deterministic failure would have shown 300 out of 300.

**What the probe recorded.** In all 6 probe failures, `queuedBeforeIdle=false`: the main looper was empty when the test reached its one `idle()`. The posted work landed during or after that idle (`queuedAtAssert=true` in 4 of the 6), and the find was gone within 1 ms. The original failure on 40280855484 carries the same mark: a suppressed `UnExecutedRunnablesException: Main looper has queued unexecuted runnables` in its JUnit XML.

**History.** I scanned the logs of every failed CI run among the last 1000 (387 failed runs, 2026-10-18 to 2026-10-26).

## Fix options, priced (none built)

1. **Test only: wait on the snapshot itself.** Wait for the snapshot to lose the record before asserting, instead of draining the looper once after the database read. At `:77-80`, keep the database wait, replace the single `idle()` with an `awaitUntil` on `findMarkers` being empty, then make the same assertion. Do the same at `:95-98`.
   - **Size:** about 4 lines over the two tests.
   - **Checks needed:** two revert checks, one per hook line in `MushroomLogViewModelFactory.kt`, so 2 filtered CI runs plus one repeat run (as above) to show the rate drops to 0.
   - **Cost:** with a hook removed, the test now takes the 10 s timeout before it fails. The message still names the hook, provided the final `assertEquals` is kept after the wait.
   - **Recommended.** It removes the race at its source and tests the same claim.
2. **Test only: drain the looper again after the read.** Loop `idle()` with a short sleep a few times before asserting.
   - **Size:** about the same.
   - **Cost:** it still guesses at a window, so it is weaker than option 1 for the same price.
3. **Production change: run the hook in the same step as the database delete,** for example by calling `onFindDeleted` from inside the IO context.
   - **Not recommended.** It changes threading in working code to suit a test, and the app does not need it: in the app, the screen's committed-id filter hides the find during that gap.

Options 1 and 2 change the test, so either needs the planner's and owner's go. That change is a stop on this dispatch.
