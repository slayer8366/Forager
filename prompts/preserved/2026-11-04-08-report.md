## Mechanism prediction (coder), first

1. **The notice and the tiles are unrelated.** "Older map style. Download again to update." is decided only by the style URL in the region's definition. The fence mark is in the tile bytes. A trail-v4 region full of pre-fence tiles shows no notice.
2. **There is no "Download again" for a downloaded region.** The only route a user has is a new download over the same area, optionally after deleting the old region.
3. **A MapLibre offline download never revalidates.** For every tile it asks only "is there a stored row with non-NULL data under this URL template and z/x/y?" If there is, it counts the tile as done and links it to the new region. It ignores expiry, must-revalidate, ETag and Last-Modified. It fetches only tiles that are missing, or stored with no data (a 204 or a 404).
4. **Deleting a region deletes no tile while the leftover cache is under 50 MiB.** Tiles held by another region stay linked to it. The rest become ambient cache. They are evicted only while that cache is over its 50 MiB default, which the app never changes, so a re-download finds them and reuses them.
5. **The online map is the only path that refreshes a stored tile.** When it draws a tile whose copy has expired (24 h after the last response, from `max-age=86400`), it sends a conditional request and rewrites the same row in place on a 200. That row is shared by every region holding it and is the one `ReadNearbyMapData` reads.

So: today, for areas downloaded before the fence data, **no app action refreshes a whole area**. Viewing online refreshes only the zoom-15 tiles actually drawn at map zoom 15 or above, one at a time. Clearing the app's storage would also work, at the cost of all app data. Session 13's evidence agrees with each step.

## 2. What MapLibre 13.5.0 does when a download meets a tile it already stores

[read, android-v13.5.0 source]

**It reuses the tile and never revalidates it.**
- `platform/default/src/mbgl/storage/offline_download.cpp:477-514` (`OfflineDownload::ensureResource`).
  - For a tile (no callback) it calls `offlineDatabase.hasRegionResource(resource)` (`:487-488`).
  - If that returns a size, it counts the tile complete, queues it to be linked to this region (`:497`) and continues without any request (`:501-513`).
  - Only when there is no size does it call `onlineFileSource.request` (`:521-556`).
- `offline_database.cpp:1018-1023`: `hasRegionResource` is `hasInternal`, which is `hasTile` for tiles (`:279-286`).
  - `hasTile` (`:591-614`) is only `SELECT length(data) FROM tiles WHERE url_template=? AND pixel_ratio=? AND x=? AND y=? AND z=?`.
  - It reads no `expires`, `must_revalidate`, `etag` or `modified`, and does not update `accessed`.
- The style and source TileJSON go through `getRegionResource` (`:1011-1016` → `getResource`). That is also a plain lookup, reused if present (`offline_download.cpp:252`, `:279`, `:489-494`).
- Linking: `markUsed` (`offline_database.cpp:1108-1158`) runs `INSERT OR IGNORE INTO region_tiles … SELECT ?1, tiles.id FROM tiles WHERE url_template… z…`, so the new region links to the existing row.
- One consequence: `length(NULL)` is SQL NULL, and `Query::get<std::optional<int64_t>>` returns `nullopt` for it (`sqlite3.cpp:415-422`). So a row stored with no data (a 204, or a 404 for a tile, `android http_file_source.cpp:172-173`) counts as absent and **is** fetched again.

**What `cache-control: public, max-age=86400` means here**
- [read] The server's header gives each stored copy `expires = now + 86400 s` at each response (`android http_file_source.cpp:154-157`; `http_header.cpp:40-42`). It carries no `must-revalidate`, so `must_revalidate = 0`.
- [read] **The offline download never reads it** (above).
- [read] It matters only to the map on screen:
  - `Response::isUsable()` is `!mustRevalidate || expires > now` (`include/mbgl/storage/response.hpp:44`). An expired copy stays usable with no signal.
  - With signal, it is revalidated when drawn (question 4).
- [read] The Worker sets only `Cache-Control` on tiles (`server/pmtiles-worker/src/index.ts:562-580`, `:567`). It sets no ETag or Last-Modified and never answers a conditional request itself: its edge lookup is `cache.match(cacheKey)` on a string key (`:549-560`).

## 3. What deleting a region does to tiles another region still holds

- [read] `OfflineDatabase::deleteRegion` (`offline_database.cpp:988-1009`) runs `DELETE FROM regions WHERE id = ?` and then `evict(0, stats)`.
  - The schema cascades: `region_tiles.region_id … REFERENCES regions(id) ON DELETE CASCADE` [observed, `.schema` of end-s13]. `PRAGMA foreign_keys = ON` is set at open (`offline_database.cpp:58`).
  - So only the deleted region's link rows go. **A tile another region holds keeps that link and its row untouched.**
- [read] A tile no remaining region holds becomes ambient cache.
  - `evict` (`:1260-1334`) deletes ambient rows in least-recently-accessed batches, only `while (newAmbientCacheSize > maximumAmbientCacheSize)`.
  - The maximum is `util::DEFAULT_MAX_CACHE_SIZE = 50 * 1024 * 1024` (`include/mbgl/util/constants.hpp:53`; `offline_database.hpp:152`). The app never sets another value (question 1).
  - So below 50 MiB, **a delete removes no tile at all**, and a later download reuses every one of them (question 2).
- [observed] S22 sizes in end-s13:
  - The ambient cache by MapLibre's own formula (`initAmbientCacheSize`, `:1336-1388`, re-run as SQL) is **14,434,726 B**.
  - All tile and resource data is **23,813,489 B**; the limit is 52,428,800 B.
  - So deleting either region or both would evict nothing [inferred from these figures and the code].
- [observed] Overlap: Region 1 (MapLibre 3) holds 34 tiles (17 `us` + 17 `reference-trails`), Region 2 (MapLibre 8) holds 1,630 (815 + 815), and **28 are shared**.

## 6. Options for the owner (none chosen, nothing built)

These are priced by what each asks the user to notice, decide or do, then by what changes in code. All touch `MapLibreOfflineMapRepository` and the offline-maps UI unless stated.

- **A. Leave it.**
  - User: nothing to do. Old areas always go by trail, with A1's fallback logged, and the drop-off never appears there.
  - User: the existing notice still says "Download again to update". Doing that produces a trail-v4 region with no notice over the same old tiles. Once the old row is deleted, nothing on screen says the data is still old. That is a state the user can misread as "updated", which CLAUDE.md names as the worst case.
  - Code: none.
- **B. Make re-downloading an area actually fetch it: delete the old region, then `OfflineManager.clearAmbientCache()`, then download.**
  - User: one action, if it becomes a single "Update" step, or the same two steps as now.
  - Limits [read]: `clearAmbientCache` (`offline_database.cpp:754-785`) deletes every tile no remaining region holds, all of the map cache, not just this area's. A tile still held by another kept region is not cleared, so redoing Region 1 alone leaves its 28 tiles shared with Region 2 old.
  - Limits: between the delete and a finished download the area has no offline map. A download that fails with no signal leaves the user with less than before. This is a new failure the user would have to notice.
  - Code: one new repository function and one new ViewModel path.
- **C. Not recommended: `OfflineRegion.invalidate()`, then download again.** I name it because it is the API whose name suggests it.
  - [read] It sets `expires = 0, must_revalidate = 1` on the region's tiles (`offline_database.cpp:787-823`). The download still reuses them (`hasTile` ignores both).
  - [read] It also makes them **unusable with no signal** until each is refreshed online: `isUsable` is false (`response.hpp:44`), so `database_file_source.cpp:34-36` returns "Cached resource is unusable", and `tile_loader_impl.hpp:120-130` does not draw cached data in that case.
  - [inferred] The offline map would go blank in exactly the place it is needed.
- **D. Give fresh tile data its own URL** (server and app): for example a new tile path or TileJSON for the patched data, under a new style URL. This extends the style rule at `TrailStyle.kt:21-23` ("a URL that never changes meaning") to tiles.
  - User: an old area keeps drawing. Downloading it again fetches everything fresh, because no row matches the new template. The style notice and the data would then agree.
  - Costs: two copies until the old area is deleted. A Worker change. `MapLibreOfflineBasemap` picks one template only (`StoredTiles.kt:59-68`, `MapLibreOfflineBasemap.kt:44-50`), so a phone holding both would need a rule for which to read. Every future data patch would need a new URL.
- **E. App-owned map data for the drop-off.** Fetch the area's zoom-15 basemap tiles into the app's own store beside its route data, and have `ReadNearbyMapData` read that instead of MapLibre's store.
  - User: nothing. It can ride the existing automatic route fetch on opening Offline maps with signal (`AvailabilityViewModelOfflineMaps.kt:58-65`) and on "Try again", so old areas gain the mark with no action.
  - Costs: extra storage (Region 2 has 600 z15 tiles) and a second copy of tiles MapLibre already holds. A new fetch step and freshness rule the app owns. A new `OfflineBasemap` implementation behind the existing interface (`NearbyMapData.kt:15-21`).
- **F. A data-based notice or button,** in place of or beside the style notice.
  - The app can already tell from the store whether an area's z15 tiles carry the mark (the reader's own test, `NearbyMapData.kt:127-131`).
  - On its own this only tells the user. It still needs B, D or E behind it to do anything.

I make no recommendation. Which of these, and whether the existing notice's wording stays, is the owner's call.

## Premises that were wrong

- **"Download again" deletes the region and downloads it** (outcome prediction). There is no such control for a downloaded region (`OfflineRegionsList.kt:249`, `AvailabilityViewModelOfflineMaps.kt:41`). The user's only route is a new download, with an optional manual delete.
- **"Tiles still held by another stored region stay old"** is true but incomplete. Tiles held by no region also stay, as ambient cache under 50 MiB, and are reused. So even deleting every area and downloading again would not refresh the S22.
- **"Kept all 17 basemap tiles at their old modified dates"** is true, but `modified` is a carried-over server header, not a write time, and not evidence of content age (row 14 has an old `modified` and the mark). What shows the reuse is the HTTP log and the unchanged `expires` and bytes.
- **Records -2103's "Both now show 'Older map style…'"** reads as a consequence of the test. By the code and the regions table it is unrelated: both regions are street-v3 and showed the notice before.
- **"Records-after-173 cc2691b68"** (baseline): the branch is at b1d0ba717. I read the dispatch there.
