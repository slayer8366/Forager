## 2. Races, replay, stale values

**What the reload does.** `AvailabilityMapDisplay.loadMapRecords` (`AvailabilityMapDisplay.kt:103-108`) reads `getMapRecords()` and does one `updateState { it.copy(mapRecords = records) }`. It writes no other field: no camera request, no sheet, no drawer, no layer choice, no cluster placement. So it cannot close anything the user opened or reset user-set UI state (CLAUDE.md UX defaults). On the draw side, `MapDataRefresh.kt:58-67` keys the overlay effect on `keptTrackPolylines` and calls `refreshOverlayData`; the camera code after it moves only for a new `searchFrameRequestId` (`:81-99`, once per id) or a changed region target. The same effect already re-runs on every breadcrumb update, roughly every 15 s while recording (its own comment, `:72-74`), so one more re-run at Stop cannot move the camera where those do not. Read, not run.

**Replay on ViewModel creation.** `AvailabilityViewModel` is per-Activity (`MainActivity.kt:111`, `by viewModels`); `TrackEnds` lives in `AppContainer` (`AppContainer.kt:189`) and outlives it. When the Activity is recreated in the same process after a recording has ended, `latest` still holds that id, the StateFlow replays it, and the collector runs `loadMapRecords()` once from `init`, before any `onMapShown`. That is one extra full records read at startup in that case, concurrent with the one `onMapShown` launches (`AvailabilityMapDisplay.kt:52`). Both read the stored state, so neither delivers a value the store does not hold; `TrackEnds.kt:22-25` documents this exact case as harmless, and `TrackRecordingViewModel.kt:366` has lived with it since #364. See L1 for the ordering caveat.

**Same id twice.** A StateFlow does not re-emit an equal value, so a second report of the same id would not reload again; no production path ends one track twice, and the id is used only as a non-null trigger. No wrong state can come from a replayed id: the reload reads what is stored, and `GetMapRecordsUseCase.kt:103-104` keeps only ended tracks with at least one point, so an open row or a halted empty track is never drawn.

**Can it race `onMapShown`?** Two `loadMapRecords` calls can run at once (a Stop followed at once by a tab flip, or the replay case above). Each is read-then-write with no ordering between them, so the last to finish wins. Both read after the end is stored (the report comes after the write), so for the track itself both agree. The only divergence is a find, photo or region saved in the milliseconds between the two reads, where an older read could finish second and hide the newer record until the next tab change. That shape exists today between two quick `onMapShown` calls and the restore reload; this PR adds one more source of it. Deleted records are not affected: committed deletes are filtered at draw time from `committedFindDeleteIds` and its siblings (`DrawnMapRecords.kt:17-29`), independent of the snapshot, so a reload cannot re-draw a deleted find or photo. Inferred from the code; not reproduced.

## 3. What else the reload re-reads, and its cost

So at a Stop the Maps tab also picks up any find, photo or region saved since the tab was last shown. The snapshot's one reader is `AvailabilityScreen.kt:441` (`uiState.drawnMapRecords(logUiState)`), which feeds the Maps tab's map, its Layers sheet counts and the journal highlights derived from it (`AvailabilityViewModel.kt:738`). The cost is the cost of one tab change, once per Stop; it was not measured on a large record set (L2).
