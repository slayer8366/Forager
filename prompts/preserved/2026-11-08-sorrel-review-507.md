## 1. Defects back to Hazel before the owner sees a build

**1.1 The route card's side bar edge draws a second line beside the side bar's (landscape, navigating).**
- The ruling it reverses: RECORD -967 (owner, 2026-10-14): "Where two outlined pieces touch, one shared 1 dp line is drawn: ... strip or card against the rail." The navigation card follows it today: its rail side carries no line while the rail shows (CompactMapLandscapeNavigationCard.kt:131-137, `landscapeColumnOutlineSides`). The route card resting on that navigation card now draws the map-chrome line on all four sides including the rail side (RouteCardFace.kt:133-143), so at the rail there are two faint lines side by side, and the two stacked cards disagree at the same edge (the navigation card has one line there, the route card two).
- Where it came from: Amendment 5's "Plain line all the way round, like a bubble" was recorded as reaching "the side flush to the screen edge" (-2187, 2026-11-08T02:51:52Z); nothing in the record names the rail side. A bubble touches nothing; this card touches the side bar.
- Hazel saw it and left it: completion report, Amendment 5, "Could not determine": "two 1 dp lines may sit side by side there. Not measured; for the S22 check." It was never measured, and the S26 round (build 4972) found the other two edges' problems, not this one.
- The test that pins it the wrong way: RouteCardOutlineOnNavigationCardTest.kt:42-47 asserts the ruled line on the "side against the side bar", so a fix must change that test's claim to the ruling (-967) and the change must be named in the report.
- What to change: in landscape navigation the route card's rail side draws no line of its own (the side bar's line is the shared one), by the same decision the navigation card uses; everywhere else all four sides stay as Amendment 5 says. What test would show it: a pixel read on the rail side in landscape navigation, day and night, both rotations, expecting the card's bare fill one pixel in (the `whyNotBare` reader already exists in RouteCardOutlineReading.kt:41), red on today's code; plus the existing RouteCardOutlineOnNavigationCardTest re-claimed. Where the navigation card's rule leaves the rail side lined (fullscreen, the rail slid away), the route card should match it.
- If the owner instead wants the line on the rail side: no code change, but -967 gains a recorded exception for the route card, and the navigation card then disagrees with it at that edge (the owner should know that before choosing).

No other defect found. Items below are the owner's calls and notes.

## 2. The owner's calls

**2.1 Navigate and Directions hide for every navigation, not only the card's.** The owner's words were about navigating from the card ("navigate and directions are still visible on the route card while navigating"). As built the buttons and the reason line hide whenever the screen is navigating at all (RouteCardStops.kt:75 reads a flag set from the screen's navigation state at CompactMapRoutePlotting.kt), so a return-to-vehicle navigation, or a navigation started from a waypoint's bubble, hides them on an open route card too. Hazel flagged it (report, Amendment 5, "Decided beyond scope"). Probably what the owner wants, but it is a wider rule than the words; worth a yes.

**2.2 A 24 dp band of clear map beside the tucked strip brings the card back instead of reaching the map.** The strip shows 24 dp; its touch target is 48 dp from the edge at the card's full height (RouteCardTuck.kt:31, :87). So a tap or long-press on the map in the 24 dp just beside the strip, anywhere along the card's height, un-tucks the card. The plan said "48x56 dp touch" for a small tab; the full-height strip makes that band as tall as the card. Hazel's own call (report, Amendment 6 A2, "Decided beyond scope"); the long-press test deliberately samples 12 dp past the 48 dp (RouteCardTuckCloseTest.kt:211), so the band is not tested as map. Material's minimum target argues for it; CLAUDE.md's "a surface over a map intercepts across its bounds" argues against. The owner's call; either answer is one constant.

**2.3 Landscape navigating, the credit "i" stays hidden while the card is tucked.** The owner said "Come back" for the "i" where the card rested; in landscape navigation the "i" is under the navigation card, not the route card, so it stays hidden (report, Amendment 6 "the credit", "Questions for the owner"). Built as the older rule (D28) has it. Hazel asked; not yet answered in the record.

**2.4 At "Arrived", the buttons stay hidden until Back or the X ends navigation.** Already answered "Stay hidden" (-2187, 2026-11-08T05:05:18Z); listed only so the S22 steps match it.

**2.5 One file over the 800 line split rule by one line.** SightingsMap.kt 800 -> 801 (one argument added at :677 for the fan's accent). The modular-code rule says split before a feature goes in; Hazel judged one argument a fix, not a feature, and asked the planner (fan report, "Questions for the owner"). AvailabilityCompactMapUi.kt is 779, AvailabilityScreen.kt 755: close to the line, untouched by this question.

## 3. Notes (no action needed, or Hazel's next pass)

- **3.1 Right-to-left layouts, inferred and untested.** The tuck's slide direction is absolute (RouteCardTuck.kt:67, RouteCardFace.kt:74) while the strip's touch is placed by the layout-relative start/end (RouteCardTuck.kt:81). In an RTL locale the touch and the drawn strip would sit on opposite sides. Pre-existing placement already mixes absolute shapes with relative padding (RouteCardPlacement.kt:64-65, :80-81), so this PR adds to a mix it did not start; Hazel's report says RTL was "from reading". Not a Play audience concern today; worth one absolute alignment when the file is next open.
- **3.2 A flag that is set and never cleared.** "Navigated from the card" is set when Navigate is tapped and never cleared when that navigation ends (RoutePlottingViewModel.kt, `onNavigatedFromCard`); it is only read gated by "navigating to a waypoint now" (CompactMapRoutePlotting.kt, the Back handler). A later navigation from a bubble with the same card still open would count as the card's for Back's order. The visible result is the same in every case I traced (one Back ends it, the card stays), so a note, not a defect; a one-line clear when navigation ends would remove the question.
- **3.3 During the slide back, the card's faded buttons are touchable for about 0.75 s.** The strip's touch leaves the tree the moment "tucked" turns false, while the words fade in over the slide. A tap in that window lands on a fading button. Not a ruling and not likely in practice.
- **3.4 Database read does a write.** Reading all routes first clears links to deleted waypoints or trips, inside the same transaction (PlannedTripRouteDao.kt:26-30). Room only re-notifies for rows that changed, so this settles after one pass and cannot loop; inferred from Room's trigger shape, not measured. The owner accepted the next-read timing (-2187, 2026-11-07T12:36:12Z).
- **3.5 The fan's pause stays.** Measured and explained by Hazel as Android's 300 ms double-tap wait inside the map library, present on pre-main; the owner chose "Leave it" (-2187, 2026-11-08T20:19:49Z). Nothing in this PR touches the tap path (I checked the diff: MapListeners.kt and the fan-out state files are unchanged).
- **3.6 Merge commit 420e69742 carries git's default message without the co-author line**; Hazel disclosed it and did not amend (right, per push-before-you-tidy).
