# Addendum to the auditor framework for E-GD (prompts/preserved/2026-10-16-05-auditor-framework-for-egd.md)

Written by Forager's planner on 2026-10-16, after the framework document was committed, recording the owner's later rulings. The original stays as written; read this alongside it.

**1. Phone checks and field walks are not gate steps** (Forager RECORD -1133). The owner: "Field walks and device checks aren't always necessary, so don't add those as gates".
- The gate is now three steps: automated checks, the auditor's report, the owner's approval.
- The planner proposes a device check or field walk when a promotion needs one, and the owner decides.
- The auditor marks anything not seen on a device as such.
- An upgrade check over the live version runs only when a promotion changes how user data is stored.

**2. The auditor runs on a different model from the coder** (-1134). The owner: auditor sessions "shouldn't be held by the same coder model that implemented it … It's useful because the same model shares blind spots", and, in general, "just another model altogether. Maybe ChatGPT or Gemini if the user has no claude subscription".
- The auditor is a fresh session, started by the planner or opened by the operator in another window.
- It is never the coder that built the work, and it runs on a different model, from another provider where only one is available.
- The same holds for independent reviews of research results.
- Each record names the model that ran the audit.

**3. What it is for** (the owner): "It's a tool for passing pre main into main cleanly. We do this pretty good now, so the rules we have are simply what we already do. Just codified". The framework writes down existing practice; it isn't new process on top.

**4. First use.** The first promotion ran on 2026-10-16/17 and was documents only (Forager -1131 to -1136).
- The auditor (an Opus session, before rule 2 existed) passed it.
- It caught two real gaps in the planner's own documents.
- The phone-check path is still untested.
- The known-bugs list (A6) now exists as `docs/process/known-bugs.md`, with statuses open, hold and resolved, and the two fields the shipping rule reads: live or new, and serious or not.
