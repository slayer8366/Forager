## 3. The cause, with file and line

**The test's steps:**
1. The repository's store runs on `Dispatchers.IO + SupervisorJob()`, and the test holds that scope [read AvailabilityScreenCrowdedIconsSettingTest.kt:74-78].
2. Three touches pick List, then Zoom in, then fan, then List (:157-166).
3. Each touch calls `onCrowdedIconsModeChanged`. It updates the screen state at once, then launches `setCrowdedIconsMode` → `dataStore.edit` in the ViewModel's scope [read AvailabilitySettingsPrefs.kt:240-248, DataStoreMapPreferencesRepository.kt:166-168].
4. Nothing waits for the write. :164-165 read only the in-memory state.

**Writes land in tap order** [read, DataStore 1.2.1 source]:
- `updateData` puts the write on the store's queue before it first suspends (DataStoreImpl.kt:167-186).
- The queue is an unlimited channel consumed one message at a time (SimpleActor.kt:45, 78-117).
- Each write re-reads the file and is applied under a lock (DataStoreImpl.kt:345-360).

**Each write trails the touches** [read; the claim that it trails is inferred]:
- A write's transform runs in the caller's context, which is the main thread (DataStoreImpl.kt:351).
- Under Robolectric the main thread's queue runs only when the test idles it (compose ui-test 1.12.0, RobolectricIdlingStrategy.android.kt:63-118).
- Compose's test rule does not replace Dispatchers.Main (no `setMain` in ui-test 1.12.0).

**:167 cannot tell the first List from the last** [read]:
- `awaitIdle("List stored") { … == LIST }` is true as soon as the store reads List.
- The first write already makes it List. With two modes, the pick sequence starts and ends on the same value.

**:168, `release(scope)`, cancels the store with writes outstanding** [read]:
- The queue checks `scope.ensureActive()` before each next message (SimpleActor.kt:108-115).
- Messages still queued are failed with CancellationException (SimpleActor.kt:56-68, DataStoreImpl.kt:212-219).
- A write whose transform has already resumed on IO runs to the file. Nothing between there and the rename checks for cancellation:
  - DataStoreImpl.kt:351-357 and 363-380;
  - FileStorage.kt:105-128, a .tmp file, fsync, then a rename;
  - the uncontended Mutex fast path, kotlinx-coroutines 1.11.0 Mutex.kt:166-169.
- A write cancelled before that point is discarded (Builders.common.kt:452-455).

**So the file holds zoom_then_fan** [inferred, by deduction from the read code and the observed value; no instrumentation was run]:
- Because writes are applied in order, zoom_then_fan can be last on disk only if the third write never landed.
- Only the cancel at :168 can skip a write.
- The wait at :167 had passed, so the List it saw came from the first write. The second write landed after it.
- The poll can see List in that window in two ways: from the cache, before the second write's version bump; or by reading the old file during the second write's .tmp write and fsync (DataStoreImpl.kt:300-337, 382-394).
- The dropped write's CancellationException is re-thrown (RunCatchingCancellable.kt:18-24), so nothing is logged.
- The longer durations of the failing executions fit slower writes [inferred].

**Shared across tests** [read]:
- File path: each test method gets its own temp data directory (RobolectricTestRunner.java:306-309, AndroidTestEnvironment.java:152 and 630, TempDirectory.java:59-61). So the file is per test.
- Store instance and scope: one per launch (SettingsDataStore.kt:33-52; test :74-78).
- The store's active-file registry is keyed by absolute path, so it differs per test (FileStorage.kt:50-63).
- Dispatchers.IO is shared across the JVM.
- `tearDown` cancels without waiting (:106-109). The previous test's store is in another directory, so it cannot write this test's file [inferred].

## 4. Whether a user can meet it

- **Reordering:** no. Writes reach the file in tap order [read, as in 3].
- **Losing the queue the way the test does:** no. In production the store's scope is the default (DataStoreMapPreferencesRepository.kt:48). It is built once, by AppContainer.kt:357, and nothing keeps a handle to cancel it [read]. The drop-the-queue path cannot run while the app is running [inferred].
- **A real restart is process death.** The last pick is lost only if the process dies inside that write's own window: from the tap to the file rename. That is one main-thread message plus a small write and fsync, which is milliseconds [inferred; not measured on a device].
  - It applies to every setting stored this way, not only this one.
  - The user would see: on reopening, Crowded icons shows the choice before the last one.
  - A person's own actions cannot kill the process that fast [inferred].

## 5. Mechanism prediction, test plan, files

**Mechanism prediction (Phase 2):**
- The case's restart waits until all three picks' writes have returned from the store, all successful, and the store reads List.
- A test-only wrapper around the real repository does the counting, and the ViewModel is given that wrapper as its crowded-icons repository.
- A write returns only after its file rename and cache update (DataStoreImpl.kt:244-281, 345-380). So "three returned" means all three are on disk before the release.
- No change to app code. Every existing assertion (:164-165, :170, :173, :174) stays as it is.

**Test plan:**
1. **Failing first, deterministic.** Add a new case with a "late store" wrapper:
   - the first write goes straight to the store;
   - each later write is held, and is let through only on the test's next read through the wrapper, where it runs to completion off the main thread.
   - This forces the interleaving CI shows. With today's wait, I predict a failure at :170 with list/zoom_then_fan on every run. With the corrected wait (list, then zoom, then list with three writes returned), I predict a pass.
2. The existing case switches to the corrected wait, using the counting wrapper without the lag.
3. **Revert check under CLAUDE.md's runner rules.** Revert the wait to today's condition on its own scratch branch. Read the compile log first. Restore the file from a saved copy, and confirm afterwards that the forward change is still present. Expected: the late-store case fails with list/zoom_then_fan.
4. **Repetition on CI.** The same 100-copy setup over the fix, 3 dispatches, about 300 filtered and 300 full-suite executions, expecting 0 failures. run2 gave 0 of 100 with the bug in place, so a clean run counts as evidence only alongside step 1.

**Files (predicted):**
- AvailabilityScreenCrowdedIconsSettingTest.kt (199 lines; about +30);
- one new test-only file for the two wrappers (about 60 lines; name to be settled);
- no app code and no ci.yml change.
