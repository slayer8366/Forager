## Two explanations already tried and disproved. Don't repeat them.

1. **"Bash doesn't run the EXIT trap on SIGTERM."** False here. In a repro, bash 5 ran its EXIT
   trap on SIGTERM without a TERM trap, both while in `wait` and with a foreground command, with
   stdout through `tee` and the signal sent to the whole process group. A TERM trap was added and
   then taken out.
2. **"The EXIT trap ran but could not log because `tee` was dead."** Consistent with the missing
   log lines, but not with the status file: `run_record.py status` is the first thing `on_exit`
   does, and its write did not land.

Under CLAUDE.md that makes this a gather-data task, not a hypothesis task.

## What to gather

1. **Reproduce under systemd itself, harmlessly.**
   - Run a tiny script with `build-usca.sh`'s exact shape (`set -euo pipefail`, the `tee`
     redirect, an EXIT trap that writes a file and calls `python3 -c` to write another, and a
     foreground child doing `sleep`).
   - Run it as a transient unit with `systemd-run`, as the builds were. Use default `KillMode` and
     `--uid=forager-build`.
   - Stop it with `systemctl stop`, and record which files the trap wrote.
   - Repeat with the child being `python3 peak_rss.py LABEL -- sleep 30`. That is how every heavy
     step runs (`TIMED` in `build-usca.sh`).
2. **Read what `peak_rss.py` does with signals,** and what exit code it gives the script when its
   child is killed.
3. **Read systemd's documented stop sequence** for a transient service: which processes get
   SIGTERM, and when SIGKILL follows (`KillMode`, `TimeoutStopSec`, `SendSIGKILL`). Quote the
   documentation; don't recall it.
4. **The journal for the real stop.** Check `journalctl -u forager-usca-routing-261017 -o verbose`
   around 06:33:36, for exit codes or signal names.
