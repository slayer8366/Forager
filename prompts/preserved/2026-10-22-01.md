## Part B: three map types in the app

**What the owner decided (-1554), as steps:**

```
Maps tab › Layers › Map type
  [ Trail Map (Default) ]  [ Topographical ]  [ OpenStreetMap ]

New user                → opens on Trail Map
Street chosen today     → after the update, opens on Trail Map (once);
                          OpenStreetMap stays on the right if they want it
Offline downloads       → Trail Map only; no OpenStreetMap tiles are ever stored
OpenStreetMap, signal lost → shows Trail Map until signal returns, then OpenStreetMap again
```

- "Trail Map (Default)" is the exact chip label. The others are "Topographical" and "OpenStreetMap", in that order, left to right.
- **Trail Map** is our own vector style. It's what `STREET_SERVED_BY_OWN_MAP = true` draws today (`map/StreetStyle.kt:21`, `STREET_STYLE_URL` at line 28).
- **OpenStreetMap** is today's raster Street (`Basemap.OSM_STANDARD`, `ui/map/Basemap.kt:137`).
- PR #359 (GitHub #359, branch street-switch-flip) is superseded: it replaced Street outright. Read it for the test updates it found (the 16 tests, the D1–D3 rulings in -1513), but don't merge it. Its compile-time switch goes away, because Trail Map and OpenStreetMap are now both always there.

**Read at 01c7c5b56:**
- `ui/map/MapMode.kt:36-37`: two modes, `STREET` (storageKey "street") and `TOPOGRAPHIC`. `DEFAULT = STREET` (line 45) and `REPLACEMENT_FOR_UNKNOWN = TOPOGRAPHIC`. The doc comment says never to change a storage key.
- `ui/map/MapLayersSheet.kt:281`: the chip row is `MapMode.entries.forEach`, so the order is the enum's order.
- `map/StreetStyle.kt`: the switch and the functions that take `ownStreet`, including `offlineDownloadStyleUrl`, `offlineRenderStyleUrl` and `regionHasOlderMapStyle`. The switch is also read in `BasemapStyles.kt` (16 references), `MapStyleReload.kt`, `OwnStreetFallback.kt`, `MapNavigationView.kt`, `NavigationView.kt`, `OfflineRegionsList.kt`, `MapLibreOfflineMapRepository.kt`, `SightingsMapLayout.kt` and the two credits screens.

The manifest declares INTERNET but not ACCESS_NETWORK_STATE (read from `app/src/main/AndroidManifest.xml`; the merged manifest isn't checked). The main Maps tab never sets `useOfflineTiles`; only `CartographyEntryReportScreen` does.

  - If the world archive's absence can't be known cheaply at TileJSON time, propose an option and stop. Don't pick one.
- **Tests:** one that fails before and passes after, plus a revert check, as before.
- **Deploy steps:** say the TileJSON is edge-cached for a day. Add a device step: after the deploy and a cache clear, panning to Bogotá at zoom 8 on Trail draws map.

A straddling tile served from `us` is therefore plain land and water, not grey. Say so in the PR's deploy check: an `r2` answer there is the overlap rule working, not a failure.
