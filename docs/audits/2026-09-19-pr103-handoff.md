## What changed in #102 after #103 was branched

Each of these is a structural change to the camera, not a tweak. If #103 touches any of them, its
premises need re-reading.

**The camera stopped being a Dialog.** It now draws in the Activity's own window, to obtain
seamless rotation, which a Dialog cannot get: the platform picks a rotation's animation from the
task's main window, which is only ever `TYPE_BASE_APPLICATION`, and then requires that window to be
the top fullscreen opaque one.

Consequences that ripple:
- `DialogWindowProvider` casts no longer resolve.
- Back no longer routes through the dialog's own `OnBackPressedDispatcher`.
- Tests that construct the dialog directly, or use `ShadowDialog`, were rewritten.

**Done was removed.** Back is the only way out of the camera. Anything referencing a Done control,
its tag, or its label is gone.

**The window's orientation behaviour was inverted twice.** It was locked, then unlocked with
seamless rotation, and reverse portrait is now excluded via `SCREEN_ORIENTATION_SENSOR` rather than
`FULL_SENSOR`. Anything written against "the window is pinned while the camera is open" is stale.

**A region model was introduced.** Viewfinder region plus two bands, zero-thick at full-bleed, with
controls anchored inside the bands rather than against screen edges.

**Control placement is now expressed in device anatomy.** The shutter sits on the charger-port
edge and the strip on the punch-hole edge, both computed from device rotation, not from a fixed
screen side. Any code or test expressing a position as "left" or "right" is expressing it in the
wrong frame.

**A top strip exists**, currently holding only a gated placeholder. Its controls are PR #103's
territory if #103 is the feature work.

**The status bar is hidden while the camera is open**, on the Activity's window, revealing on a
swipe from the screen's top edge.

**A four-minute absence timeout** closes the camera, decided by comparing two `elapsedRealtime`
readings on return.

**Photos persist on shutter success**, so `captures/` holds a file only between the shutter and the
save. The startup sweep's remaining job is crash debris.

**Diagnostics gained an instrument.** Each capture writes a `capture shot` entry carrying
`deviceRotation`, `displayRotation`, `targetRotation`, `requestDegrees` and `resolution`, plus one
`capture orientation` outcome. This is the tool for any future orientation question and it has
already settled two.

## Outstanding from #102, not blocking #103

**Step 11 of the device check, colour, has not been run.** The scrubbed file carries no
`ICC_Profile` on a wide-gamut device and whether that is visible has not been checked.

The order established for settling it:

1. **Run a stock-camera photo of the same subject through exiftool.** This separates "this camera
   writes no profile at all" from "ours is losing one", and needs no particular light. It can close
   the whole line of inquiry.
2. **Only if the stock file has a profile and ours does not:** read
   `androidx.exifinterface:exifinterface:1.4.2` (pinned at `gradle/libs.versions.toml:50`), the
   JPEG save path, `saveJpegAttributes` and `getJpegAttributes`. The narrow question is whether the
   writer copies the remainder of the stream verbatim after its own APP1, or re-emits only
   segments it recognised. Verbatim preserves every APP2 chunk; selective re-emission is where a
   chunked profile could be lost.
3. **Only if something survives both:** the step's own side-by-side, one subject under the same
   light, in-app against stock.

**A known gap in the coverage, worth carrying:** the scrub's ICC test uses a single APP2 segment
with a 16-byte synthetic payload and asserts only that the marker survives. A real phone profile
over roughly 64 KB is split across several APP2 chunks. That test passes identically whether or not
the multi-chunk path works, so it is not evidence about it.

**Two smaller items with committed records:** `ExifIFD Light Source` survived the allowlist scrub,
and `rewritten` appears unreachable on the reference hardware because its HAL writes the correct
orientation tag.

## One thing learned tonight, recorded because it will recur

`docs/audits/README.md` is a serialization point, and **the cost is per landing rather than per
change**. #106 paid the conflict twice for one row, because it waited behind #105. A branch's cost
is the number of other branches that land before it, not the size of what it carries.

The resolution is always the same: merge `main` in, never rebase, keep every row. Check it by
**containment in both directions**, not by arithmetic. A count can balance through one row being
dropped and another duplicated.

## Verification, added 2026-09-19: the five questions came back clean, and the finding came from elsewhere

Checked against `claude/camera-groundwork-vto65i@b1c45f9`, whose merge-base with `main` is
`0e83bd4`. #103 touches four source files: `CameraCaptureSession.kt`, `CameraXCaptureSession.kt`,
the new `FakeCameraCaptureSession.kt`, and `InAppCameraDialogTest.kt`.

**All five answers are no.** No `ShadowDialog`, no `DialogWindowProvider`, no dialog constructed
(the only `Dialog` hits in the branch are unrelated `AlertDialog` call sites that predate both
PRs). No reference to Done; the one match in its test edit is `onDismiss`, which still exists on
`main`. No orientation code, so nothing assumes a locked window. Nothing positioned by screen side.
Nothing added to the overlay. #103 sits entirely below the UI.

**And that is why the five questions could not have found the real problem.** They were derived
from #102's change list, which is UI-level throughout: the window, the bands, Done, the strip, the
status bar. A checklist built from the changes you know about can only find problems in the area
those changes touched. #103 is below that line, so a clean sweep was the expected result and not
reassurance about anything. What follows was found by reading the branch's diff, not by answering
the checklist.

### The finding: `FakeCameraCaptureSession.kt` was written twice, at one path

`main` carries a 71-line version, landed in #102. #103 adds a 53-line version at the same path, as
a new file. They are the same idea reached independently in the same week, with some of the same
sentences: both record that it used to be a private class inside `InAppCameraDialogTest`, both keep
the one-byte stub on failure, both cite the revert check that found the stub mattered.

Each carries something the other does not. `main`'s has `readyOnOpen` and counts `open`/`close`
calls, which is the lifecycle the camera-open deadlock fix hangs on. #103's returns a
`CaptureOutcome` naming the destination and `ImageFormat.JPEG`.

**This is the second instance in this project of the pattern CLAUDE.md records under "Verify your
base branch before you start":** two branches each individually correct, asserting the same
globally-unique thing, merging without a semantic conflict a file-level merge could detect. The
first was PR #26 and the Phase 1 branch each declaring `ForagerDatabase.version = 5` with different
`MIGRATION_4_5` bodies. Here the unique claim is a shared test fake rather than a schema version,
and the collision surfaces as an add/add conflict whose mechanical resolution picks one file and
silently discards the other's design.

### `CaptureOutcome` is the part that is genuinely new, and it is now a rewrite

`git grep CaptureOutcome origin/main` returns nothing. `main`'s `capture` still returns
`Result<Unit>` (`CameraCaptureSession.kt:64`). But that function has grown substantially since
#103 branched: the diagnostics pair, the `IntendedOrientation` reapply and its four outcome
branches. The merge-base is `0e83bd4`, the **first** commit of #102's work, so `capture` changed
almost entirely underneath #103. Reapplying `CaptureOutcome` is a rewrite against a different
function, not a port.

### Recommendation

**Not a rebase.** A three-commit rebase presents a design question as two textual conflicts and
invites the resolution that loses one side. Instead: take `main`'s fake and add `CaptureOutcome`
to it, then reapply `CaptureOutcome` to the current `capture` by hand.

**Retarget #103 to `main` first.** Its base, `claude/new-session-vto65i`, still exists at `de78d30`
rather than having been deleted on merge, so the PR currently compares against a stale branch and
any diff read from GitHub is misleading until that is changed.
