**Mergeable into pre-main at `2c3566977`,** with two Mediums to settle before the engine routes on these folders

engine would read: every file is written under a `.download` name, the folder under `.partial`, the record last,

### M1, the path

`download` removes the id from `inFlightRegionIds` in the `finally` at `MapLibreOfflineMapRepository.kt:149-154`,
updates the metadata and upserts the Room row (`:157-170`), then calls `routes.fetchFor` (`:173`). From that point until the route fetch
ends, `listRegions` shows the region: MapLibre lists it complete, the row exists, and `routes.status(id)` finds no
`<id>` folder (`RegionRouteStore.kt:70-72`), so `NotFetched`. `RecordsTab.kt:242-248` runs `onOfflineMapsOpened` on
every entry into the sub-tab, and a download keeps running in `viewModelScope` while the user is on another sub-tab.
So: start a download, tap another sub-tab, tap back while the files come. `onOfflineMapsOpened` joins the list,
`regionsNeedingRoutes()` includes the new id (`AvailabilityOfflineRoutes.kt:29-30`), `fetch` finds it absent from
`offlineRouteFetchingIds` (`:38`), `fetchRoutes(id)` passes both checks (`:196-199`), and `beginFetch`
(`RegionRouteStore.kt:40-46`) `deleteRecursively`s the `.partial` the download's fetch is writing into. The
download's `fetchFile` then fails to open its temp (`RouteStorageException`, `RouteAreaClient.kt:79-83`), its
`commit` throws on the record write, `fetchFor` returns `Missing(STORAGE)` (`RegionRouteFolders.kt:50-54`), and its
`endFetch` removes the second fetch's `.partial` and drops the id from `fetching`; the second fetch fails the same
way. Nothing is recorded; the download's answer marks the region failed (`noteDownloaded`), the row says B with Try
again, and Try again works. The ViewModel's own guard (`offlineRouteFetchingIds`, revert 24) cannot see the
download's fetch because that one goes straight through the repository.

Shape of a fix, either side: `beginFetch` refuses an id already in `fetching` (its own set, `:35`), returning a
distinct answer rather than clearing the folder; or the repository keeps the id in `inFlightRegionIds` until the
routes are in (then `listRegions` does not show it yet, which also removes the window where a listed region has no
route line and no size for its routes). One store, one writer per id, is the invariant the folder design already
assumes.

### M2, what a keyless build says

`fetchRouteArea` returns `NO_APP_KEY` before any request (`RouteAreaFetch.kt:32`; test "a build with no app key sends
nothing", revert 5). `retryHelps()` excludes it (`RegionRouteData.kt:137-143`), so `offlineRouteLine` gives C's text
with no button (`OfflineRegionRouteLine.kt:30`). The log says why; the user reads "No trail routes for this area
yet", which is false about the area. CLAUDE.md asks that an unsupported capability return an explicit "unsupported",
never a plausible value, and "don't make me think" names the state a user could misread as broken as the worst case.
This is the owner's to rule on (a fifth line, or C with a different word), and it only matters if a keyless build
reaches a phone, which is the second half: the key reaches `BuildConfig` from an environment variable or a Gradle
property (`app/build.gradle.kts:260-263`), CI sets it on the debug APK step only, and I found no release recipe that
sets it. The planner should confirm how the next Play build gets the key before it is cut.

## 1. The key

- **Where it lives.** `BuildConfig.ROUTING_APP_KEY` (`app/build.gradle.kts:260-263`), read once in `AppContainer.kt:289-295`
  and passed to `RouteAreaClient` and `fetchRouteArea`. `git grep` at the head for `routingAppKey`,
  `ROUTING_APP_KEY` and `FORAGER_ROUTING_APP_KEY` finds only the Gradle script, the CI step, the comments and the
  Worker's own secret name: no value anywhere in the tree. `gradle.properties` has no routing key.
- **Not logged.** The debug client's `HttpLoggingInterceptor` is `Level.BASIC` (`ApiClients.kt:31-33`): request line
  and status, no headers. The URL carries the four edges, never the key. No log line in `RouteAreaFetch`,
  `RegionRouteStore` or `RegionRouteFolders` interpolates `appKey`; the details that are logged are file names,
  statuses, codes, messages, byte counts and the file list's `url` (on another host, which is the one place a
  server-chosen string reaches the log, truncated to the url).
- **Not in a file.** `routes.properties` holds state, reason, run id, timestamp, names, sizes, sha256s
  (`RegionRouteRecord.kt:26-49`). Hazel's phone check (`x-forager` matched 0 lines) is her claim; I did not see the
  logcat.
- **CI.** `env: FORAGER_ROUTING_APP_KEY` is on the "Build the debug APK" step alone (`ci.yml:112-120`); "Run the unit
  tests" (`:180-192`) sets only `TESTS`; `lint`, `release-compile`, `route-cutter` and `pmtiles-worker` have none. A
  fork's pull request gets no secrets from GitHub, so its APK has an empty key. The `.github` diff is those four
  lines, as the report says.
- **An empty key sends nothing.** `RouteAreaFetch.kt:32`, before the client is touched; revert 5's failure is that
  test. The client itself does not guard (`RouteAreaClient.kt:129` would send an empty header); it is reached only
  through `fetchRouteArea`.
- **Never to another host.** `resolveOnBase` (`RouteAreaClient.kt:135-139`) refuses a file url on another scheme,
  host or port; revert 6.
- L5 is the one thing to know: the artifact on a public repo.

## 2. Atomicity and clean-up

**Can a crash leave an `.rd5` the engine reads as corrupt?** I traced each point:

1. *While a file streams:* it is `<name>.rd5.download` (`RouteAreaClient.kt:75`), inside `<id>.partial`
   (`RegionRouteStore.kt:40-46`). The engine's pre-check reads `.rd5` only (#382, `RoutingDataFolder.kt:28`), and it
   is handed a folder only from `RegionRouteData.Stored.folder` (`FindRouteDataForPointUseCase.kt:33-36`), which
   `status()` returns only for a `<id>` folder with a readable record whose every file has its recorded length
   (`RegionRouteStore.kt:70-96`). `<id>.partial` is never that folder. Test "a download cut off mid-file" records what
   is on disk at the moment the connection drops (`RegionRouteFetchTest.kt:151-179`), and revert 21 (`val temp =
   destination`) fails it with `[W125_N45.rd5]` on disk: the check sees the moment, not the clean-up after.
2. *Between the file's checks and its rename:* the three checks run before `renameTo` (`:99-123`); a failure deletes
   the temp. The header is checked against the list first, then the length, then the body hash; a list/header
   disagreement is refused before the bytes are trusted (reverts 1 and 16, the "without its header" test).
3. *Between files:* a `.rd5` of a finished file sits in `.partial` beside a `.download` of the next ("while a file
   downloads its name does not end in rd5", `:181-196`). A crash here leaves `<id>.partial`, which `cleanOrphans`
   removes unless this process is still fetching it (`:138-146`; revert 10 proves the running case is kept).
4. *The record and the folder rename:* `commit` writes `routes.properties` into `.partial`, moves any old `<id>` aside
   as `<id>.deleting-<n>`, then renames `.partial` to `<id>` (`:52-60`). A crash before the rename leaves `.partial`
   (cleaned); between the discard and the rename, no `<id>` (`NotFetched`, fetched again next opening); after, a whole
   folder. Rename within one filesystem is atomic to a process crash. For a non-stored record the files are removed
   before the record is written (`:53-55`), so a folder under an id holds either every listed file or none.
5. *Power loss:* L2. Without `fsync` a renamed file can be short or empty on the next boot; the size check and the
   unreadable-record path turn that into `Damaged`, which `needsFetch()` re-fetches and which the lookup never hands to
   the engine. The one case neither catches, a right-sized file with wrong bytes, is the engine's own checksums (L7).

**Sha checks against both the list and the header:** `RouteAreaClient.kt:99-116`, in the order header-present,
header-equals-list, length, body-equals-list. Reverts 1 (body), 16 (header absent) and the "header disagrees" test
cover the three.

**Reconciliation:** `reconcileOfflineRegions` reads each shown region's state, adds its bytes to its size
(`OfflineRegionReconciliation.kt:95-108`), deletes a never-finished region's routes with its tiles (`:59-60`), and
last calls `cleanOrphans` with every Room row id, every live id but those just deleted, and every running download
(`:113`). `cleanOrphans` removes `.deleting-` folders, `.partial` folders no running fetch owns, and `<id>` folders in
no keep set, logs each, and leaves any other name alone with a log line (`RegionRouteStore.kt:113-146`). Revert 7
(both keep-set tests) and the seven `OfflineRegionReconciliationRoutesTest` cases cover it. The keep set is right:
a Room row with no MapLibre region is "kept, not shown" by the existing rule, so its folder stays with it.

**Delete with the region:** `deleteRegion` → tiles, row, then `deleteRoutesOrLeaveForCleanup`
(`MapLibreOfflineMapRepository.kt:203-206`, `OfflineRegionReconciliation.kt:121-128`): the folder is renamed aside first (all or nothing), a failure is logged and the folder is an orphan for
the next listing. Revert 3.

promised size (`RouteAreaClient.kt:86`).

## 4. The automatic fetch

- **Once per opening.** `RecordsTab.kt:242-248`: `LaunchedEffect(selectedTab)` calls `onOfflineMapsOpened()` on entry
  to the Offline maps sub-tab; it re-runs when the key changes or the tab recomposes from scratch (another tab and
  back, or recreation), each of which is an opening. It does not re-run on ordinary recomposition. The ViewModel
  (`AvailabilityViewModel.kt:776-782`) reads `noSignal()` at the opening, joins the list load, and fetches
  `regionsNeedingRoutes()` once; `fetch` ends with `reloadRegions()` (`AvailabilityOfflineRoutes.kt:57`), which is
  `loadOfflineRegions`, which triggers nothing. No loop.
- **Nothing with no signal.** `if (noSignal()) return` before the launch (`:778`); revert 22 removes it and the
  no-signal test fails. `noSignal` is MainActivity's real monitor (`MainActivity.kt:79`, `:363`:
  `AndroidNetworkSignal.validated` through the hysteresis), live on every tab, and the ViewModel's default is
  `{ true }` so a ViewModel built without it fetches nothing.
- **No double fetch.** `fetch` filters ids in `offlineRouteFetchingIds` and writes the set synchronously before
  launching (`:38-40`); the test "a region being fetched ... is not fetched twice" opens twice and taps Try again
  while a gated fetch runs and sees one call (revert 24, `[1, 1, 1]`). The one writer it cannot see is the download's
  own fetch: M1.
- **One attempt, then Try again.** A fetch whose answer still `needsFetch()` or whose `Result` failed marks the id
  failed (`:43-55`); a download's own result does the same through `noteDownloaded` (`:62-64`, revert 25). The
  "once per opening, not looped" test opens twice and sees two attempts (revert 26).

## 6. The Room decision

Sound under CLAUDE.md's rule as I read it. The deciding question is what the data will be queried for: nothing
joins on, filters by or indexes a region's route state; the one reader that decides on it
(`routeDataForPoint`) lists every region and reads the state off each, which is what a Room column would give it
too. The state is also a derivative of files on disk, and the tile count and size already follow "read live, never
stored" for the same reason. The migration-number point (two branches in flight) is a real cost avoided, and
`ForagerDatabase` stays at 22 (no `app/schemas` change in the diff).

**A journal backup restored onto another phone.** `offline_regions` is in the backup (`JournalTables.kt:45`); the
route folders are not, and neither are the tiles: `data_extraction_rules.xml` excludes every domain whole, and the
journal backup copies tables, not `files/`. On the new phone the row has no MapLibre region, so it is "kept, not
shown" by the existing rule or shown as not downloaded with "Download again"; `routes.status` is read only for live
regions (`OfflineRegionReconciliation.kt:95`), `fetchRoutes` refuses an id MapLibre does not list
(`MapLibreOfflineMapRepository.kt:196-199`), and "Download again" fetches the routes under the new region's id in
`download` itself. A restored row's negative id is a folder name like any other
(`RegionRouteStoreTest` "negative region ids") and cannot collide with a folder MapLibre's positive ids left. Had the
state been a Room column, the restored row would claim routes the phone does not have, which is the case Hazel's
doc comment names (`RegionRouteStore.kt:17-19`). I agree with the choice.

## 7. Modular code

Asked to say plainly: **yes, M3 breaks the rule as written for `AvailabilityViewModel.kt`.** The skill's test is "a
fix of a few lines to a big file doesn't need a split first; a new capability does", and the automatic fetch is a new
capability whose decision, by RECORD -1450's own rule, has to sit in a ViewModel function. The work is in a new
65-line collaborator, which is the right shape; what went into the ViewModel is +32/−3, not two lines. The report
discloses "no split was made for that" and so is honest about the fact while wrong about the size. `JournalTab.kt`
(+3) and `AvailabilityCompactScaffold.kt` (+2, at 1,441 and not named in the report's list of big files) are the
pass-through case the allowance covers. New files: 24 to 239 lines, each one job (`RouteAreaClient` the two routes,
`RouteAreaFetch` the one fetch, `RouteAreaErrors` the mapping, `RegionRouteStore` the folders, `RegionRouteRecord`
the file, `RegionRouteFolders` the interface and its phone implementation, two domain files, two UI files).
`MapLibreOfflineMapRepository.kt` 404 → 422, under the dispatch's 450. Domain files import no Android. CI still has
no line-count warning (as in #382 L6; `ci.yml` has none).

The owner's rule and the owner's ruling for this feature pull against each other here, and the planner is the one
to carry that: either the ViewModel split (a pure move, its own PR) goes ahead of the next feature that touches it,
or the owner says the decision functions are the allowance.
