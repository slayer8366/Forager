## Verdict

**Mergeable into pre-main at `0b127f374`.** No finding is a secret-exposure path, and nothing can run the signing
steps without the owner's approval or off main. Four Lows, each a one-line change Hazel can make before or after
the merge; nothing blocks. The workflow has not yet run end to end, by construction (it needs the file on main and
the Play secret), and the section "Not verified" below says exactly what a first real run is still the only test of.

## Findings

Severity: High blocks; Medium should be fixed before the next promotion; Low is a real gap with a cheap fix; Info
is a fact worth recording, not a defect.

**L1 (Low). The signing guard prints the key alias, which is stored as a secret.** `app/build.gradle.kts:476-479`
logs `alias '$keyAlias'` in its first "Verified:" line, and `release.yml:132` tees that log to the public Actions
log. The alias is `FORAGER_SIGNING_KEY_ALIAS`, one of the environment's secrets (names listed via API). GitHub masks
registered secret values in the log, so the public page shows `***`; the plain value is in
`app/build/release-gradle.log` on the runner's disk only, which no step uploads. Residual risk is the masking
itself, which is best-effort (a short or common-word alias masks every occurrence of that word and can be worked
around by transformation; here the value is printed verbatim, so it is masked). An alias on its own unlocks
nothing without the keystore and both passwords. Fix, either side: stop treating the alias as secret, or change the
guard's message to omit it. Pre-existing in the build file; the workflow is the first place it meets a public log.

**L2 (Low). The service-account JSON is written into the checkout and only the action's own `finally` deletes it.**
`release.yml:216-222` passes `PLAY_SERVICE_ACCOUNT_JSON` as `serviceAccountJsonPlainText`. At the pinned SHA the
action writes it to `./serviceAccountJson.json` in `$GITHUB_WORKSPACE` with default permissions
(`src/main.ts:124-128`), exports the path as `GOOGLE_APPLICATION_CREDENTIALS`, and unlinks it in `finally`
(`src/main.ts:107-113`); `lib/index.js` carries the same strings. `action.yml` declares `main` only, no `post:`
hook, so if the node process is killed (a cancel, or the job's 45-minute timeout landing during the upload) the
file stays on the runner until the ephemeral runner is destroyed. The workflow's own `always()` step
(`release.yml:224-232`) removes only the keystore. Fix: add `rm -f "$GITHUB_WORKSPACE/serviceAccountJson.json"` to
that step and assert it is gone, as the keystore line does. Exposure is bounded by the runner being ephemeral, no
artifact upload existing, and `permissions: contents: read`.

**L3 (Low). The Play-secret check runs after the signed build.** `release.yml:202-210` checks
`PLAY_SERVICE_ACCOUNT_JSON` after the keystore has been decoded and `bundleRelease` has run. A run with the secret
missing (today's state) would decode the keystore, build and verify a signed bundle, then fail with nothing
uploaded. Nothing leaks, but the keystore is touched for no reason. Move the step above "Decode the upload
keystore"; the secret is visible only inside the approved job, so that is the earliest possible point.

**L4 (Low, pre-existing, shared with ci.yml). The SDK script downloads cmdline-tools without a checksum.**
`scripts/setup-android-sdk.sh:8,14` fetches `commandlinetools-linux-11076708_latest.zip` over HTTPS from
`dl.google.com` with no pinned hash; `sdkmanager` then verifies its own packages against Google's repository
manifest. The release job runs this script (`release.yml:99`) before the keystore is decoded. Out of this PR's
scope, but it is now in the signing job's supply chain, which is why it is recorded here.

**I1 (Info). The gradle/actions pin is a full SHA of the annotated tag object, not of a commit.**
`release.yml:92` (and `ci.yml:90,515,566`) pins `67621b124fd2e251c5e8a0e6e3b91318f2287669`. The API has no commit
by that SHA; `git/ref/tags/v6.3.0` points at it as a `tag` object, which dereferences to commit
`9c971963bec38e04b3d30dcc455b5382be2fdbfb` (tagger date 2026-08-02, signature verified). A tag object is
content-addressed and embeds the commit it names, so this is as immutable as a commit pin, and CI resolves it (run
40020613280 used it). The dispatch's "pinned by full commit SHA" is met in substance; tools that expect a commit
SHA (pin checkers, Dependabot) may not recognise it. The other three pins are commits and match their tags exactly:
`actions/checkout` v7.0.1 `3d3c42e5…`, `actions/setup-java` v5.7.0 `b6effb05…`, `r0adkll/upload-google-play`
v1.1.5 `e738b9dd…`.

**I2 (Info). What the gate actually rests on, read from the API.** Environment `release`: `required_reviewers`
= slayer8366, `prevent_self_review: false` (needed, since the owner both dispatches and approves),
`can_admins_bypass: true` (the sole admin is the owner, so a no-op today; a second admin could skip the reviewer),
branch policy: one entry, type `branch`, name `main`. `main` has no branch protection and no ruleset, and the only
collaborator with push is the owner. So "main only" means "whatever the owner pushes to main", which is the
intended trust model, stated here so nobody reads the environment rule as stronger than it is. The job's
`GITHUB_TOKEN` is `contents: read` (`release.yml:22-23`) and cannot push.

**I3 (Info). Concurrency and timeouts.** `group: release`, `cancel-in-progress: false` (`release.yml:26-28`): a
second dispatch queues, nothing is cancelled. `timeout-minutes: 45` (`:50`) is shorter than the action's internal
one-hour limit (`src/main.ts:97-99`), so a stuck upload ends by job timeout, which cancels mid-edit exactly as the
line-25 comment warns a cancel would; an uncommitted Play edit expires on Play's side and the next run makes a new
one. See L2 for what a cancel leaves on disk.

## Checks, by the dispatch's list

### 1. Secret exposure in a public repo

- **Echo, log or upload of a secret or the keystore.** None in the workflow. Every secret is referenced only in
  a step `env:` (`:105,124-127,205`) or an action `with:` (`:218`); no `run:` line interpolates `${{ secrets }}`.
  The decode step prints the keystore's path, size and mode (`:117`), not content. The verify step captures
  `keytool -printcert -jarfile` into a variable and prints only the SHA-1 and SHA-256 lines (`:160-164`). The step
  summary (`:191-200`) carries versionCode, versionName, certificate SHA-256 and commit, all public. The action's
  `with:` inputs appear in the step header on the runner, masked. L1 is the one value that reaches the log, masked.
- **`set -x`, debug flags, `--info`/`--debug`, bundletool output.** No `set -x` anywhere (grep). Gradle runs with
  `--stacktrace --console=plain --no-configuration-cache` (`:132`), no `--info` or `--debug`. A stack trace on
  failure names paths and variable names, not values (`build.gradle.kts:202-213, 394-397, 435-442`). bundletool is
  invoked with `dump manifest --xpath` for two attributes (`:180-181`); its output is the value only.
- **pull_request or push trigger.** `on: workflow_dispatch:` only (`:19-20`), no `inputs:`. No
  `pull_request_target` or `workflow_run` in any workflow (grep over `.github/workflows` on the branch).
- **Caches written during signing.** `cache-read-only: true` (`:96`) is load-bearing, not decorative: at the pinned
  setup-gradle, the default is read-write on the default branch (`setup-gradle/action.yml:25-28` at `9c97196`), and
  this job runs on main. The configuration cache is off in `gradle.properties` (no such key) and disabled again on
  the command line, so no serialised signing config lands in `.gradle/configuration-cache`. No `actions/cache`
  step. The log is written to `app/build/release-gradle.log`, inside the checkout but under the ignored `/app/build`
  (`.gitignore:12`), so `git status --porcelain` does not see it and the `.dirty` suffix cannot fire on it.
- **The action's handling of the service-account JSON** (read at `e738b9dd`). Written to a file in the workspace
  and deleted in `finally` (L2). No `console.log`, `core.info` or `core.debug` in `src/edits.ts` prints credentials
  or tokens: the debug lines name edit ids, tracks, status, version codes and file paths (`:192-199,234,264,
  310-356`); the final `console.log` prints `result`, which is the internal-sharing URL and is void for `internal`
  (`:72-74,76-80`). Auth is `google.auth.GoogleAuth` with the androidpublisher scope reading
  `GOOGLE_APPLICATION_CREDENTIALS` (`:52-54`). `status: draft` is accepted without a user fraction
  (`src/input-validation.ts:16-37`); `tracks: internal` passes through (`:65-77`); `releaseFiles` is the
  non-deprecated input (`:47-63`).
- **Keystore cleanup on failure and cancel.** `if: always()` (`:225`) runs on failure, cancel and timeout;
  `rm -f` then an existence check that fails the step if the file remains (`:227-232`). `umask 077` before the
  decode (`:108`); the file is in `$RUNNER_TEMP`, outside the checkout (`:113`). The service-account file is not in
  this step (L2).

### 2. Approval and branch protection

- **Can anything run the signing steps without approval, or off main?** The job declares `environment: release`
  (`:52`), so the environment's gate is evaluated at job start, before step 1. The dry run shows the order: the
  deployment went `waiting` at 20:36:15Z and `failure` at 20:36:25Z with no approval and **zero steps** recorded
  for the job (jobs API, `steps: []`). Secrets are environment-scoped (`FORAGER_UPLOAD_KEYSTORE_B64`,
  `FORAGER_SIGNING_*`, `FORAGER_ROUTING_APP_KEY` listed under the environment); the only repository-level secret
  is `FORAGER_ROUTING_APP_KEY`, which ci.yml already uses (`ci.yml:119`) and which is embedded in every APK by
  design (`build.gradle.kts:118-127`). A fork's pull request gets neither the environment nor a dispatch.
- **Is the ref check meaningful?** `release.yml:55-62` compares `$GITHUB_REF` to `refs/heads/main`. It runs only
  after approval, so it never substitutes for the gate; it matters in two cases: the environment's branch policy
  being loosened later, and a ref that is not a branch (the policy type here is `branch`, name `main`; a tag named
  `main` would be `refs/tags/main` and this step refuses it). For a `workflow_dispatch` run `GITHUB_REF` is the
  chosen ref, so on main it is `refs/heads/main`. Meaningful as a backstop, correctly described as one.
- **`workflow_dispatch` input injection.** Not applicable: no `inputs:` block, and no `${{ github.event.* }}`,
  `github.ref`, `github.head_ref` or other attacker-influenced context appears in any `run:` line. No `run:` block
  contains a `${{ }}` expression at all (grep); `env.PACKAGE_NAME` and `github.workspace` are used in `with:` and
  `env:` only.

### 3. Supply chain

- Every `uses:` is a 40-hex SHA; three resolve to the tagged commits and one to the annotated tag object for the
  tagged commit (I1). actionlint flags a non-SHA `uses:` only as a style matter, so this was checked by API, not by
  the linter.
- bundletool: `BUNDLETOOL_SHA256` at `release.yml:44` equals the `digest` GitHub publishes for
  `bundletool-all-1.18.3.jar` on the `1.18.3` release (`sha256:a099cfa1543f55593bc2ed16a70a7c67fe54b1747bb7301f37fdfd6d91028e29`,
  32,520,401 bytes), and the file is checked with `sha256sum --check --strict` before `java -jar` (`:179-180`).
  I compared the published digest to the pinned constant; I did not download the jar.
- Gradle wrapper: validated by `setup-gradle`, whose `validate-wrappers` defaults to true at the resolved commit
  (`setup-gradle/action.yml:200-203` at `9c97196`), and the action runs (`:91-96`) before the first `./gradlew`
  (`:132`). No separate wrapper-validation step, and none needed at this version.
- L4 for the SDK script.

### 4. Correctness

- **Both guards' "Verified:" lines.** `release.yml:140` greps
  `^Verified: that certificate matches the pinned upload identity`, which is the start of the single line
  `logger.lifecycle` emits at `build.gradle.kts:480-483`; `:142` greps
  `^Verified: a routing app key is set for this release build`, the message at `:514`. Both are `doLast` lines, so
  they appear only if the task body ran, not merely if the task was listed. The task-header greps (`:134-139`) use
  the same `^> Task :app:$task\b` form ci.yml already runs on GitHub's runner under `--console=plain`
  (`ci.yml:577-588`), so the anchor is known to work there. `set -euo pipefail` (`:129`) makes the `tee` pipeline
  fail the step when Gradle fails.
- **jarsigner and the fingerprint checks.** `:154-157` requires `jarsigner -verify` to exit 0 and print
  `jar verified.`; `:160-173` requires exactly one certificate from `keytool -printcert -jarfile` and an exact
  string match of its SHA-1 and SHA-256 against `EXPECTED_UPLOAD_CERT_SHA1/SHA256` (`:39-40`), which are the
  values Rowan supplied. The SHA-256 is also required to equal `RELEASE_KEYSTORE_CERTIFICATE_SHA256` in the build
  file (`:73-83` against `build.gradle.kts:385-386`); I confirmed the two strings are identical today. So the
  artifact's certificate is compared against the upload key's fingerprint from two committed places that must
  agree, and against the build's own in-process check (`build.gradle.kts:462-474`) which fails the build on any
  other certificate. An unsigned bundle yields zero fingerprints and fails the count (`:166-169`).
- **versionCode = commit count, read from the bundle.** `:176-185` reads `android:versionCode` from the AAB with
  bundletool and compares it to `git rev-list --count HEAD` on the same full checkout (`fetch-depth: 0`, `:69`);
  `:186-188` rejects `UNVERSIONED-*` and `*.dirty` names. This is independent of Gradle, not of the checkout; it
  catches a shallow clone (`resolveBuildIdentity` would have produced code 1), a dirty tree and a provisional name.
  Collision with Play: origin/main is at 3740 commits (`381515c61`), the PR body's figure, which I recounted; Play
  holds 3292 (active) and 3500 (draft) per RECORD -1366; main only gains commits, so every run from main is above
  3500, and Play refuses a reused versionCode, so a rerun of one commit fails at upload rather than replacing.
- **Internal track as a draft.** `tracks: internal`, `status: draft` (`:221-222`); the action validates both
  (section 1). `changesNotSentForReview` is left at its default `false`; for a draft on internal nothing is sent
  for review by this run, which matches the owner's "someone rolls the draft out in Play Console".
- **Concurrency.** I3.
