## Verdict

**Approve with notes.** The artifact is the right file, hashed before anything could change it, and I downloaded it
and got the same hash. The "no R2 write" assertion now bites: the revert run fails on it with a message only that
edit could produce, and the reverted build compiled. The Bogotá `deepEqual` carries all four values; Portland asserts

## 1. The `pmtiles-worker-dist` artifact

**The right file, confirmed.** `npm run build` is `wrangler deploy --outdir dist --dry-run` (`package.json`), which
writes `dist/index.js`; the tests import `../dist/index.js` (`worker.test.mjs:110`); the upload step's path is
`server/pmtiles-worker/dist/index.js` (`ci.yml:719`). So the kept file is the one the tests ran against and the one
the owner pastes into the dashboard.

**The sha256 is logged, and it describes the uploaded file.** The hash step (`ci.yml:681-682`) runs after the build
and before the tests. Nothing between it and the upload writes `dist/`: `npm test` is `node --test` alone
(`package.json`), and the summary step only reads the JUnit XML. On run 39840337744 the log prints
`53bb1a1148a0c36d4e45584a8de556eb8be6162e0eed7de3c20e47b9df1262db  dist/index.js`. I downloaded artifact
`pmtiles-worker-dist` (ID 12452158211) from that run into an empty directory with `gh run download` and hashed it:
the same `53bb1a11…`, 385829 bytes. That is one more pair of eyes than the PR body's, on the same file.

**Only from passing runs, confirmed, and sensible.** The upload step has no `if:` (`ci.yml:716-720`), so it takes
GitHub's default `success()` and is skipped when any earlier step failed. The summary step (`:688-706`) is
`if: always()` but exits non-zero on a failed, skipped or empty test set, so a red test suite also withholds the
bundle. A bundle from a failing run is one the owner should not paste; the build log and JUnit XML are still kept
by the `always()` results artifact (`:707-714`), so nothing diagnostic is lost. Hazel flagged this as a choice; I
agree with it.

**A push to pre-main produces it, inferred from the workflow, not yet seen.** `on.push.branches` includes `pre-main`
(`ci.yml:13`); the `pmtiles-worker` job has no `if:` and the workflow has no `paths` filter (grep of `if:` and
`paths` over the file: only the nine `always()` steps); the concurrency block exempts pre-main from cancellation
(`:43-45`). Two things the owner should know when fetching it:

- A merge commit whose title carries `[skip ci]` skips the whole workflow, push and pull_request alike (GitHub's
  rule). This repo uses that title: `main`'s log shows PR #266 and #267 merged that way. If #378 is merged under it,
  there is no pre-main run and the bundle to download is this PR's own run's (39840337744). That run checks out
  the merge of `cc142246e` into `c9e2e6fe3`, which for every file under `server/pmtiles-worker/` is `cc142246e`
  itself, so it is the same source. Whether two runs of the same source give byte-identical bundles I did not
  verify (the tests-only run predates the hash step, so there is no second hash to compare); the `Total Upload`
  size is the same `376.79 KiB` on both.
- The artifact expires 90 days after the run (`expires_at` 2027-01-20 for this run's, from the artifacts API). It
  is a download window, not a store.

## 3. Coverage lost: the overflow's 404 branch

**Confirmed lost.** `index.ts:241-243` answers 404 when `z` is outside the live build's own zoom range. Before this
PR both z15 tests reached it by accident, because `tiny.pmtiles` stops at z14 (the follow-up, section 2). Now the
live-build fixture's range is 15 to 15 (parsed above), so every z15 request passes the check; and a z16 request
is 404 at `:540`, before the overflow is called, because `OVERFLOW_MAX_ZOOM` is 15 (`:595`). No test can reach
`:241` with this fixture and this fake. Hazel's disclosure is accurate.

**Does it matter? A little, not much.** The branch is the guard for Protomaps' build ceiling changing, the case
the comment at `:586-594` describes as self-correcting. Its answer is a cached 404 (a day, through
`cacheableResponse`) with no live tile read and no R2 write. The behaviour is cheap, documented, and unchanged by
this PR; what is lost is only that a future edit to the overflow could silently turn that 404 into a read, a
write or a 500. Worth one test, not a change before merge.

**The one test that would restore it.** It cannot simply swap the fixture for today's URL: the Worker's header
cache `CACHE` (`index.ts:52`, a pmtiles `ResolvedValueCache`) is module-wide and keyed by the source URL
(`ResolvedValueCache.getHeader` uses `source.getKey()`, and `FetchSource.getKey()` returns the URL; read in
`js/src/index.ts` of protomaps/PMTiles at its default branch today, whose `js/package.json` is 4.5.0, the
locked version), so the live-build header for `…/20261022.pmtiles` is already cached from earlier tests. The
build-URL resolution itself does re-run per test, since `caches.default` is a fresh `FakeCache` in `beforeEach`
(`worker.test.mjs:119`; the revert log's `HEAD` then `GET` confirms it). So:

- give the fetch fake a per-test map from build URL to archive bytes, defaulting to today's URL → `LIVE_BUILD`, with
  `HEAD` answering 200 only for URLs in the map;
- in the new test set the map to yesterday's URL → `ARCHIVE` (`tiny.pmtiles`, z0-14), computed as
  `candidateBuildUrl(1)` does;
- request `/us/15/5303/11553.mvt` (Portland) and compare one object: `status 404`, `bucketPuts []`,
  `overflowReads ['overflow/us/15/5303/11553.mvt']` (the R2 lookup still happens first, `:228`), `fetchCalls`
  `['HEAD …today', 'HEAD …yesterday', 'GET …yesterday']`.

A different URL is a different cache key, so the test sees the z14 header and the 404 branch runs. Reverting the
branch (removing the range check) would then fail on `status` and `bucketPuts` together, since `getZxy` on a z14
archive would return no tile and answer 204, not write; so the message would name the branch. The test's own
claim should be stated as "a live build that does not reach z15 answers 404 and writes nothing", not as a
Protomaps fact.

## 4. The README line, and `src/`

**`src/` is unchanged, confirmed:** `git diff origin/pre-main...origin/worker-deploy-artifact -- server/pmtiles-worker/src`
is empty, and the five changed paths are `ci.yml`, the README, the fixture, its generator and the test file.

**The README line (`README.md:57`) is right about the Worker and wrong about the download.** Against `index.ts`:
z0-8 south of the archive come from `world-south.pmtiles` (`WORLD_FILL_MAX_ZOOM = 8`, `:288`; `worldFillTile`
returns nothing above it, `:347`); z9-14 are 204 (`:576`); z15 wholly south of the archive's `minLat` is 204
(`:535-537`). So the live map there shows world tiles to z8 and nothing from z9 up, z15 included, and "the
overflow no longer runs south of the archive's own bounds" is accurate (to within the one straddling z15 row the
follow-up noted). But the sentence is about **offline downloads**, and an offline download never asks for z0-9:
`OfflineTilePyramidRegionDefinition(OFFLINE_STYLE_URL, bounds, MIN_ZOOM, MAX_ZOOM, density)` with
`MIN_ZOOM = 10.0` and `MAX_ZOOM = 15.0` (`MapLibreOfflineMapRepository.kt:114-120`, `OfflineMapRepository.kt:125-126`;
MapLibre enumerates the definition's own zoom range, `offline_download.cpp:61-76` at android-v13.5.0, read for
the follow-up, not re-read today). A southern download therefore stores empty rows at every zoom it holds and no
world tiles at all. The world tiles to z8 are what the picker and the live map show, which is what makes the
empty download surprising, and that was the point of the follow-up's second Low.

The wording came from the dispatch's item 3 verbatim, which paraphrased the follow-up's two sentences ("a
southern pack is now rows of nothing at every zoom"; "the world fill now makes that area look mapped in the
picker at z8 and below") into one. Hazel reproduced the premise; CLAUDE.md's rule that a dispatch's claims are
premises to check would have caught it, but the dispatch did not ask for the download's zoom range to be read and
I would not expect a coder to go looking. A one-line reword, for whoever touches the README next: "An offline
download south of 15.92°N (the live `us.pmtiles` header's south bound) stores only empty tiles: it asks for
z10-15, and the overflow no longer runs south of the archive's own bounds (the owner's "Stop it", dispatch
2026-10-22-01 Amendment 4). The live map there shows world tiles to z8 and nothing from z9 up, so the picker
looks mapped where a download yields nothing."

"15.92°N" is the live `us.json`'s south bound as read for the first review, not re-read today.
