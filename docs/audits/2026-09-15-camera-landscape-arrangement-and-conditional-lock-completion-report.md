# The camera's window pins where it is, and a landscape window gets a landscape arrangement

**Date:** 2026-09-15 · **Branch:** `claude/new-session-vto65i` (PR #102) · **Base for the reads:** `51882cb`, verified against the remote before reading.

**Finding, from the device check on `51882cb`, step 3.4 — the owner's, and it supersedes the earlier orientation-lock decisions.** Two constraints have to hold together: nothing in the camera layout moves while the camera is open (no reflow, no re-layout, no rotation animation of the app), and in a landscape window the shutter is on the right edge, never along the bottom — a hard UX constraint, not a trade to accept. The forced-portrait lock of `3591df2` satisfies the first by paying a flip on open from landscape and cannot satisfy the second at all; the first `LOCKED` version of `8d9761c` kept a landscape window but laid the portrait controls into it, which is the case 2.4 that got it replaced. Neither had a landscape arrangement. A design change, not a bug fix, and read whole before building.

**One-paragraph outcome.** The window lock is conditional on "Lock camera to portrait": off, `SCREEN_ORIENTATION_LOCKED`, the window pinned to whatever it already was when the camera opened, so nothing is forced and there is no flip; on, `SCREEN_ORIENTATION_PORTRAIT` as before, where the one flip from landscape is the point of the setting. The dialog chooses one of two arrangements once at open, from the setting and the window's shape, and holds it: portrait is exactly what existed, with the controls turning in place by sensor minus display; landscape puts the shutter on the right edge, vertically centred, the count beside it, Done top-left, all upright, with `rotateWithDevice` not applied. Capture, the gate, the reapply, scrub, sweep, persist and `configChanges` are untouched.

## §1 — Verification, before anything was built

**1. `LOCKED` pins the current orientation at the moment the effect runs, and nothing else in the open path can move the window afterwards.** Android defines `SCREEN_ORIENTATION_LOCKED` as locking the orientation to its current rotation, whatever that is, when the request is made; that it does so was seen on this device in step 2 of the window-lock check, when a camera opened while held landscape kept a landscape window (`670e182`, case 2.4). The request is made in `LockWindowOrientation`'s `DisposableEffect`, which runs once when the dialog enters composition (`InAppCameraDialog.kt`, the `LockWindowOrientation(lockToPortrait)` call, before the `Dialog`). Nothing else in the app sets `requestedOrientation` — grep of `app/src/main` this session finds the one write, in `WindowOrientationLock.kt`. `configChanges` (`AndroidManifest.xml:160`, `orientation|screenSize|screenLayout|keyboardHidden`) keeps a rotation from recreating the Activity, so the effect is not re-run by a rotation. The setting cannot change while the dialog covers Settings (`AvailabilityViewModel.onLockCameraToPortraitChanged`'s own doc). So after the effect runs, the window can move only where the platform ignores the request (Android 16 on screens 600dp and wider for this API target, or an OEM), which the lock's doc already records as device-decided. One edge stated rather than assumed: the configuration read that chooses the arrangement (next item) happens in the same composition pass as the effect is scheduled, and the effect runs after that pass; a rotation landing in the microseconds between them would pin the new shape under the old arrangement. Not observed, not defended against, named.

**2. How the arrangement is chosen, and why the value is stable for the life of the dialog.** `InAppCameraDialog` reads `LocalConfiguration.current.orientation == ORIENTATION_LANDSCAPE` in its first composition and passes it, with the setting, to `cameraArrangement(lockToPortrait, windowIsLandscape)` inside `remember(lockToPortrait)` — **no configuration key**, on purpose: if the window ever did turn, `LocalConfiguration` would recompose the dialog but the remembered arrangement would not change, which is the "never reflowed" half of the requirement, and the revert that drops the `remember` fails the held-arrangement test (§3). The value read is the Activity's configuration as Compose provides it, which is the window's shape at open. It is stable because of the lock: with the setting off, `LOCKED` pins exactly that shape for as long as the dialog lives; with the setting on, the window is about to be forced portrait, so the shape at open is *not* used — the function returns portrait for the setting-on column regardless, because reading the pre-flip landscape would hold the wrong answer. Not derived from `WindowWidthClass`, from the display's rotation, or from anything that reports the window's *current* state after open. On an Activity recreation while open (a night-mode toggle), the dialog is composed fresh by the ViewModel-retained flag and reads the new window's shape then, which is right.

**3. The capture path is untouched.** `CameraXCaptureSession.kt` is not in this diff. `capture()` reads the gated `deviceRotation` from the sensor listener, sets `targetRotation`, and after the save reapplies the intended tag (`IntendedOrientation.kt`, also not in this diff); confirmed correct on device in all four combinations on `51882cb`. The only display read left in that path is the logged fallback for a shot with no sensor reading; under a landscape `LOCKED` window it reads `ROTATION_90`, which is the right fallback for that window. The dialog's new parameter reaches the session nowhere: `InAppCameraHost.kt:52` builds the session from the same `lockToPortrait` it always did, and `:53–60` now passes the same value to the dialog beside it.

**4. Whether the width-class subtree swap can fire with a landscape-locked window, and what the retained flag does.** `currentWindowWidthClass()` (`ui/adaptive/WindowWidthClass.kt:39–46`) buckets `LocalConfiguration.current.screenWidthDp`; on a phone a landscape window is `MEDIUM` and a portrait one `COMPACT`, so the class at open is `MEDIUM` and the swap would fire only if the window turned to portrait while the camera is open. With `LOCKED` holding the window it cannot on a phone; with the setting on the window is forced portrait *before* the dialog's content lays out, and stays there. Where the lock is ignored (large screens on Android 16), the swap can fire — and it does not matter to the camera: `InAppCameraHost` is composed once, above the width-class branch (`AvailabilityScreen.kt:2080–2089`, the branch at `:2091`), so the dialog, its session and its remembered arrangement survive the branch swapping underneath them; that was the second mechanism of the rotation bug fixed on `7a1e5be` and is unchanged. The ViewModel-retained flag (`InAppCameraViewModel`) covers the other mechanism, Activity recreation, which `configChanges` already prevents for a rotation. It holds, by three independent means, and this is stated from the code rather than assumed.

## §2 — What was built

- **`WindowOrientationLock.kt`:** `LockWindowOrientation(lockToPortrait)` sets `windowLockFor(lockToPortrait)`, a pure function: `PORTRAIT` on, `LOCKED` off. Restore is the same two lines. The doc's "PORTRAIT, after LOCKED was tried" section is replaced with the conditional design and why the first `LOCKED` was rejected — the window was right, the layout was not.
- **`ui/log/CameraArrangement.kt`, new:** `enum CameraArrangement { Portrait, Landscape }` and `cameraArrangement(lockToPortrait, windowIsLandscape)`, landscape only when the setting is off and the window is landscape. Pure.
- **`InAppCameraDialog.kt`:** a `lockToPortrait` parameter; the lock call takes it; the arrangement is chosen as in §1.2; the controls box is a `when` over the arrangement. **Portrait branch: the previous controls block, byte for byte in layout terms** — Done top-left with `rotateWithDevice`, the bottom `Column` of error, count and shutter, each with `rotateWithDevice`. The one textual change to it is that the shutter's `onClick` lambda became a local `onShutter` shared by both branches (the double-tap guard, the capture, the cleanup and the error are the same lines moved). **Landscape branch:** Done top-left, upright; a `Row` at `CenterEnd` holding a right-aligned `Column` of error and count beside the shutter, upright; no `rotateWithDevice` anywhere in it.
- **`InAppCameraHost.kt:53–60`:** passes `lockToPortrait` to the dialog. The four test call sites of the dialog pass it too (the dialog test's `Subject` passes `false`; the host and screen tests pass what the slot received).
- **Not changed, per the constraints:** `IntendedOrientation.kt`, `effectiveDeviceRotation`, `PhotoMetadataScrub.kt`, the sweep, persist, `AndroidManifest.xml`, the portrait arrangement, `RotateWithDevice.kt`; no screen other than the camera dialog gained a landscape layout.
