## Decisions made

### §5.1 — Rebase or reapply

**Reapply.** Take `main`, port PR #26's feature across as fresh commits using its branch as
reference, rather than replaying its 10 original commits across 51 commits of drift. Original
commit messages are lost; the branch (`claude/plan-implementation-rjzmkr`) stays available as
reference either way.

### §5.2 — `OfflineRegionEntity`'s relational design

**Design it now**, not deferred to a later migration. `MushroomLogEntryEntity` gets a foreign
key to `offline_regions`, with its index, as part of the same migration that creates the table
(currently scoped as `MIGRATION_5_6` per the renumbering in the source pulse — see that
document for why `version = 5` collides with `main`'s existing tracks/waypoints migration).

**Delete behavior, in full — a two-step flow, not a single rule:**

1. **Block by default.** A region delete is refused while any `MushroomLogEntryEntity` still
   references it. The block names the specific referencing entries (not a generic "in use"
   message) — the error-presentation spec's "tell the user what's actually true" rule applies
   here as much as to a caught exception.
2. **The user has two ways past the block, both explicit:**
   - Edit or remove the referencing log entries directly, which clears the reference and lets
     the delete proceed normally.
   - Or, proceed with deletion anyway: each referencing entry's own small tile footprint
     (**~1m radius — the owner's own sizing: "the radius in the mushroom journal doesn't need
     to be large, 1m per entry is probably more than enough"**) is captured into its own
     independent `OfflineRegionEntity` first, so the entry keeps local map context after the
     big region is freed, and only then does the region delete proceed.

Rejected explicitly: cascade-deleting the log entry when its region is deleted ("almost
certainly wrong," per the source pulse) and silently nulling the reference (would let a region
disappear out from under an entry with no record of what was lost).

### New workstream — entry-level tile capture

This did not exist in the original five workstreams. The owner scoped it in now, not deferred,
specifically so the design wouldn't go stale: *"my call. I want to make sure this gets done
while the idea is fresh and it doesn't go stale in memory."*

**Capture mechanism: a fresh small-radius download**, reusing
`MapLibreOfflineMapRepository.download()` unchanged, called with a ~1m-radius region instead of
a user-picked one. Confirmed feasible without any new verification — it's the exact same
`OfflineManager.createOfflineRegion` path the existing per-region download already uses, just a
smaller `Region`.

**Explicitly not chosen:** extracting the already-cached tiles for that point out of the big
region's store before it's wiped. That would avoid a redundant network fetch, but nothing in
this codebase has verified that MapLibre's `OfflineManager`/`OfflineRegion` API exposes
tile-level extraction (its own doc comments describe everything in terms of *regions* —
bounds and zoom — not raw tile access) — this project's own discipline is to check such a claim
via `javap` against the pinned SDK artifact before relying on it (see
`MapLibreOfflineMapRepository.kt`'s and `MapPreferencesRepository`'s doc comments for the
precedent), and that check has not been done. The fresh-download path avoids needing it.

### §5.3 — Is a failed offline-map download belief-changing?

**Yes.** Same shape as the track-recording case: a user who believes they have offline coverage
for an area they're about to lose signal in is carrying a false assumption into the field.
Gets a message phrased as state (like `startRecordingErrorMessage`'s Toast, or
`waypointsErrorMessage`'s inline error-color render), not a plain empty state. This determines
the treatment for workstream §2.2 (error-presentation compliance) in the source pulse: the
distinction it flagged as undecided — "a failed download is belief-changing... a failed region
*list* load probably is not" — is now decided on the download side; the list-load side was not
revisited and remains as the source pulse left it (probably not belief-changing, not confirmed
either way).

## What is still open

These were not asked, and are not decided by anything above — flagging them now rather than
letting them surface mid-implementation as a silent judgment call:

- **How does a log entry acquire its region reference in the first place?** Automatically (any
  entry created while inside a downloaded region's coverage links to it) or by explicit user
  choice? This affects both the migration (does it need to backfill existing entries against
  existing regions?) and the UI (does anything need to expose the link before delete-time?).
- **Is the auto-capture-then-delete flow a single atomic user action**, or does it surface as a
  distinct confirmation step ("this will download N small regions, then delete this one")
  before proceeding? `OfflineRegionsSection`'s existing `pendingDeleteRegion` confirmation
  dialog (PR #26) is the natural place to extend, but the exact UI shape wasn't specified.
- **Failure handling if a capture download fails partway** — does the whole region-delete abort
  (leaving the big region intact, matching "no partial state" precedent elsewhere in this
  codebase), or does it proceed for the entries that succeeded and report the rest as failed?
- **The region-list-load failure's belief-changing status**, noted above, was not revisited.
