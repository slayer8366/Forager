**Run-time form (the "web engine only" question).** The matching is on parsed RGB, not text, and the parser reads
`#rrggbb[aa]`, `rgb()`/`rgba()` strings with decimal channels (rounded by `toChannel`), and `["rgb"|"rgba", r, g, b(, a)]`
arrays (`NightColour.kt:327-352, 291-304`). From my memory of maplibre-native core (not read here): `Color::stringify`
gives `rgba(r,g,b,a)` with 0-255 channels, and a colour literal inside an expression serialises as `["rgba", r, g, b, a]`
with doubles; both forms are read, and a float like `169.00001` rounds to 169, so the exception matches. That is
inferred; what is **observed** is only that every colour property in the v2 file (103) parses to `Recoloured` with
none `Left` (`OfflineNightRecolourTest`). Nothing here works only in the web engine by construction: the renders'
night was drawn by a scratch script mirroring the Kotlin, not by the browser's own machinery. The device-only items
are the three in M1.

### 4. The pattern repaint at night, and the night/day switch

- The repaint runs inside the `setStyle` callback (`MapStyleReload.kt:117-129`), after `disableSymbolFade` and before
  any overlay is added, for every style load whose source `usesStreetSprite` and whose request is night. The effect is
  keyed on `nightMode` and `nightModeLoaded` (`:63`), so night→day and day→night each call `setStyle` again from the
  URI, which discards every image with the style; a day load repaints nothing (the style comes fresh), a night load
  repaints from the fresh day images. There is no in-place toggle that could paint twice or leave a day image behind.
- The -1513 fallback relaunches the same effect (`ownStreet` is a key), and the `StreetWithTopoOver` builder loads the
  same URI (`StreetStyleApply.kt:43`), so it takes the same repaint; `hideStreetLabelsUnderTopo` caps every
  `SymbolLayer`, so the new `pois_area_names` layer is covered under the topo too (`:56-63`).
- A `fill-pattern` layer has no `fill-color`, so the paint walk skips it (`value.isNull -> continue`,
  `OfflineNightRecolourApply.kt:35`). Confirmed in the file: `landuse_forest_glyphs` and `landuse_wetland_tufts` carry
  only `fill-pattern`.
- Whether Native re-lays-out pattern tiles after `addImage` under an existing name is M1(b). The icons already go
  through this path and symbols and patterns share the image manager, so I expect it to work, but that expectation has
  never been checked on a phone either (M1).
