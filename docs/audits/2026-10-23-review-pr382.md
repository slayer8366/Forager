**The messages arrive with those prefixes.** `RoutingEngine.logException` (`:812`) stores `t.getMessage()` for a
`RuntimeException` and `t.toString()` otherwise. Every throw above is an `IllegalArgumentException` or
`RuntimeException` except the `IOException`s in `PhysicalFile` and `OsmFile`, and those pass through
`NodesCache.getSegmentFor`'s `catch (IOException re) { throw new RuntimeException(re.getMessage()); }` (`:197-198`),
which keeps the message and drops the class name. So the prefixes are reachable as written, not only through
"error reading datafile". The same line is why an `EOFException` with no message (a file cut inside its 200-byte
header) becomes a `RuntimeException(null)` and a null error message, which is the case `RoutingDataFolder` exists
for and the one revert 2 proves.

**Unrecognised strings** fall to `EngineFailed` with the message kept (`:38`) and are logged at
`BRouterTrailRouter.kt:70`; a null message with fewer than two points is logged at `:78`; anything thrown rather
than reported is logged at `:63`. Three real BRouter messages land there by design: `memory limit reached`
(`:2028`), `… timeout after N seconds` (`:1982`), and `operation killed by thread-priority-watchdog` (`:1976`,
unreachable here, see M1).

**The header pre-check, false refusals.** `RoutingDataFolder.check` refuses in three ways, and I asked of each
whether BRouter would have routed:

- *No folder, or no `.rd5`:* BRouter throws at `NodesCache.java:83` or fails the first file access. No route either way.
- *An end whose five-degree square has no file:* `preloadPosition` (`NodesCache.java:327-332`) resets the
  first-access flag and loads the end's own segment first; `fileForSegment` (`:347-390`) sets
  `first_file_access_failed` when that file is absent (`:384-386`; the secondary dir, read from a
  `storageconfig.txt` the app never writes, is null), so BRouter throws "datafile … not found" at `:331`. The
  pre-check changes the kind from `DataMissing` to `EndOutsideData`, which is the truer one for a region that has
  data elsewhere, and never the outcome. Neighbouring-cell loads across a square edge with no file do not set the
  flag, since it is set only on the first access (`:384`), so an end near a stored square's edge is not refused.
- *A header that will not open:* `PhysicalFile(f, DataBuffers(), -1, -1)` (`RoutingDataFolder.kt:48`) is the
  constructor BRouter's own integrity checker uses (`PhysicalFile.java:71`), with the lookup-version check off,
  which the engine then makes itself. An old-format file with no footer returns early (`:115`) and passes. The route
  cutter's CI proof runs that same checker on every cut (`format.test.mjs:89-94` through `brouter-cli.mjs:61-64`),
  so the Worker's cut files are known to pass the pre-check. `DataBuffers()` gives a 65,636-byte io buffer
  (`DataBuffers.java:21`), above the 200 and 113 bytes read.

The only way the pre-check refuses what the engine might have routed is L3: a bad file for a square the search
would not have touched.

`use_dynamic_range` reaches the profile through `profile:` params into `rc.keyValues`
(`RoutingParamCollector.java:241-243`), read as the global at `RoutingContext.java:200`. I did not trace the

## 3. Threading and the limit

`route` is `withContext(dispatcher) { ONE_ROUTE_AT_A_TIME.withLock { routeNow(…) } }` (`:51-54`), a static
`Mutex` (`:125`).

- **Deadlock:** the mutex is not reentrant and `route` never re-enters; inside it the only other locks are
  `ProfileCache`'s `static synchronized` methods (`ProfileCache.java:33`, `:126`) and the engine's own
  `synchronized (openSet)`, none of which is ever held while waiting on the mutex. No lock-order risk.
- **Starvation:** kotlinx's `Mutex` grants in arrival order, and waiters suspend without holding a thread. A waiter
  waits for the running route's full duration (see M1 for the cancelled case). `ProfileCache.parseProfile` marks
  a slot busy and `doRouting`'s `finally` releases it (`:332`); if a constructor throw ever left it busy, the next
  parse overwrites the one-slot cache (`:66`, `:103`) rather than blocking.
- **Off the caller's thread:** `Dispatchers.Default` by default; the dispatcher test (`:171-180`) proves the work
  waits for it and revert 4 proves the test bites. Blocking file reads on a CPU dispatcher is a judgement call;
  BRouter is CPU-bound with small reads, so I would leave it.
- **The 30 s:** passed to `doRun` (`:106`), stored at `RoutingEngine.java:203`, enforced by BRouter at
  `:1979-1983` on every open-set pop, from one `startTime` (`:201`). Island checks (`:949-968`, 500 nodes) and both
  passes run under that one clock. It is a bound on the search, not on `route()`: L1 and M1.

## 8. The open -1547 point

The costlier detour is not detectable from what this interface carries today, and the interface leaves room to
add it without breaking the callers that exist (none in production) or the shape of the ones to come:

- `TrailRoute` is a data class; a field with a default (`leavesStoredArea: Boolean = false`, or an edge-touch
  measure) is source-compatible for every caller.
- `TrailRouteFailure` is sealed; a new kind (`DetourSuspected`) compiles until a caller writes an exhaustive `when`,
  and then it breaks at compile time, which is the right place.
- `route()`'s inputs are the limit: detection needs something the folder does not carry, the region's rectangle
  or the margin cells, since a detour stays inside the cut by definition and the phone never sees the route the
  full data would give. That means either a parameter (one implementation to update) or a richer `routeData`
  type, or the caller comparing `points` against the region's bounds itself, which needs no interface change.

So: room, yes; but the owner's design question (what counts as "leaving the area" when the detour is inside it,
and what the phone can know) comes before any of those, as the PR says.
