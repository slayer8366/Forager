## What the next dispatch needs to know (from the two most recent pulses)

These are the load-bearing findings from the C/D and Log & Location pulses that any dispatch
written against `docs/plans/pr26-rework.md`'s (now-superseded) C/D section needs to account for —
not reproduced in full here; see the pulse reports themselves
(`/tmp/.../scratchpad/pulse reports/workstream-cd-rescoping-pulse.md` and
`log-location-rework-scoping-pulse.md` as delivered to the owner this session — **these live only
in that scratchpad and the chat transcript, not in this repo**; if they matter for a future
session that isn't this one, they should be committed under `docs/plans/` or `docs/audits/` before
this container is reclaimed, per CLAUDE.md's own "an artifact that exists only in a session
transcript is not recorded" rule. This handoff does not do that copying itself, to avoid
duplicating a large, still-possibly-revised document — flagging the risk instead.):

- **Five long-press location sites exist, not three or four** — `JournalTab.kt`'s own picker
  (`LogEntryLocationPicker`) is easy to miss since it's nowhere near the other four in
  `AvailabilityScreen.kt`, and it's the *only* one with a real confirm/cancel step today.
- **Nothing in this codebase renders a draggable or centered marker anywhere.** Marker rendering
  is exclusively "replace the whole `GeoJsonSource` on state change" — a centered-marker picker is
  mechanically simplest as a fixed Compose overlay icon with the map panning underneath, not a
  MapLibre marker/drag API this codebase has no plumbing for. Reported as a feasibility note, not
  chosen as the design.
- **`foundAt`'s ripple is much smaller than assumed**: zero reads in map rendering, DBSCAN
  clustering, or distance calculation — those all operate on `Sighting`/`ForagingArea`, never
  `MushroomLogEntry`. Real ripple: three display-string sites, one Room migration
  (`MIGRATION_6_7` — `lat`/`lng` are non-null `Double` columns today, current DB version is 6),
  and 13 `.draft(` construction call sites.
- **A single `offlineRegionId: Long?` column cannot represent "capture owed" as distinct from
  "not applicable"** — both currently collapse onto `null`. At least one more signal (column,
  enum, or table) is required; not designed here.
- **`MushroomLogViewModel` and `AvailabilityViewModel` remain fully isolated** — confirmed twice
  now, across both pulses. Both capture-on-location-set and entry-delete capture-cleanup need the
  same currently-nonexistent bridge between the mushroom-log domain and `OfflineMapRepository`.
  Whoever dispatches either piece first should decide where that bridge lives (three shapes
  reported in the pulse: a new use case in `AppContainer`, a repository-level dependency, or a
  ViewModel-level one) — an independent decision made twice is this rework's recurring failure
  mode (see `CLAUDE.md`'s own schema-version-collision precedent).
- **Photo cleanup on entry-delete is fully independent and could ship today** — every type it
  needs already exists (`PhotoStore.delete()`, `LogPhoto.relativePath`, the entry's photo list
  already in hand at `MushroomLogViewModel.onDeleteEntry`). Not blocked on anything else in either
  pulse.
- **An ambiguity in the owner's decisions themselves, not resolved by either pulse**: decision #2
  ("adding an entry from the journal goes to the entry page") names the journal's own "+" — the
  map tab's separate "Log a find" long-press option is a second, textually distinct entry point
  the decision doesn't address. Needs an explicit owner call before a dispatch can say what happens
  to it.
- **`docs/plans/journal-trips-and-offline-regions.md` is cited by path in three shipped source
  files** (`MapLibreOfflineMapRepository.kt`, `MapLibreStorage.kt`, `domain/OfflineMapRepository.kt`)
  **but does not exist anywhere on `main` or this branch** — only on PR #26, never ported. Anyone
  following those citations today finds nothing.
