## B. Duplication and drift

**5.** Concrete duplicated logic:
- Decimal-degree coordinate formatting `"%.4f".format(lat), "%.4f".format(lng)` appears independently at 9 sites: `ui/log/LogEntryReportScreen.kt:131`, `ui/log/LogEntryListScreen.kt:91`, `ui/log/JournalTab.kt:195`, `ui/log/LogEntryDetailScreen.kt:102`, `ui/availability/AvailabilityScreen.kt:1628`, `:1706-1707`, `:2050`, `:3780`, `:3842`. No shared formatting function exists; each site re-writes the same two `.format()` calls.
- Three independent live subscriptions to the same GPS stream, each deriving its own state from it (detailed under Q9 below): `ui/track/TrackRecordingViewModel.kt:168`, `ui/availability/AvailabilityViewModel.kt:90`, `service/TrackRecordingService.kt:101`, all `locationTracker.fixes.collect { fix -> ... }`.

**6.** Multiple ways of formatting the same kind of value:
- **Decimal coordinates**: labeled (`"Lat. 45.5231 Long. -122.6414"`, `AvailabilityScreen.kt:3434`) in the compass strip vs. unlabeled comma-pair (`"45.5231, -122.6414"`) everywhere else — `PlannedTripRow` (`:3780`), `RecentSearchRow` (implied by `:2050`), the offline-map picker (`:1706`), and all four mushroom-log screens listed in Q5. The compass strip's own doc comment (`:3427-3429`) explains this as a deliberate distinction ("that row sits next to a named trip... this strip has no such context"), so it's recorded intent, not silent drift — but it is two different presentations of the identical underlying `LatLng` value depending on which screen renders it.
- **Distance**: `ui/availability/DistanceUnit.kt` defines a single `formatDistanceKm(radiusKm: Int, unit: DistanceUnit)` that every other distance display in the app is documented to route through ("Distance values stay kilometers everywhere else in this app, always... only `formatDistanceKm`... converts the label," `DistanceUnit.kt:11-14`). But `returnToStartStripText` (`AvailabilityScreen.kt:3366-3378`) formats the return-to-vehicle distance independently and never calls `formatDistanceKm` or takes a `DistanceUnit` parameter:
```kotlin
val distanceText = if (info.distanceMeters < 1000) {
    "${info.distanceMeters.roundToInt()} m"
} else {
    "${"%.1f".format(info.distanceMeters / 1000)} km"
}
```
  This one distance display is hardcoded to km/m regardless of the user's selected `DistanceUnit` (miles), unlike every display that goes through `formatDistanceKm`.

**7.** Hardcoded values appearing in more than one place:
- `48.dp` — appears as `.heightIn(min = 48.dp)` at `AvailabilityScreen.kt:1258, 1323, 1518, 1535`, and separately as two *named* constants with the same literal value: `MIN_TOUCH_TARGET = 48.dp` (`:1757`) and `MAP_ICON_STACK_DIAMETER = 48.dp` (`:2842`) — five independent occurrences of the same dimension, two of them named differently for what may or may not be the same underlying constraint (min-touch-target vs. an unrelated icon diameter that happens to match it).
- `18.dp` icon size — unnamed literal at `:1100, 2075, 2249, 3301, 4097` (5 sites).
- `15` (km) — the default `radiusKm` in `AvailabilityUiState.kt:21` and the default `offlineMapRadiusKm` in `AvailabilityUiState.kt:121` are both hardcoded to the literal `15`, for two conceptually distinct radii (search radius vs. offline-download radius).
- A `Spacing` object (`AvailabilityScreen.kt:264-275`, values 4/8/12/16.dp) is used 92 times in the same file, but 33 raw `.dp` literals still coexist in that file outside `Spacing`, including several of the above.

## Highest-signal findings

1. **Three error-state fields with real, user-facing message text are never rendered anywhere in the UI** — `MushroomLogUiState.loadErrorMessage`/`saveErrorMessage`, `TrackRecordingUiState.startRecordingErrorMessage`/`waypointsErrorMessage`, and `AvailabilityUiState.conditionsErrorMessage` — because this is a genuine, currently-live silent-failure gap (not a hypothetical), confirmed by exhaustive grep with zero read sites outside each field's own ViewModel and state-class file.
2. **`AvailabilityScreen.kt` is 4243 lines with a 672-line, 67-parameter root composable**, because both numbers are extreme outliers against the rest of the codebase (next-largest file: 802 lines; next-largest parameter list: 22) and concentrate nearly a third of all production Kotlin in one file.
3. **The device's live GPS fix is independently subscribed to and re-derived in three separate places** (`TrackRecordingViewModel`, `AvailabilityViewModel`, `TrackRecordingService`), because this is the exact "same fact represented in more than one place" risk Q9 asks about, with three real listener registrations rather than a documented two.
4. **The reported "555 passing tests" is partly inherited-and-re-executed rather than 555 distinct assertions (525 raw `@Test` annotations, +30 from one base class run across three Robolectric device configs), and the dispatch's flagged risk pattern (a test asserting a constant against a self-referential range) recurs in at least two more files** (`MotionTokensTest`, in addition to `MotionPrecedenceTest`), because this directly confirms the dispatch's stated concern that the pattern "recurs elsewhere."
5. **`returnToStartStripText` hardcodes km/m formatting, bypassing the app's own `DistanceUnit`/`formatDistanceKm` mechanism that every other distance display is documented to route through**, because it's a concrete, single-line-quotable instance of the "multiple ways of formatting the same value" pattern, on a safety-adjacent feature (return-to-vehicle guidance).
