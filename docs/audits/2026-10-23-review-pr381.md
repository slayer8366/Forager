### M1, in numbers

A five-degree square at 45°N is about 556 km north to south and 393 km east to west. At the 50 km side limit
(`area.ts:13`) that is 12 by 8, 96 areas; an interior area is one `area.json` and one file, two requests, so
about 200 requests a square and about 37,000 for the 187 squares, less for the many small ones. At 600 a minute
that is about an hour from one Cloudflare location, and "approximate and apply separately in each Cloudflare
location" (the binding's page, section 4) means a second location is a second hour in parallel. The cuts are the
cells byte for byte (`cut.ts:6-7`), so they reassemble the full data. The owner's choice already says "a
deterrent, not secrecy" and the data is ODbL OpenStreetMap; what needs fixing is only the sentence, which the
owner could otherwise rely on. Suggested wording: "slows a copied key to about an hour per location for the whole
map, and makes it visible".

### M2, the probe

`area.ts:squaresFor` grows the rectangle by 1/32 degree in floating point and floors to five degrees;
`cells.ts:cellOfLon/cellOfLat` rounds to a microdegree first (`micro`, `cells.ts:39-41`). The two agree unless an
edge lies within a microdegree of a five-degree line, which needs seven or more fractional digits. The probe
(a Python port of the two decisions, 20,166 areas: a sweep of every 1/32 step across 105°W and 40°N at six
decimals with ±1 and ±2 microdegree offsets, 20,000 random six-decimal boxes near 5-degree lines, and thirteen
seven-decimal cases) found 0 disagreements at six decimals and 4 at seven. Two of the four are the harmless
direction (a margin column in the neighbouring square is wanted by the cells but the square is not listed, so that
one column of margin is not served). Two are the other: `squaresFor` lists a square that `wantedCells` says the
rectangle does not overlap (for example `west=-104.9687504`, which lists `W110_N35` and `W110_N40`), so
`cutRd5` throws `RangeError` at `cut.ts:51` (the throw itself is `cells.ts:59`), `cutFailure` rethrows anything it does not name
(`handler.ts:146`), and the fetch handler rejects: the client sees Cloudflare's own error page, not a status and
`{"error"}`. The app will never send such an edge by accident at six decimals, and an abuser gains nothing but a
500. The fix is on the contract side: the app formats each edge to six decimals (about 11 cm) and the contract
says so; optionally `DECIMAL` tightens to six fractional digits so a non-conforming client gets a 400 rather than
an exception. The number-format gap is the Medium; the disagreement behind it is Low on its own.

## 1. Access and limits

**Can a route answer without the key?** No. Every path under `/routing/` enters `routingResponse`
(`index.ts:457-460`), which runs in this order: the fail-closed check (`handler.ts:231-239`), the per-address
limiter (`:246`), the key compare (`:249`), the key limiter (`:252`), and only then path dispatch (`:256-260`). The
manifest is never served: `/routing/manifest.json` is 403 without a key and 404 `not_found` with one
(`routing.test.mjs:237-240`); Aspen's record shows the live Worker already answering 404 for it, and nothing in
this PR adds a reader for `routing/` keys outside the handler. The tile parsers cannot reach them either: `tilePath`
appends `.pmtiles` to the name (`shared.ts:6-11`) and `assetKeyFor` prefixes `fonts/` or `sprites/`
(`index.ts:398-412`).

**Caching.** `cache.match` is called at `handler.ts:117` (inside `cutFor`) and `:208` (the file route), both
reachable only through `routingResponse` after the key compare. The cached copy carries
`Cache-Control: public, max-age=2592000` (`:47`, `:125`), which the Cache API needs in order to store it; the copy
sent to the client carries `no-store` (`:203`), so no shared proxy between phone and edge keeps a cut. Cloudflare's
CDN does not cache a Worker's own responses on its own (the "how the cache works" page: caching a Worker's responses
is explicit, "through `cache.put()`"). Every error response is `no-store` (`:54`). The test at
`routing.test.mjs:105-111` asserts a wrong key gets 403 for a file the cache already holds, and R1 (section 3)
shows that assertion biting. The one forward risk is L3, for the custom-domain move.

**Order of the checks.** Right. Address first, so a keyless or wrong-key flood from one address is counted and
stops at 30 a minute (`routing.test.mjs:113-124`: "the key is not even checked"); key second; key limiter last, so
wrong-key requests never drain the shared 600. The key compare hashes both sides and XORs the digests
(`handler.ts:68-74`), so its time does not depend on how much of a wrong key matched.

**Fail-closed.** `!env.ROUTING_APP_KEY || !env.ROUTING_IP_LIMITER || !env.ROUTING_KEY_LIMITER` → 503
`not_configured`, before any R2 read (`handler.ts:231-239`; test `:134-142` removes each of the three in turn and
asserts no R2 read). An empty-string secret is also refused. It is logged with `console.error`, which under this
Worker's configuration goes nowhere persistent (L1); the 503 body is what a deploy check sees.

## 2. Correctness against the real manifest

The real `routing/manifest.json` (Aspen's copy, sha256 `d2ff0d6b…` per the upload record): `run_id`
`usca-20261021T111429Z`, `osm_timestamp` `2026-10-17T20:20:51Z`, `osm_sequence` a string, 187 files. Every path
matches `usca-20261021T111429Z/segments4/[EW]\d+_[NS]\d+\.rd5` (checked by regex over all 187; none fail); sizes
are positive integers from 4,440 to 98,155,814; every `sha256` is 64 hex characters.

- `parseManifest` (`manifest.ts:35-59`): `run_id` passes `RUN_ID`; the prefix check uses the manifest's own
  `run_id` (`:46`), so a manifest whose files sit under another run is refused rather than followed;

  does not matter; the manifest's `sha256` is not read, which Hazel's report explains (a whole-file hash per cut
  would be 55 to 220 MB of reads; here the largest real square is 98 MB, not 55). The cutter checks the header
  and tile indexes against the file's own CRCs; the Worker checks every ranged read's object size against the
  manifest (`handler.ts:100-102`) and its length (`:104`); cells carry their own checksums for BRouter.
- The verify-first case assumed 55 MB squares. The real maximum is 98 MB. The cutter reads by range, so the count
  of reads (47 worst case, Hazel's table) is what the subrequest limit sees, not the size; the premise is off, the
  conclusion stands.
- `FILE_PATH` (`handler.ts:49`) accepts the real run id (`[^/]+`) and `isRunId` (`:193`) the same regex as the
  manifest's.
- `squaresFor` (`area.ts:81-93`) on the two-square fixture rectangle gives `W110_N35, W110_N40`, which I
  recomputed by hand: west −105.341 floors to −110, east −105.249 stays below −105; south 39.954 floors to 35,
  north 40.046 includes 40. The naming matches BRouter's (`W5_N45`-style; `squareName`, `area.ts:70-74`).
- `run_superseded` (`handler.ts:214-218`): a file URL from an old run, not in the cache, answers 409 with the
  current `run_id`; a cached old-run cut is served from cache first (`:208-210`), which is correct because the run
  id in the URL means those bytes never change, and old run folders stay on R2 (-1553). The cache key is the
  canonical file URL on the request's host with the run id in its path (`:198`), so a new run never matches an old
  entry (R3 in section 3 proves the test depends on that).
- "Serve what exists" (`e3d72cac9`): `present`/`missing` split at `handler.ts:163-164`; 404 only when nothing is
  present (`:165-167`); `missing` always in the body (`:184`), empty when none. The test at `routing.test.mjs:151-169`

## 4. The rate-limit numbers and the binding

**The numbers.** One download is one `area.json` plus at most four files, five requests; three tries is fifteen;
two areas back to back is thirty (`wrangler.toml:39-43`). That is a reasonable floor for one phone. The owner
confirmed both numbers (addendum 2). Two things to know when reading them: L2 (IPv6 rotation and IPv4 carrier
NAT pull in opposite directions; at tester scale neither bites), and M1 (600 a minute slows a copied key, it does not
stop one). The configuration is as the binding's page documents it: `[[ratelimits]]` with `name`, `namespace_id`
("a string containing a positive integer that uniquely defines this rate limiting namespace") and `simple` with
`limit` and `period` ("must be either `10` or `60`"); `limit({ key })` resolves to `{ success }`, which is the
`RateLimiter` interface at `handler.ts:27-29`.

**What the documentation says, read 2026-10-23** (developers.cloudflare.com, `workers/runtime-apis/bindings/rate-limit/`):

- "Rate limits are approximate and apply separately in each Cloudflare location." and "These counts do not combine
  into one worldwide limit."
- "Rate limiting bindings are not currently visible in the Cloudflare dashboard."
- "You must use version 4.36.0 or later of" wrangler. The lockfile pins 4.124.0 (`package-lock.json:1496-1497`;
  `package.json` says `^4.59.1`, so the lockfile is what pins it). CI's dry-run build at every run above accepted
  the two `[[ratelimits]]` blocks, which is all CI can show about the binding.
- The page says nothing about plans, pricing or `workers.dev`; the Workers pricing page does not mention rate
  limiting at all. So there is no documented restriction to cite, and no documented permission either.

**Unverified:** that the binding attaches on this account and on `*.workers.dev`. The first deploy check settles it
in one request: a 503 `not_configured` with the key set means a limiter did not attach. Hazel's "GA" is not on the
page I read (I did not find a status statement either way).

## 5. Hazel's two calls, for the owner

**Coverage, now "serve what exists" by the owner's ruling.** The risks that remain:

- A route near a missing neighbour stops at the five-degree line with no visible reason on the map, because the
  present square's cut has no margin cells across the line (`cells.ts:55-58` clips to the square). The Worker names
  the gap in `missing`; the app must show it, or the user sees trails on the map and a route that will not cross
  them: the state CLAUDE.md's "don't make me think" calls the worst case. That is the app dispatch's to build, and
  it is the one thing I would ask Rowan to carry into it explicitly.
- With the 261021 set, which squares are missing is a matter of the run's coverage (187 squares over the US and
  Canada); Sunday's set replaces it as a new run. A phone that downloaded with a gap keeps the gap until it
  re-downloads; `run_id` in the answer lets the app tell.
- L1: "logged" is a live tail, not a record.

**The error codes.** Thirteen codes (PR body §3). Each is a distinct condition the app can act on differently:
re-ask (`run_superseded`), wait (`rate_limited`, with `Retry-After`), tell the user the area has no routes
(`outside_coverage`), or report a server fault (the 502s and 503s). None is an empty success; every one is
`no-store`. The cost is on the app side, where a `when` over thirteen strings must not fall through silently; the
app dispatch should say what an unknown code does. The one condition without a code is M2's exception.

## 8. Deploy notes for the planner (not findings)

1. **Deploy with `wrangler deploy` from the merged tree**, as -1564 did, never a dashboard paste: the two limiters
   exist only in `wrangler.toml` and are "not currently visible in the Cloudflare dashboard". A pasted bundle has
   no limiters and answers 503 `not_configured` on every routing request, which is the fail-closed design working,
   and is also a deploy that serves no route data.
2. **The check, in order:** without the key, `GET /routing/area.json?south=39.985&west=-105.31&north=40.015&east=-105.28`
   must be 403 `{"error":"forbidden"}`; with the key it must be 200 with `run_id` `usca-20261021T111429Z`, two
   files and `"missing": []`; a 503 `not_configured` at that point means the secret or a binding did not attach. An
   all-sea area (for example `south=30&west=-140&north=30.1&east=-139.9`) must be 404 `outside_coverage`. A tile
   request before and after must be identical. Then fetch one file URL twice and compare times: a second fetch
   noticeably faster is the only sign available that `caches.default` stores on this hostname (section 9).
3. `wrangler deploy` overwrites dashboard-set environment variables ("If you change your environment variables in
   the Cloudflare dashboard, Wrangler will override them", the configuration page); secrets survive. That was
   already true of -1564's deploy, so it is not new, but the two unused Access secrets and any dashboard `vars`
   are worth a glance after.

## 9. What is unverified

- **Whether `caches.default` stores on `*.workers.dev`.** The Cache API page says "Workers deployed to custom
  domains have access to functional `cache` operations" and, separately, that `.workers.dev` domains "include the
  query string in the cache key by default"; neither sentence settles whether a put on the current hostname is
  kept. If it is not, every file GET cuts again (about twice the R2 reads per download, still far under the
  limits) and correctness is unaffected, because the file route falls through to cutting
  (`handler.ts:208-227`). The tests cannot show this: `FakeCache` always stores. The tile routes have relied on the
  same cache on the same hostname since before this PR.
- **R2's `size` on a ranged `get`** is assumed to be the whole object's size (`handler.ts:100`). The R2 API page
  says only "Size of the object in bytes". If it were the range's size, every cut would fail 502 `checksum` on
  the first live request: loud, and in the safe direction.
- **The binding on this account and hostname** (section 4); **the secrets Rowan has set** (I cannot see them);
  **Workers Paid** (the record's word, as in Hazel's report).
- **CPU and memory on a dense city core:** reasoned, not measured, as Hazel's report states.
- **The app side,** including what it sends as edges (M2) and how it shows `missing` (section 5).
- **`tsc --noEmit`:** not run in CI and not by me (no `node` here). The bundle builds, which catches syntax but not
  types.
