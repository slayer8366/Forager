## The `ErrorLog` seam — full rationale

Mid-way through section (a), following the dispatch's literal instruction — copy `MushroomLogViewModel`'s `Log.w(TAG, ..., error)` pattern into `AvailabilityViewModel`/`TrackRecordingViewModel` — broke 23 existing tests. `android.util.Log` is unmocked and throws under a plain JVM unit test, and most of the broken tests hit it incidentally: `AvailabilityViewModel`'s `init` block unconditionally loads planned trips and offline map status, and a large fraction of `AvailabilityViewModel*Test.kt` files stub those two dependencies with `Result.failure(UnsupportedOperationException(...))` as a deliberately-failing stand-in for a dependency the test doesn't otherwise care about — every one of those tests now hit the new `Log.w` call and crashed.

The named premise that turned out wrong: `MushroomLogViewModel` was called "the model to follow" on the strength of its code shape alone. What no prior audit could show is that it has **zero test coverage of its failure paths** — no `MushroomLogViewModelTest.kt` existed before this task (see Queue Items below) — so its `Log.w` calls had never been exercised and the JVM hazard was invisible there. Validating a reference example against an absence of tests, then copying it into the two most heavily tested ViewModels in the repo, is what broke.

The session stopped and reported this rather than picking a fix unilaterally. The resulting decision, with its own reasoning, is fixed in `domain/ErrorLog.kt` (commit `74ae513`) — **read that file's own doc comment before touching either ViewModel's failure-logging shape.** The constraints that shaped it, and why each one is a constraint rather than a stylistic preference:

- **No Robolectric conversion.** The plain-JVM testability of `AvailabilityViewModel`/`TrackRecordingViewModel` is a deliberate, documented, repo-wide architectural choice, not an accident of how their first tests happened to be written. Reversing it across a dozen test files to accommodate one logging call would be the tail wagging the dog — and would silently widen the scope of a task the dispatch scoped as "what strings reach the user," not "how these ViewModels are tested."
- **`MushroomLogViewModel` itself stays untouched for this concern.** It works in production as-is; converting its `Log.w` calls to match the other two ViewModels would be scope creep with no user-visible benefit, and its coverage gap is a separate, pre-existing problem (queued below), not something this task's fix should paper over by making the inconsistency disappear.
- **The throwable must still be preserved for diagnosis in production.** Catch-and-discard was never on the table — CLAUDE.md requires a failure to be reported, never swallowed, and this is the exact reason `Log.w` was in the dispatch to begin with: the difference between a DNS failure and a 500 is the whole diagnosis when a user reports "search doesn't work."
- **The seam must not throw under plain JVM with zero per-test setup.** A default that only works if every test remembers to configure it will be forgotten by the next test written — the same class of failure that caused the 23 breaks in the first place, just deferred.
- **Minimal surface.** A small seam used by exactly these two files — not a logging framework, not a new dependency, not an interface hierarchy. `ErrorLog` is a one-method `fun interface`, mirroring the `CurrentTimeProvider` precedent already in `domain/` for the same underlying reason (a plain-JVM-testable class needs its non-deterministic/side-effecting dependencies injected, not called inline).

**If someone later "fixes the inconsistency"** by giving `MushroomLogViewModel` the `ErrorLog` seam too, or by reverting `AvailabilityViewModel`/`TrackRecordingViewModel` to call `Log.w` directly to match it, re-read this section first — the first path needs `MushroomLogViewModelTest.kt`'s coverage gap closed before it's safe (this task's own new test file uses Robolectric specifically because `MushroomLogViewModel` still calls `Log.w` directly — converting it to `ErrorLog` would leave that choice looking arbitrary rather than load-bearing), and the second path reintroduces the exact 23 failures this seam exists to prevent.

## The `strings.xml` divergence — deliberate, not an oversight

Section (b)'s two new neutral strings ("Rainfall data unavailable.", "Log entries unavailable.") are Kotlin string literals owned by their ViewModels, **not** `strings.xml` resources — even though the spec's own wording rules say "All strings in `strings.xml`, flat feature-prefixed convention."

This was checked against the actual codebase, not assumed: every sibling `*ErrorMessage` field in `AvailabilityViewModel`/`MushroomLogViewModel` (`tripWindowsErrorMessage`, `plannedTripsErrorMessage`, `startRecordingErrorMessage` — the untouched PR #32 reference example — etc.) is a plain Kotlin literal, with no exception anywhere in either class. The `strings.xml`/`Context.getString` split exists in this codebase only for strings a non-Compose caller needs (`track_recording_needs_location`, read from `MainActivity`, not from inside a `@Composable`). Moving only these two new strings to `strings.xml` would apply the spec's convention inconsistently within the same file, for no behavioral gain — the two would need to be handled differently from every other field around them for no reason a future reader could reconstruct.

**Do not "tidy" this into consistency with the spec's literal wording rule without re-reading commit `13618d4`'s message first.** The inconsistency is between the spec text and the existing codebase convention, not between these two strings and their siblings — and siblings win, per existing precedent, unless there's a reason to move all of them together (which is a larger, separate decision).

## Queue items from this task — recorded, not fixed

1. **`MushroomLogViewModel`'s test coverage is still thin.** It had zero tests before this task; the new `MushroomLogViewModelTest.kt` covers only `saveErrorMessage`'s clearing behavior (what section (d) needed). Its load/create/photo-add/photo-remove failure paths remain untested — this is also the reason the `ErrorLog` premise above went unnoticed until it broke something.
2. **The `Result.failure(UnsupportedOperationException(...))` stubbing pattern**, used throughout `AvailabilityViewModel*Test.kt` files to stand in for a dependency a given test doesn't exercise, is fragile: any side effect added to a failure path (exactly what the `ErrorLog` incident above was) breaks every test that stubs that path only to satisfy construction, not because the test cares about it. Worth knowing before the next person adds a side effect to any `onFailure` block anywhere `AvailabilityViewModel` is constructed.

## The open queue this task touches or sits next to

These are not this task's to fix — recorded here because a future session working in this area needs to know they exist before assuming a clean slate.

- **The permission-request flow (upfront vs. in-context) is an open owner decision with its own dispatch.** `docs/error-presentation-spec.md`'s own Scope boundary excludes it explicitly: this spec covers what the user is *told* when a permission is absent, not *when* the app asks. Don't fold a permission-flow decision into a future error-presentation change without checking whether that separate dispatch has landed.
- **PR #26 ("Add multi-region offline map management") is open and unmerged, and changes the same interface this task's section (a) touched.** It replaces `OfflineMapRepository`'s single-region `download`/`delete`/`getStatus` with `download(name, region, onProgress)`/`deleteRegion(id)`/`listRegions()`, backed by a new Room migration (DB v4 → v5). This PR's `MapLibreOfflineMapRepository.kt` fix (the SDK-diagnostic-text separation in `onError`) and `AvailabilityViewModel.kt`'s `offlineMapStatus` fallback-string fix both sit on the *current*, single-region shape of that interface. **Whichever of #26 or #34 merges second will very likely need a manual merge/rebase against the other** — the conflict is in the same handful of methods both PRs touch, not a coincidental nearby diff.
- **PR #31 ("Surface four unrendered error-state fields (Phase 2)") is open and explicitly superseded in part by this task.** The spec says so directly: PR #31 renders `conditionsErrorMessage`/`loadErrorMessage`/`waypointsErrorMessage` as inline `Text` with `colorScheme.error`, and its `startRecordingErrorMessage` Toast wiring is superseded by PR #32. **"PR #31 is rebased after this spec is implemented, not before"** — i.e., after PR #34 merges, not before. Once #34 merges, PR #31 needs a rebase that drops its now-redundant/now-wrong rendering of those first two fields in favor of what #34 landed, and keeps whatever else it does that #34 didn't touch.
- **Map waypoint interaction is a known gap, out of scope for both the spec and this task.** Tapping a waypoint marker on the map currently does nothing. The spec's own Scope boundary and Open Questions section both flag it: "a missing feature with its own scope, not an error-presentation problem," needing an owner decision on what a tap should do before anyone builds it.
- **The location-fix collector in `TrackRecordingService.startRecording()` escapes its intended scope — root cause not yet diagnosed.** This surfaced during the FGS crash-fix work (PR #32), not from the phase1 audit or PR #26/#27 — a future session searching those sources for it won't find it, which is exactly why it's recorded here instead. The concrete symptom: a "permission granted, service still starts" positive-path test was written, then had to be removed. `startRecording()` launches a real coroutine collecting `AndroidLocationTracker.fixes` on `Dispatchers.Default`, and that coroutine is not controlled by the test — a first attempt at the test outlived its own test method and threw against a torn-down `Context` deep inside the *next* test class's Robolectric sandbox, failing `AvailabilityScreenBackNavigationTest` with no visible connection to the actual cause. The service's manual `CoroutineScope(SupervisorJob() + Dispatchers.Default)` (`TrackRecordingService.kt:57`), cancelled in `onDestroy()` (`:101`), is an unremarkable pattern on its own — cancelling in `onDestroy()` is roughly right — so the concern is not "this code looks wrong," it's the **observed** escape: a coroutine from one test survived into a different test class. Two consequences follow, neither yet resolved: `startRecording()`'s success path is effectively untestable right now, which is why no positive-path test exists for the app's core safety feature; and in production, the same escape means the collector's lifetime may not actually be bounded by `onDestroy()` as intended — worth confirming rather than assuming, since a location collector surviving service teardown is battery drain during exactly the long sessions this app exists for.

## Provisional decisions carried forward

- **`saveErrorMessage`'s Toast is provisional, per the spec.** It was chosen specifically to test whether transient dismissal is enough for a failed save; the spec names the alternative (an inline banner with an explicit dismiss control) as the fallback "if misses are observed in field use." If a future session is asked to revisit this, that's the open question to resolve first — not whether the Toast pattern itself is correct in the abstract, but whether it's been *observed* to work in practice.
- **"Dismiss" for `saveErrorMessage` is implemented as "displayed," not as a real dismiss action.** Android's `Toast` API has no dismiss callback, and the spec explicitly rules out adding a dismiss affordance (an inline banner would be the alternative, not a dismissible Toast). So `LogPanel`/`JournalTab`'s `LaunchedEffect` calls `MushroomLogViewModel.onSaveErrorDismissed()` immediately after showing the Toast — the one-shot Toast being shown is what "dismiss" means here, for a field with no interactive control at all. This is a deliberate reading of an ambiguous spec phrase ("cleared on dismiss"), not an oversight — if the Toast is ever replaced with something that has a real dismiss action, this clearing call needs to move to that action instead of firing eagerly.
