## PR #376: findings, by severity

### High. The fill cannot be reached from the app while `us.json` advertises the old bounds

**What I read.**
- The live TileJSON, fetched during this review (`curl https://forager-pmtiles.brandonlee1-894.workers.dev/us.json`, `cf-cache-status: HIT`): `"bounds": [-180, 15.92097, 180, 85.04032]`, `minzoom 0`, `maxzoom 15`. The Worker builds it from the archive header (`src/index.ts:234-242` at `c67a0cb5a`, `p.getTileJson(...)`), and pmtiles' `getTileJson` writes `bounds: [header.minLon, header.minLat, header.maxLon, header.maxLat]` (protomaps/PMTiles `js/src/index.ts`, read on GitHub today).
- The Street style's source is that TileJSON by URL (`src/street-style-v1.json`, `sources.protomaps.url = …/us.json`; the offline style's too).
- MapLibre Native at the Android 13.5.0 tag, the pinned version, `src/mbgl/renderer/sources/render_vector_source.cpp:32` passes `tileset.bounds` into `TilePyramid::update`, and `src/mbgl/renderer/tile_pyramid.cpp:178-188`:
  ```
  if (bounds) { … tileRange = util::TileRange::fromLatLngBounds(*bounds, zoomRange.min, maxZoom); }
  auto createTileFn = [&](const OverscaledTileID& tileID) -> Tile* {
      if (tileRange && !tileRange->contains(tileID.canonical)) { return nullptr; }
  ```
  A tile outside the range is never created, so never requested. `src/mbgl/style/conversion/tileset.cpp:82` is where the TileJSON's `bounds` is parsed into `tileset.bounds`.

**Failure scenario.** The Worker is deployed with the fill and the world file is on R2. The owner opens Trail Map and pans to Bogotá at z8. MapLibre computes that tile `8/75/124` lies south of 15.92°N, outside the source's bounds, and does not request it. The map stays grey, exactly as in the S22 test that produced -1554. Meanwhile the PR's deploy check (`curl /us/8/75/124.mvt`) answers 200 with `X-Forager-Origin: r2-world-south`, so the check passes while the phone shows the same grey. This is the family CLAUDE.md names as "check reachability before measuring behaviour": the Worker path works and has no caller.

**What it is not.** Not a defect in Hazel's code, and not something the dispatch let Hazel fix: Part A says "Nothing else changes: the tile JSON (`us.json`)". The premise was the planner's, and it is wrong for the one client that matters. The fix is a planner's decision, for example the TileJSON advertising bounds that cover the fill (south to the world archive's -85.05°) while the fill is on, with a test that `/us.json` reports them. Two consequences to price with it: the TileJSON is edge-cached for a day (`Cache-Control: public, max-age=86400`, seen on the live response) and MapLibre caches it too, so phones pick a new `bounds` up within a day of the deploy; and the Street and offline styles share the TileJSON, so one change covers both.

**Inferred, not confirmed on a phone:** that the S22's grey in the -1554 test was the bounds skip rather than 204s. Both produce grey. The distinguishing check is in the device section below.

### Medium. The tile row that straddles 15.92°N is served from `us` at every zoom 0 to 8, and what it holds south of the line is unknown

**What I read.** The fill runs only when `us` returns no tile (`src/index.ts:275-285`): `if (tiledata) return 200 from us; if (name === STREET_ARCHIVE_NAME) { fill }`. The PR body states the rule ("The `us` tile wins wherever `us` has one") and has a test for it (`worker.test.mjs`, "a tile us.pmtiles holds is served from us.pmtiles…").

**Why it matters.** At each zoom 0 to 8 exactly one tile row contains the 15.92°N line, and at z0 to z2 that row is the whole band from the equator north. If `us.pmtiles` holds those tiles with content clipped to its own extent (as an area build from a US-only OSM extract would), the band south of 15.92°N inside that row stays grey after the fill: at z3 the tile `3/2/4` spans 0° to 40.98°N, so Colombia and Venezuela stay grey at z3 even once everything south of the equator is filled. If instead `us.pmtiles` was cut with `pmtiles extract`, those tiles carry the planet's content and the band is fine.

**Could not determine** which, from the repository: how `us.pmtiles` was built is not recorded in either PR, and the Pi's build is Aspen's. The PR's "overlap" note records that both archives hold the rows but not this consequence. The deploy check's z3 tile (`/us/3/2/4.mvt`, South America) is listed as a fill tile; with `us` holding `3/2/4` it would answer from `us`, origin `r2`, and the check as written would read that as a failure of the fill when it is the overlap rule working. Worth a sentence in the deploy notes either way, and a device look (below).

### Low. Notes that need no change

- **`STREET_ARCHIVE_NAME` is computed at module load** (`src/index.ts:285`, `archiveNameFromTileJsonUrl(streetStyle.sources.protomaps.url)`), and the parser throws if the bundled style's source URL is ever not `/{name}.json`. Then the whole Worker fails to start, styles and tiles alike. Loud and immediate, which is the right failure, but it is a new way for a style edit to take the Worker down; the style route tests in CI would catch it before a paste.
- **Warnings nobody reads.** The two logged skips (world archive missing, tile type mismatch) go to `console.warn`, and the PR says Workers Logs is off. CLAUDE.md asks that a fallback be logged when it fires, and it is; but with logs off, the only visible sign of a missing world file is grey. The deploy notes say this plainly. Fine as stated.
- **CI job.** `if-no-files-found: warn` on the results artifact where route-cutter uses `error`; harmless, since the summary step already fails a run with no XML. The job runs on pull requests (no branch filter on `pull_request`, `ci.yml:14-16`) and ran on #376's own PR run.
- **The 204 that is cached.** A z ≤ 8 miss in both archives, or a miss with the world file absent, is a 204 cached for a day at the edge (`cacheableResponse`, `src/index.ts:209-216`). The PR says so and the dispatch asked for nothing else.

### What holds up in #376

- **The diagnosis.** The dispatch's three verify-first questions are answered correctly: the 404 path (`:245-250`) applies only outside the archive's zoom range, so z ≤ 8 cannot reach it; the fill is keyed on the Street archive's name read from the bundled style, not a literal `"us"`; `worker.test.mjs` ran in no CI job before this PR, and now does.

- **`us` wins**: confirmed by the order of the two reads (`:270` then `:278`).

The world `KeyNotFoundError` is caught inside `worldFillTile` (`:313-318`) and becomes the 204, not the outer catch's 404; the `revert-catch` run is the test that the distinction is live.
- **Archive separation.** `R2Source.getKey()` returns the archive name (`:63-65`), so the module-wide `ResolvedValueCache` keeps the two archives' headers and directories apart.

- **The fixture is honest.** `make-world-south-pmtiles.py` holds `0/0/0` (also in tiny, so "us wins" is a real test), `5/9/16` and `8/75/130` (fill), `9/150/260` (present but capped, so the z9 test fails if the cap goes), and `5/9/17` is in neither archive. ## PR #377: findings, by severity

### Medium. A Trail user whose Trail Map has already fallen back gets no downloads when the signal goes

**What I read.** `ui/map/NoSignalTrailMap.kt:40-41`:
```
internal fun drawsFromDownloads(useOfflineTiles: Boolean, basemap: Basemap, noSignal: Boolean): Boolean =
    useOfflineTiles || (noSignal && basemap != Basemap.FORAGER_TRAIL)
```
`SightingsMap.kt:590` feeds it the chosen `basemap`. After `OwnStreetFallback` has fired, `basemap` is still `FORAGER_TRAIL` while the map drawn is OpenStreetMap's raster (`BasemapStyles.kt:146` `rasterDrawn()`, `OwnStreetFallback.kt:36`).

**Failure scenario.** Cold start with the Worker unreachable and a cold cache (the -1513 case): the fallback fires and the Trail user is drawn OpenStreetMap's raster for the process. They then walk out of coverage over an area they downloaded. `drawsFromDownloads(false, FORAGER_TRAIL, true)` is `false`, so the raster stays and the map goes grey; an OSM user beside them gets Trail Map from the downloads after 5 s. The one user the rule is written around, the default map type, is the one it leaves out, and only in the state where they are in fact looking at OSM.

**What I am not saying.** The owner's rule in -1554 and -1556 names OSM and Topo users, so this PR implements the rule as written. The gap is between the rule and "every failure has a fallback" (-519). The candidate is one condition (`basemap != FORAGER_TRAIL || !OWN_STREET_FALLBACK.ownStreet()`), but it widens the ruled behaviour, so it is the planner's to raise, not Hazel's to add. Not a blocker.

### Low. The hysteresis restarts with the Activity

`MainActivity.kt:78` holds the monitor `by lazy` for the Activity (`noSignalState(applicationContext, lifecycleScope)`), and `NetworkSignal.kt:99-101` takes the first reading with no delay by design. A rotation, or any configuration change that recreates the Activity, takes a fresh first reading: if the network is unvalidated at that instant (a hand-over in progress), an OSM user's map reloads to the downloads at once with no 5 s guard, and stays there at least 30 s. The PR body states it ("Activity scope: the monitor lives for the Activity"). Moving the monitor to the Application or a ViewModel would keep the 5 s rule across rotations; a decision for later, not this PR.

### Low. A hand-over is the case the S22 cannot test

`net/AndroidNetworkSignal.kt:48-55` sends `false` on `onLost` and the validated flag on `onCapabilitiesChanged`. On a Wi-Fi to cellular hand-over the order and timing of `onLost` for the old default against `onCapabilitiesChanged` for the new one is platform behaviour I did not read (unverified), and the 5 s guard is what covers it. The test phone has no SIM, so the only phone that can see a hand-over is the owner's. The checklist has no step for it. Added below.

### Low. Wording and small things

- `AvailabilityViewModelBasemapTest.kt` (updated line): the unknown-key log line now reads "opening on Topo and storing that" because the log quotes `MapMode.label`. A chip label is now inside a log message meant for the owner reading logcat; harmless, worth knowing when grepping old logs for "Topographical".
- The Layers sheet while no signal still shows OSM or Topo selected, and the caption reads "Protomaps © OpenStreetMap" (`SightingsMapLayout.kt:139` through `mapCreditsFor` with `useOfflineTiles` true). That is the ruled behaviour; I note it only because it is a state a user could read as "my map type changed by itself". The dispatch rejected a prompt explaining the update; it says nothing about a hint for this state. Observation for the owner, not a finding against the PR.
- The night paint on the offline branch: `mapStyleSourceFor` with `useOfflineTiles` returns the regions' style "regardless of basemap and night" (`BasemapStyles.kt`, the doc comment above `mapStyleSourceFor`). So a Topo-at-night user with no signal gets whatever offline mode gives at night today. I did not trace whether night paint is reapplied after load; a device observation, below.
