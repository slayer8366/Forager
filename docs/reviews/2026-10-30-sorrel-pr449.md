### S-1. A saved route's fit is applied again every time the Maps tab is returned to while the route shows, over the camera the user moved

**Read.** `savedRouteCameraRequest` (`CompactMapRoutePlotting.kt:91-100`) builds a request whose id is
`saved-route-<trip>-<serial>`, constant for the whole Showing mode, and `AvailabilityCompactMapUi.kt:492` copies it into
`renderMode` on every composition. The map applies a request once by remembering its id in `lastAppliedCameraRequestId`
(`MapDataRefresh.kt:108-120`), and that memory is `remember { mutableStateOf(null) }` inside `SightingsMap`
(`SightingsMap.kt:522`): it lives and dies with the MapView. The Maps tab is one branch of `TabCrossfade(targetState =
compactTab()) { when (tab) … }` (`AvailabilityCompactScaffold.kt:1154-1166`), so a tab change disposes the map. What outlives
it is `MapCameraMemory` (`MapCameraMemory.kt:36-44`): the saved camera and `appliedSearchFrameId`, which RECORD -750 added
for exactly this reason for a search's frame ("applies a search's frame once, not again over the camera the user has moved
since"). Nothing in it holds a camera request id. `routeCardHeightDp` is also a tab-local `remember`
(`AvailabilityCompactMapUi.kt:303`), so on return the request is `null` for a frame and then reappears once the card is measured.

**Failure path.** Open a saved route (the map fits it). Pan and zoom to look at one leg. Go to Journal. Come back to Maps. The
restored camera (`cameraRestoreFor`, `MapCameraMoves.kt:143-152`) is applied, then `MapDataRefresh` sees a request with an
id it has never applied and fits the route again; if Locate following had been turned back on meanwhile, `stopsFollowing`
ends it again (`:108-109`). CLAUDE.md, UX defaults: "a piece of user-set UI state that resets on a tab change is a bug unless
the exception was stated explicitly for that case." The first stop's (d) said "A tab change: everything [survives]"; this is
the one piece that does not, and the fixture cannot show it (the stub slot never runs `MapDataRefresh`), so no test fails.
**Inferred** from the code path end to end; not observed. The S22 step can observe it in one minute (phone check 3).

**Why S rather than N:** the project's own rule names it a bug, the mechanism has no gap, and the fix has a precedent in the
same file (`appliedSearchFrameId`): keep the applied request id in `MapCameraMemory`, or have the ViewModel consume the open
(its `serial`) once the fit has been applied. If the owner instead rules that a route re-fits on return, that is the stated
exception and this closes as a decision, not a fix.
