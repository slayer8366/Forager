## Verdict

**No blocking finding; three should-fix, one of which decides whether the upstream draft is fit to file;
seven nits.** The mechanism is as the PR body says, and I traced every exit (section 1). The 300 ms puzzle is
solved from MapLibre's source and it is not a puzzle: MapLibre's parser gives a style with no `transition` a
300 ms duration *as a set value*, so Android reads 300, not 0; the code comment, the test fake, the PR body,
the upstream draft and RECORD -1752 all rest on the opposite premise, and the `0 -> 300` rule is dead code on
the phone (S2, section 3). One path leaves the old style's patterns at `""` with nothing able to restore them:
a second style request landing between the clear and the restore whose load then fails by URI (S1, section
1); it is narrow and inferred from MapLibre's source, not seen on a phone, and a three-line change closes it.
The fresh-tile case (cold start, a basemap switch onto Trail Map) now clears patterns that were drawing and
restores them 100 ms later, and nothing measured whether that blinks (S3). The revert runs are evidence: I read
R2's and R3's JUnit XML and all four job logs (section 4).

## Findings, ranked

### Blocking

### Should-fix

**S1. One path leaves the old style's patterns cleared with no way back: a new style requested between the
clear and the restore, whose load then fails.** `onStyleRequested` (`PatternRelayout.kt:58-68`) cancels the
pending restore and logs "a new style was requested before the restore (2 layers left cleared; the new style
brings its own); dropped." That is right when the new style loads. It is wrong when it does not. The call sits
at `MapStyleReload.kt:130`, one line before `map.setStyle(builder)`; `MapLibreMap.setStyle` invalidates the
old Java `Style` at once (`MapLibreMap.java:1143-1145`, `Style.clear()`, after which every call throws
`IllegalStateException`, `Style.java:791-797`), so from that line on nothing in the app can set a property on
the old style. On the native side a URI style keeps the previous sources and layers until the new document
parses (`style_impl.cpp:68-85`: a fetch error calls `onStyleError` and returns; only `parse` at `:98-106`
clears them), and in continuous mode the renderer draws whatever the style holds whether or not it is loaded
(`render_orchestrator.cpp:430-433` returns early only for non-continuous modes). So: night toggled, T0, the
clear at +400 ms, and a second style request by URI in the next 100 ms to 2 s whose fetch fails, and the map
keeps drawing the first style's forest and wetland with `fill-pattern` at `""`, until the next successful
load. That is the state the dispatch called worse than the bug. The requests that can land without the user
touching anything are the no-signal switch (`NoSignalTrailMap.kt`, via `useOfflineTiles`) and the own-Street
fallback flip (`OWN_STREET_FALLBACK.ownStreet()`), both keys of the effect at `MapStyleReload.kt:76`; the first
fires on a signal loss, which is also when a URI load is likeliest to fail, and the offline style fails when no
region covers the camera. The window is short, so I rank this should-fix rather than blocking; Rowan or the
owner may rank it otherwise. **Remedy:** when `onStyleRequested` finds a restore pending, restore the cleared
layers synchronously *before* returning (the old `Style` is still valid at `MapStyleReload.kt:130`), then
cancel; log "restored N before the new style". The restore costs one `setProperties` per layer and the new
style replaces them a moment later in the common case. The test
`nothing is restored when the style changed between the clear and the restore` (`PatternRelayoutTest.kt:195-211`)
asserts the current behaviour and would turn around. Inferred from source; not reproduced on a device.

**S2. The 300 ms "puzzle" is a wrong premise, and it is written into the code comment, the test, the PR body,
the upstream draft and the record.** The claim is "Android reads an unset transition as 0
(`native_map_view.cpp:920-930`), so 0 stands for unset" (`PatternRelayout.kt:29-30`, `:164-165`;
`PatternRelayoutTest.kt:24` "its transition as Android reads it", `:26` default `transition = 0L`, `:131` "an
unset transition reads 0"; PR body item 1; upstream draft lines 52-55; RECORD -1752 "The app already writes an
explicit 0/0 style transition"; -1754 "unexplained"). What the source says: the parser's member is
`TransitionOptions transition{{util::DEFAULT_TRANSITION_DURATION}};` (`parser.hpp:40`), so a parsed style
starts with `duration = 300 ms` as a *present* optional and `delay` unset; `parseTransition` replaces it only
when the document has a `transition` member (`parser.cpp:107-109`), and `street-style-v3.json` has none (read:
no top-level `transition`, no `*-transition` paint key on any layer); `Style::Impl::parse` copies it
(`style_impl.cpp:106`); `NativeMapView::getTransitionOptions` then returns `value_or(zero)` of a present 300
and an absent delay (`native_map_view.cpp:921-926`), that is 300/0. `disableSymbolFade`
(`PlacementTransitions.kt:20-21`, `:28-30`) reads that back and writes `TransitionOptions(300, 0, false)`,
so from the callback on the style's transition is an explicit 300/0, not 0/0. That is exactly what the phone
logged ("style transition 300 ms") and it means: (a) the `0 -> 300` branch of `clearDelayMs`
(`PatternRelayout.kt:167-168`) never runs on this app's styles, and the one case it would run on, a style that
sets `"transition": {"duration": 0}` on purpose, is the case it gets wrong (an explicit 0 is not "unset"; the
wait would still be a harmless over-wait, since the S22 showed +0 to +250 failing with a 300 ms transition
and nothing is known about a 0 ms one); (b) the test fake's default of 0 models a phone that does not exist,
and the asserted 400 matches the real phone by coincidence of `300 + 100 = (0 -> 300) + 100`; (c) the
upstream draft's "Against it" bullet tells the maintainers the app sets 0/0, which is false, and would send
them looking in the wrong place; the truth (the 300 ms default is in force, and the threshold is 261-300 ms)
*supports* the hypothesis the draft then half-withdraws. **Fix:** correct the comments and the test fake's
default (300, and a test for a style that sets its own); either drop the `0 -> 300` branch or rename it a
floor ("never less than the measured S22 threshold of 300 ms, whatever the style says") with that reason;
replace draft lines 52-55 with the correct reading; and a RECORD entry correcting -1752's sentence. Until the
draft is corrected it is **not fit to file** (section 5); the code change is cosmetic on the phone's
behaviour.

**S3. Every fresh-tile load now clears patterns that were drawing, and nothing measured the result.** The
relayout runs on every style load (`PatternRelayout.kt:87-107`), including the MapView's first (a cold start,
or Maps re-entered) and a basemap switch onto Trail Map from OSM or Topo, where every vector tile is laid out
fresh and the glyphs draw at once. On those loads the clear at T0 +400 ms takes drawn glyphs away and the
restore brings them back at the first full frame at least 100 ms later (100-109 ms on the S22). With
`fill-pattern` cross-fading over the style's 300 ms (`fill_layer_properties.hpp:40`, `properties.hpp:31-64`,
`DEFAULT_TRANSITION_EASE` front-loaded), that is a dip of the glyphs to a fraction of their opacity and back,
about half a second after the map appears, on the owner's phone at every launch that opens on forest. The
cause report priced this as "one wasted relayout" (`glyph-cause.md`, "The proposed fix", Cost) when the gap
was to be one frame; the measured gap changed the price and the PR body does not mention the case. The device
check read at 1 s and 30 s after a *switch* (PR body, "How it is measured"), so the window 0.4-0.9 s after a
cold start was never sampled. **Ask:** either a measurement (screenshots at about 100 ms steps from 0.3 to
1.0 s after a cold start at the cap over forest, by day; pass if the glyph share never drops below, say, half
its resting value), or an owner ruling that the dip is accepted, recorded. A code option if it is visible:
skip the relayout on the MapView's first style (`state.appliedStyle == null` at `MapStyleReload.kt:114` is
already the test for that); a basemap switch onto Trail Map has no kept vector tiles either, but the app
cannot tell that from a Night switch without reading the previous source, so that one is harder. Inferred
(the visibility); the sampling gap is confirmed from the PR body.

## 3. The 300 ms puzzle

Solved; see S2 for the chain of six source lines. In one sentence: the style's transition is not "unset, read
as 0" but "set by the parser to 300 ms", `PlacementTransitions.kt` keeps that 300 when it switches the
placement fade off, so the phone's "style transition 300 ms" is the ordinary reading and the `0 -> 300` rule is
never exercised. The wait is therefore computed from the right value on this app's styles (300 + 100), for
the wrong stated reason. The upstream draft's "Against it" paragraph inverts the evidence.

What this does *not* settle: whether the 300 ms transition is the cause. The "no fade" probe set the
*per-layer* `fill-pattern-transition` to 0/0 and fixed night but not day (PR body table), and `Transitioning`
(`properties.hpp:31-38`) does honour a per-layer 0/0 (`isDefined()` true, `end == begin`, complete at once).
So a zero transition on the layer was not enough, and the 261-300 ms threshold matching
`DEFAULT_TRANSITION_DURATION` remains a correlation. The draft says so ("That link is not shown"), correctly.
