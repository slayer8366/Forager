## 2. `reset()` on every search result (Rowan's check 2)

`offTrail.reset()` has exactly one call site in the PR, `AvailabilityWaypointRoute.kt:236`, inside the search
job's result handler, before the `when (result)`. Every search starts in `startSearch` (`:218`), which has
two callers:

1. `:159`, the `shown == null` branch of `onFix`: the first fix, or a straight-line result that
   `WayToRetry.judge` says to try again (Amendment 1's entering an area, Amendment 2/3's 50 m walked inside
   an area). `line` is `null` here by the branch's guard (`:156-157`).
2. `:168`, `StrayVerdict.REROUTE`: the stray at more than 50 m, once per stray (`WayToStray.kt:28-32`).

Whether a non-stray result can wipe an OFF state that should have stayed comes down to: can `state` be
anything but ON while `line == null`? No. `judgeOffTrail` runs only in the `shown != null` branch (`:162`),
so the state moves off ON only while a line is shown; and every path that sets `line = null` is inside the
same result handler that has just called `reset()` (`:236` then `:250`). So at every non-stray result the
state is already ON with nothing held, and the reset is a no-op. The one reset that changes anything is
the stray re-route's, and that is the ruling (−1726: "a stray re-route calls the existing reset(), so the new
line shows at full strength with no 'Back on trail'"). A stray re-route that comes back `StraightLine` (the
engine found nothing from the stray point, `:249-253`) also resets, and the HUD is `ReturnRoute.Straight`,
which carries no off-trail state: −1725 step 5 holds there too.

Two orderings checked: `judgeOffTrail` runs before `show` on each fix (`:162-163`), so the state `show`
reads is this fix's; and the freshness ticks (`:116-120`) call `publish()` only, which rewrites `placed`
with freshness and never re-judges (`:212-216`).

Not a finding, stated for the walk: while a stray's search is in flight the old line is still judged
(`:162`), so a walker beyond 50 m can go OFF on the old line during the search; it is invisible (beyond the
far band `show` gives `hud = null, line = null`, `:191`, `:206`) and the result's reset clears it.

## 5. The structural no-alert test (Rowan's check 5)

`WaypointOffTrailQuietTest` reflects over `AvailabilityViewModel`, `AvailabilityWaypointRoute`, its
`Following` and `WayHomeOffTrail` for any field or constructor parameter of type `AlertDelivery`, with
`ReturnWatch` (which holds one, `ReturnWatch.kt:106`) as the positive control. It is about 40 lines and
runs in milliseconds.

**Worth its keep, with N1's comment fix.** A behavioural check ("no sound or vibration call is reached")
needs a seam to observe, and there is none: `AvailabilityViewModel` is built without any `AlertDelivery`,
so there is nothing to fake and nothing to assert was not called. Adding a fake delivery to the ViewModel
so a test can assert it stays silent would be building a path in order to prove no path, and CLAUDE.md's
"new capability is a new path, not a conditional threaded in" cuts the other way. The structural test is the
cheapest statement of the actual fact, that none of these classes can reach the one delivery seam, and its
positive control shows the check can see one. Its blind spots are the ones it names (a lambda handed in) plus
notifications (N1). Rowan's call whether a comment in the class doc would do the same job without a test
class; I would keep the test, since a comment cannot turn red when someone later hands `AvailabilityViewModel`
an `AlertDelivery`.
