## 4. The audit's pitfall: could any remaining test pass the same way? (read)

The S22 audit passed portrait on a 44 px gap between the pill and the card measured while the bar was being moved by the card
(three card heights, one gap). What closes it, and what is still gap-shaped:

- **The bar:** `RouteCardBarRig.assertBarUntouched` asserts the bar shows once, then `assertSame(barBefore, bar)` on all four
  edges to 0.5 dp, then that the card is apart from the bar and from the pill. `barBefore` is captured by each test after
  `setScreen()` and before `plotTo(...)`, and every measurement follows `settle()` (`mainClock.advanceTimeBy(2_000)` then
  `waitForIdle()`), so nothing is read mid-move. A displaced bar cannot pass this: the `cardraisesbar` revert fails three
  tests with the bar's expected rectangle in the message (41331327924, computed). The landscape column goes through the same
  helper.
- **Still measured as a gap, by design:** the pill's bottom against the card's top (`RoutePlottingChromeTest:123`), the legend
  chip's bottom (`:170, :176, :189`; `RouteCardBesideBarTest:169, :182`), and the "i" (`RouteCardAttributionTest:135`). These
  are the three things the rule says must rise, so a gap is the right assertion for them, and each of those classes settles the
  clock before reading. They could still pass if the card were lower than it should be, which is why the card's own edges are
  asserted elsewhere: 8 dp from the far edge and 8 dp from the bar (`RouteCardBesideBarTest:207`), bottom above the navigation
  inset, and in landscape the tuck.
- **Deliberately mid-move:** the two widening tests read twelve frames with `autoAdvance = false`, which is the point of them,
  and then settle before the final width. The reduced-motion test reads 24 frames and requires at most three distinct widths.
- **One residue of the same shape, read, not a defect:** `RoutePlottingChromeTest` and `RouteCardAttributionTest` assert the
  rise against the card's top but not that the card's top is where it should be in those classes; the card's placement is
  asserted in the beside-bar classes under native graphics, and a card that moved the bar would fail those first. I found no
  test that passes only because something was mid-animation.

## 5. Robolectric's default text widths (read, computed)

The PR body measured a 28-character line at about 10 dp under default graphics. So the question is which fit assertions run
under which mode:

- **Native graphics (`@GraphicsMode(NATIVE)`):** `RouteCardBesideBarTest` (9), `RouteCardContentWidthTest` (13, with the
  tablet and landscape classes in the same file), `RouteCardFontFitTest` (1), `RouteCardLandscapeBarTest` (5),
  `RouteCardPhoneFiguresTest` (1), `RoutePlottingWindowsTest` (5), `RoutePlottingBubbleFontScaleTest` (2). Every assertion
  that a line is whole goes through `assertWhole`: the `TextLayoutResult` from `GetTextLayoutResult`, no line
  `isLineEllipsized`, no `hasVisualOverflow`, and the last line ends at the text's end. Under native graphics those can fail,
  and did: the fail-first run's "line 0 of … is cut" lines, and the `cutname`, `cutcount`, `cuthint`, `cutrow` reverts.
- **Default graphics:** the remaining classes assert positions (the total line stays put, the handle's 32 dp, the "i" and
  pill rises, touches at fractions of a node's bounds) and words through semantics text. A semantics-text equality cannot see
  a cut, since the full string is in the node whether or not it is drawn whole, so none of these is a fit test, and none
  claims to be. I found no width-fit assertion left in a default-graphics class (a grep of the twelve default classes for cut,
  ellipsis, maxLines, overflow, lineCount and width assertions finds only touch coordinates).
- **The one thing default graphics still shapes:** in those classes the card is as wide as its buttons' minimum widths, since
  the measurer sees the fake text widths; positions are asserted relative to the card's own bounds in the same run, so this is
  consistent, but any number printed by a default-graphics class is not a phone number.
