### 2. The owner's rulings

**-761 and the 10 s.** RECORD -761 (read) is "Keep last reading (Recommended)", with "the heading still shows '—' when
there was never a reading". The 10 s itself is not in -761's text; it lives in the code (`TrueHeading.kt:191-194`, "Stale,

"stale", "10 s" and "heading" did not find the figure recorded by name; I did not search further. So "-761's 10 s rule" is
-761's keep-last-reading rule with the code's 10 s, which is the rule the tab return already uses. **Unverified:** where
the 10 s was recorded.

**What the PR does with it** (`TrueHeading.kt:124-128`): on each start after the first stop, if the value is `Available`
and `nowMillis() - stoppedAt !in 0..HEADING_KEPT_FOR_MS`, the value becomes `NeedsFix`. Exactly 10 000 ms keeps (the range is
closed, the same shape as `HeadingMemory.fresh` at `:197`); 10 001 ms dashes. A negative gap (the Maps tab's clock is the
wall clock, `currentTime::nowEpochMillis`, `AvailabilityCompactMapUi.kt:417`) also dashes, which is the honest side. Only an
`Available` value is replaced: `Unreliable` stays `Unreliable` (no false all-clear), `NeedsFix`/`NoSensor` stay. Matches the
owner's "Same rule as tab returns".

**The trust hold** (`CompassTrustJudge.kt:73-75`, `TrueHeading.kt:125`): `restartClearHold()` nulls `goodSinceMillis` and
keeps `unreliable`. Called on every return, before the gap check, whatever the gap's length. A judge that was untrusted at
screen-off needs 2 000 ms of good readings after the return (`CompassTrustJudge.kt:53-57`); one that was trusted stays
trusted (`:52` returns before the hold). Matches "Yes, re-check". The two judge tests pin both halves, and r3 (`reset()` in
place of the null) fails all three tests that depend on it with messages naming the untrusted state being forgotten.

**One route around the hold, pre-existing, not this PR's:** the judge is created inside the producer
(`TrueHeading.kt:119-120`), whose keys include `hasFix`. If the fix is lost during the screen-off and is back by the
return, nothing restarts; but if it is lost and still absent at the return, the producer restarts with a fresh judge, and
when the fix comes back it restarts again, so a compass that was calibrating is trusted on its first good reading. The same
happens today on screen whenever the fix flips. Outside this dispatch; recorded here, not touched (N-4).

### 3. STARTED, not RESUMED

`TrueHeading.kt:123` uses `Lifecycle.State.STARTED`. Under a system permission dialog or in split-screen on a phone
without multi-resume the activity is paused, not stopped, so the compass keeps turning; a Compose `Dialog` does not pause
the activity at all (inferred from the platform, not read in AndroidX source here). The choice is right and its reason is
in the doc comment (`:77-78`).

**Not pinned by a test.** `screenOff()` goes to CREATED and `screenOn()` to RESUMED (`CompassScreenOffTest.kt:125-133`).
A revert of `STARTED` to `RESUMED` passes all seven tests: at CREATED both states have stopped the collection, at RESUMED
both have started it. The one state that tells them apart, STARTED, is never visited. This is N-1.

### 4. The default-clock change

`nowMillis` defaults to `SystemClock::elapsedRealtime` instead of `{ 0L }` at both overloads (`TrueHeading.kt:93, :112`).
Callers that take the default (read, `git grep` at 37ea85576):

- **`SightingsMap.kt:281`**, production: the own heading of every map under `AvailabilityScreen` not handed one (the
  pickers). It passes no `memory`, so before this PR the clock was used only by `memory?.record` (a no-op) and the
  `initial` (memory null). After it, the clock measures the screen-off gap: with `{ 0L }` every gap would read 0 and the
  stale heading would always be kept on the puck; with the monotonic clock, a gap over 10 s turns the puck's reading to
  `NeedsFix` and the engine's status to `UNRELIABLE` until the first reading. This is the one behaviour this change adds,
  and it is the behaviour the owner asked for on the strip applied to the puck. `MapCompass` (`NavigationView.kt:224-228`)
  carries no clock, so the alternative was to add one; -1862 records the planner accepting the default instead.
- **`LandscapeHeadingReadersTest.kt:97`**, test: never moves the lifecycle, so the clock is never read except by the
  no-op `memory?.record`. Unaffected; it passed in the green run.
- The Maps tab (`AvailabilityCompactMapUi.kt:417`) passes `currentTime::nowEpochMillis` and is unchanged by the default.

Two clocks now age two headings on one screen (wall clock for the strip, monotonic for the pickers' pucks). Both are
consistent within their own call; nothing compares them. Not a defect; noted for the planner (N-5).
