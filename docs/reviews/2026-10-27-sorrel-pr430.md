## Verdict

**Mergeable into `pre-main`; no blocking finding; five should-fix, of which two are Back-chain gaps on
paths the dispatch did not list and one is landscape-only and inferred; six nits.** The owner's six steps
are built as ruled, on the Maps tab only (-1749), and the five accepted choices are in the code where the PR
says they are. The zoom loop cannot oscillate (section 3). The fits check is the same function the fan's
placement uses (section 4). The list is a bounded `Surface` with its padding outside the touch area, a real

seven revert runs fail with messages only their own edit can produce, on builds that reached the test step
(section 5). The seam for the next PR is clean (section 8).

The should-fix findings. **S1:** a move the app makes because the user asked for it (the locate button, a
search result, Return to Route) folds the fan but leaves the list up with a stale anchor and the camera
return pending, so the next Back jumps the map away from where the user just sent it; the PR's own rule for
the pan applies to those moves too. **S2:** the camera returns and the list live in a `remember` inside the
Maps tab, which leaves composition on a tab change, so after "Open in Journal" from a fanned icon and Back
(which reopens the fan through the hoisted return memory) the camera step is gone and Back goes fold >
toast. **S3:** in landscape a full list (the only kind that shows) reaches to within about 68 dp of the
window's top, under the search strip, with no clearance like the bubble's `minY`; inferred from sizes, no
landscape test. **S4:** one exit of the zoom loop is a fallback with no log line. **S5:** the S22 steps
miss four cases and one pass condition is misread.

### Should-fix

- **S1. An app-requested camera move leaves the list and the camera return behind.**
  `MapTapHandler.kt:164-170`: `crowded?.onUserGesture()` runs only for `USER_GESTURE`; an
  `APP_REQUESTED` move folds the fan (`:169`) and nothing else. So with the list up, or a return pending
  after the zoom's fan was folded, a press of the locate button (or a search result's frame, or Return to
  Route) moves the camera and (a) the list stays, anchored at `CrowdedList.anchorXPx/anchorYPx`
  (`CrowdedStackZoom.kt:200-209`) which a row tap hands to the bubble as its screen point
  (`CompactMapCrowdedList.kt:71`), now a point on the map where the stack no longer is; (b) the next Back
  restores the pre-tap camera (`CrowdedStackBack.kt:28`, `MapStackCamera.kt:52-67`), undoing the move the
  user just asked for. The PR body's rule for the pan, "Back undoes the app's move, not the user's", covers
  these moves equally: they are the user's. The fix is not one line: the restore's own move is marked as an
  app move (`MapStackCamera.kt:53`, `:63`) and classed `APP_REQUESTED`, so clearing the returns on every
  `APP_REQUESTED` would also clear the rest of a chain of returns (S22 step 5). It needs the restore marked
  as its own cause, or a flag on the host set around the restore. A step path for the owner: tap crowded >
  zoom > press locate > Back > ?

- **S2. The camera returns and the list do not survive a tab change; the fan does.**
  `AvailabilityCompactMapUi.kt:299`: `val crowdedStacks = remember { CrowdedStackHost() }` inside
  `CompactMapTab`, which is the `CompactTab.MAP ->` branch of the scaffold's `when (tab)`
  (`AvailabilityCompactScaffold.kt:1158-1166`, inside a `TabCrossfade` per `ScaffoldMapTabCall.kt:5`), so
  the host is rebuilt empty when the tab comes back. The fan left by "Open in Journal" is reopened through
  `mapReturnMemory`, hoisted in the scaffold (`AvailabilityCompactScaffold.kt:354`; `FanReopenCoordinator`
  at `MapListeners.kt:223`), and the camera comes back zoomed in through `mapCameraMemory` (`:352`;
  `MapListeners.kt:204-217`, the snapshot at `:207`). So the path tap crowded > zoom > fan > tap icon > bubble > Open in Journal >
  Back gives back the fan at the zoomed camera, and the next Backs go fold > toast: the camera step is
  skipped. Hoist the host beside `mapReturnMemory` (it is plain state with no map reference except the
  `StackCamera` it is handed at each push, `CrowdedStackZoom.kt:85-88`, which the rebuilt map's handler
  re-hands at the next tap; a return pushed by the old map's camera would restore through the old
  `MapLibreMap`, so the hoist also needs the host to take the live camera at `stepBack`, or to drop its
  returns when the map is rebuilt). Also the right home for the next PR's mode (section 8).

- **S3. Landscape: the list runs under the search strip (inferred).** The list is at most 300 dp tall

## 3. The zoom loop

`CrowdedStackZoom.kt:141-185`. Each iteration: list if already at 17 (`:156`); frame the current stack
(`:157`); locate its members and re-stack them about the tapped one (`:165-171`); split, fan, or carry on
(`:172-178`); list if the zoom did not increase (`:180`). The frame is the stack's own bounds with the entry
map's padding, capped at 17 (`frameOf`, `:226-233`; `cappedFrameZoom`, `MapCameraMoves.kt:158`, `:187`), and
each later stack is a subset of the one before, so its bounds are no larger and the fitted zoom is no
lower: the zoom is monotone, bounded by 17 and by `MAX_ZOOM_STEPS` = 8 (`:32`), and a step with no gain
exits. **No oscillation.** Zoom caps: Trail 18, OpenStreetMap 19, Topographical 17 (`BasemapStyles.kt:285-290`),
applied by `setMaxZoomPreference` (`MapStyleReload.kt:117`) and read back through `camera.spot()` after
the move, so a clamp shows up as "no gain" and lists. **The failed-frame path:** before any push, the stack
is fanned past the edge and logged twice (`:158`, `:214-218`, plus `MapStackCamera.kt:48` and
`MapCameraMoves.kt:178`, `:184`); after a push, the list opens at the zoom reached, logged by the camera.
**Logged:** every exit but the normal three outcomes and one, S4.

Two things rest on the device: that `moveCamera` applies the camera synchronously so `markersOf`
(`FanOutLayers.kt:361-365`, through `map.projection`) reads the post-jump projection in the same tap
(disclosed in the PR body and in `MapStackCamera.kt:17-20`); and that setting `cameraMode = NONE`
(`MapStackCamera.kt:45`) starts no camera move of its own. Not checked here.
