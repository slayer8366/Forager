## 2. The live queries and the collector

- **Same rules as the one-shot counts.** Each live query's `WHERE` is its one-shot sibling's without the `= :id` term:
  `kept = 1 AND isDraft = 0` for waypoints, tracks and offline regions (`CartographyEntryDao.kt:207-235` against `:155-186`), `isDraft = 0`
  alone for photos (`:237-245` against `:192-200`; photo refs have no `kept`, per the one-shot's own comment at `:188-191`). Saved
  entries only, no drafts, kept references only. `EntryDeleteRefRowsTest.kt:75-84` asserts those rules on the live source itself, with
  a draft, a withheld decision and two committed entries in one table; revert R6 (dropping `isDraft = 0`) failed it with
  `{wp-1=3, wp-3=1}` where `{wp-1=2}` was expected (run A's XML).
- **Collector lifecycle.** `watchEntryReferenceCounts` (`EntryReferenceCountSource.kt:49-59`) launches one coroutine in the scope it is
  given; every caller passes the ViewModel's `viewModelScope` (`TrackRecordingLists.kt:58-65` via `scope()`,
  `AvailabilityOfflineMaps.kt:118-122`, `MushroomLogGallery.kt:53-58`), and each `watchReferenceCounts()` is called exactly once, from
  `init` (`TrackRecordingViewModel.kt:351`, `AvailabilityViewModel.kt:374`, `MushroomLogViewModel.kt:338`). A cleared ViewModel cancels
  the collection; `catch` does not catch cancellation, so no spurious log line on clear. No leak that I can construct.
- **No `runTest` stall.** The collector is a suspended wait on a `Flow`, not a `delay` loop, so `runTest`'s idle-advance has nothing to
  spin on, and `viewModelScope` is not a child of the test scope, so `runTest` does not wait for it. The ViewModel tests that now take a
  `FakeEntryReferenceCountSource` (`MutableStateFlow`s, `FakeEntryReferenceCountSource.kt:16-25`) ran green in two full runs
  (`40787634936`, `40789923689` attempt 2; 5901 tests, 0 failures, 24 skipped in each run's XML; 807 suite files). The new live tests
  record nothing, so they cannot leave the Track ViewModel's poll loop running (`LiveWaypointTrackCountsTest.kt:37-38`'s own note).
- **The logged-failure path.** A failed read logs once through the caller's `ErrorLog` and the flow completes
  (`EntryReferenceCountSource.kt:57-58`); the last map written stays. That is the accepted rule ("a failed read logs and keeps the last
  good counts"). `EntryReferenceCountWatchTest.kt:19-36` holds it on a flow that emits once and throws; revert R14 (dropping `.catch`)
  failed it with the `IOException("disk read failed")` escaping to `runTest` (run A's XML). The photo collector wraps `Log.w` as an
  `ErrorLog` (`MushroomLogGallery.kt:54`), since that class has no `ErrorLog` seam; the other two use the ViewModel's. See N4 for what
  "keeps" means after the failure.

**N2. `OfflineMapsPanelTextTest` was outside revert A's filter.** Its locator of the new text is `OfflineMapsPanelTextTest.kt:176`

**N3. Revert A's R1 to R4 did not reach the stale-count assertion.** In run A, each "deleting ..." live test failed at its positive
control ("timed out waiting for: positive control: the waypoint is listed and counted in 1 entry", and the same for track, region and
photo), because a source replaced with `NoEntryReferenceCounts` never delivers a 1. So run A shows the tests notice a source that
delivers nothing; the run that shows they notice a *stale* count is the fail-first run (section 4). Both runs are needed to read the
evidence, and the completion report's "Fail first" and "Revert run A" sections do keep them apart; I record it because the index row's
"every failure was its own edit's" is true of A and could be read as the stale-count proof, which lives in the other run.

**N4. One failed read freezes the counts for the ViewModel's life.** `EntryReferenceCountSource.kt:57-58`: `catch` completes the flow,
and nothing restarts it. Failure path: a transient read failure on the local database logs once ("...keeping the last counts.") and the
counts on screen never change again until the ViewModel is recreated (a process restart in practice), with nothing on screen saying so;
a user who then deletes the only entry keeping a waypoint still reads "used in 1 journal entry", the very symptom this PR removes, in a
narrower window. This is within the owner's accepted rule; whether "keeps the last good counts" meant "until the next change" or "until
restart" was not asked. CLAUDE.md says not to build correction logic without data showing the case, and there is none; the log line is
accurate. Record only. Should the owner want it, the smallest change is a retry on the next successful write, which Room's own
invalidation does not provide on a completed flow.

**N5. A drafts-only read failure now reads as "No drafts."** `MushroomLogViewModel.kt:354-357`: when `getDraftEntries` fails, it logs
and keeps the previous drafts, and sets no `loadErrorMessage`. On a fresh start that previous list is empty, so the Drafts tab meets
`FindsGalleryScreen.kt:175`'s condition and shows "No drafts. A find you leave before saving waits here." for drafts that exist but could
not be read. Failure path: a user whose draft is on disk is told there is none, and may start a second. Pre-existing seam, not made by
this PR: before it the tab was blank in the same case, which told the user nothing either. The new sentence is more confident than the
blank was, so I record it for the owner; the fix, if wanted, is a drafts error field or folding the drafts failure into
`loadErrorMessage`, which is a wording question for the owner first.

**N6. The one-shot count queries are production-dead.** `CartographyEntryDao.kt:155-200` and `CartographyEntryRepository`'s four
`countEntriesReferencing*` methods (with their Room implementation and the sixteen fakes' overrides) have no caller in `app/src/main`.
Kept deliberately and disclosed. Failure path: none today; the cost is the next reader asking "who calls this?" and the next fake
author implementing four methods nothing reads. `EntryDeleteRefRowsTest.kt:75-84` now asserts the live rules directly, so the one-shots
are no longer needed as the reference the live `WHERE` is compared to. A follow-up removal is cheap and separate.

**N7. The live tests never clear their ViewModels.** `LiveWaypointTrackCountsTest` and `LiveRegionPhotoCountsTest` build ViewModels
through the factories and leave them; their Room collectors and the Track ViewModel's `takeUpRunningRecording()` one-shot stay alive
until Robolectric tears the test down. Not a `delay` loop, so not the stall CLAUDE.md describes, and both full runs were green. Record
only; `viewModelScope` here is the real `Dispatchers.Main.immediate`, idled by the harness's own looper loop.

**N8. The completion report quotes revert B's failures as finding the text "where it must not be".** The XML messages are
`Failed: assertDoesNotExist.` at `RecordsFilterChipsTest.kt:612` and `:626`; the lines are the two `assertDoesNotExist` calls on "No finds
yet. Use New find to log one.", so the reading is right, but the message itself does not name the text. For whoever reads the record
later: the line numbers carry the specificity, not the message.

**N9. Observed, not a finding.** Every committed write to `cartography_entries` (a draft's autosave on each edit included) re-runs up to
four `GROUP BY` queries across the three live ViewModels. An unchanged result produces an equal map and an equal state, which
`StateFlow` drops, so nothing recomposes. No data says this costs anything; noted so that nobody adds `distinctUntilChanged` or a
debounce without a measurement.
