## 1. No flip-flopping

Traced from `NetworkSignal.kt:44-62` (hysteresis), `NoSignalTrailMap.kt:114-131` (the state),
`OwnStreetFallback.kt:54-70`, `MapStyleReload.kt:72-88` and `NoSignalTrailMap.kt:54-60,89-101`.

**What drives the retry.** `noSignalWithHysteresis` takes `validated.distinctUntilChanged()`, delays each
change by 5 s (loss) or 30 s (return) under `collectLatest` so an unheld change is dropped, and its output is
`distinctUntilChanged()` again (`:62`). So the state emits `false` once per return of the signal, never twice
in a row, and `onSignalReturned()` (`:129`) runs once per return. Its first emission is taken at once with no
delay (`:53-55`); at a cold start online that is one `false`, and `onSignalReturned` is then a no-op because
nothing has fallen back yet (`OwnStreetFallback.kt:67`; a style load takes a round trip, so it cannot have
failed before the first network reading is read synchronously at `AndroidNetworkSignal.kt:38`).

**Why there is no loop.** The thing that retries (the network state) reads Android's validated capability and
nothing else (`AndroidNetworkSignal.kt:38-46`; -1556: never tile errors). The thing retried (the style load)
never writes to it. A retry that fails sets the flag again (`:55-56`) and relaunches the style effect with
`ownStreet = false` (`MapStyleReload.kt:72-73`), and that is the end of it until the signal next drops for 5 s
and returns for 30 s. There is no path from a failed load back to a retry.

**Cost per loss-and-return cycle, worst case, Trail Map user who has fallen back:**

| State change | Today (6064fef86) | This PR | Where |
|---|---|---|---|
| Signal lost 5 s, a downloaded area exists | 1 reload (to downloads, Amendment 3) | same | `NoSignalTrailMap.kt:60` |
| Signal back 30 s | 1 reload (back to OpenStreetMap's raster) | 1 reload (to Trail Map) | `MapStyleReload.kt:73` |
| Trail Map fails again | none | 1 reload (to the raster) | `OwnStreetFallback.kt:55-56` |

So at most one extra style load per cycle, and only when Trail Map is genuinely down at the moment the
signal has held 30 s. A user who has not fallen back is unaffected (`:67`). At the edge of coverage the
hysteresis bounds the cycle rate exactly as it bounds today's downloads switch; this PR adds no faster path
(the report's choice (a), rejected at `OwnStreetFallback.kt:29-30`, would have).

**One ordering I could not rule out from source alone.** `onSignalReturned()` runs in the `onEach` before
`stateIn` publishes the new `false` (`:120-131`). For the Trail user drawing from downloads, a recomposition
that saw the cleared flag before the new `noSignal` would compute `drawsFromDownloads` false
(`:60`: `!trailMapDraws` is now false) and request Trail Map online one frame early; the next recomposition
requests the same style, and `needsStyleReload` (`MapStyleReload.kt:88`) compares against `appliedStyle`,
which is set only in the load callback (`:171`), so a duplicate `setStyle` of the same style is possible in
that window. Both writes happen on the main thread in one coroutine step and should land in one frame; I did
not run it. Not a flip (the two requests are identical), and the same shape exists today between the
downloads flag and any other key. Recorded under "Could not determine".
