## 6. What a phone needs to see it

**6a. A Worker deploy, yes.** v3 is bundled: `server/pmtiles-worker/src/index.ts:27` imports
`./street-style-v3.json` and `:491-493` serves it at `/style/street-v3.json`. The app loads that one constant
URL (`StreetStyle.kt:23`, `BasemapStyles.kt:268`). Nothing on a phone changes until the Worker is rebuilt from
`main` (the Worker builds from `main` automatically since −1609; this PR goes to `pre-main`) or deployed by
hand on the owner's word. Merging #426 alone shows nothing anywhere.

**6b. A day, twice over at worst.** The style response carries `Cache-Control: public, max-age=86400`
(`index.ts:433`) and no ETag or Last-Modified. That is up to a day at the edge after the deploy. On the phone
the day runs from each phone's own last fetch, because MapLibre defers the refetch to the stored copy's expiry:
`OnlineFileRequest::activate` schedules the first network request at `getUpdateInterval(priorExpires)`
(`online_file_source.cpp:478-485`), which is `expires − now` (`http_timeout.cpp:40-42`). So a phone sees the
new v3 at its first style load after its stored copy expires: up to 24 h after its last fetch, plus up to 24 h
of edge cache. Nothing in the app invalidates MapLibre's cache (no `invalidateAmbientCache`,
`clearAmbientCache` or `invalidateOfflineRegion` call in `app/src/main`).

**6c. Downloaded v3 areas refresh when online; they keep the old buildings until then.** From MapLibre Native
at `android-v13.5.0`:
- Every non-asset request goes to the database first (`main_resource_loader.cpp:84-110`). The stored response
  is returned at once if `isUsable()`, which is `!mustRevalidate || not expired` (`response.hpp:44`); the
  Worker sends no `must-revalidate`, so the stored style always serves first, expired or not.
- The network request then follows (`requestFromNetwork`, `:38-62`), scheduled as in 6b, and its 200 is written
  back by `DatabaseFileSource::forward` → `OfflineDatabase::put` (`database_file_source.cpp:48-49`;
  `offline_database.cpp:288-300`).
- `putResource` is an `UPDATE resources … WHERE url = ?` (`offline_database.cpp:452-473`). Region resources live
  in that same `resources` table (the region link is a join table; `putRegionResourceInternal` writes through
  `putInternal`, `:1088`), so the update rewrites the region's stored style too. There is no "frozen copy" per
  region: the freeze this repo relies on is the URL's meaning (`index.ts:374-378`), not stored bytes.
- Offline (`NetworkStatus::Offline`), the refetch is parked until the network returns
  (`online_file_source.cpp:500-506`); the stored copy keeps drawing.

So: a phone that downloaded an area against v3 draws the old half-opaque buildings until it is online at a
style load after expiry, then draws the new ones with the same stored tiles (the tiles are unchanged; the
`protomaps` source URL is pinned equal to v2's, `worker.test.mjs:453`). No re-download is needed and none is
asked: `regionHasOlderMapStyle` compares the region's style URL with the download URL (`StreetStyle.kt:85-89`),
so a v3 region never shows the older-style notice, which is right, since downloading again would change
nothing the refresh does not. v1 and v2 regions are untouched by this PR. Inferred, not read: that the style
request itself is issued with the default loading method (`All`), which is what puts it on the path above; the
style loader was not read.
