## In one paragraph

The app downloads an offline area as MapLibre tiles only; there is no place for route data in it today (Q1). The Pi builds BRouter's `.rd5` files, one per 5-degree square, 185 for the US and Canada, kept on the Pi and never uploaded; the Seattle square is 54.9 MB (Q2). BRouter names and opens files by 5-degree square, but inside a file it reads 1-degree tiles and 1/32-degree cells one at a time and tolerates empty ones, so a *sparse* square file holding only an area's cells is a legal file. The engine spike already made one that way (0.64 MB for 60 x 60 km, routes identical) by building from a clipped extract. No BRouter tool cuts an existing `.rd5`, but the format lets a small tool do it by copying cells (Q3). At the app's own radii the cut data is 0.1 to 0.2 MB for the default areas and 0.5 to 0.85 MB for the largest, against 54.9 MB for a whole square (Q4). Serving it needs the Pi to upload the squares, one new Worker route, and the app's own downloader plus a Room column with a reader (Q5). The data is ODbL and must be credited as OpenStreetMap with a route to the licence; BRouter's MIT notice must ship in the credits (Q6).

## Q1. Today's offline-area download

**What is fetched, from where.** `MapLibreOfflineMapRepository.download` builds an `OfflineTilePyramidRegionDefinition` from a style URL, the area's bounds, zooms 10 to 15 and the screen density (`app/.../map/MapLibreOfflineMapRepository.kt:114-121`, read). The style URL is `offlineDownloadStyleUrl()`: with the Street switch off, as it is (`map/StreetStyle.kt:21`, `STREET_SERVED_BY_OWN_MAP = false`), that is `OFFLINE_STYLE_URL`, `https://forager-pmtiles.brandonlee1-894.workers.dev/style/offline.json` (`map/OfflineStyle.kt:18`; `StreetStyle.kt:44-45`). That style's one source is the Worker's `us.json` tileset (`server/pmtiles-worker/src/offline-style.json:3-8`), so the tiles come from the Worker's `/us/{z}/{x}/{y}.mvt` route (`server/pmtiles-worker/src/index.ts:354-450`). MapLibre's `OfflineManager` does the fetching (`:135-140`); the app never sees a tile.

**The area.** A centre and a radius, `Region(lat, lng, radiusKm)` (`domain/model/Region.kt:4-8`). The radius slider runs 1 to 24 km (`Region.kt:10`, `MIN_RADIUS_KM = 1`; `domain/OfflineMapRepository.kt:203`, `MAX_RADIUS_KM = 24`, clamp at `:206`), defaulting to 8 km in miles and 10 km in kilometres (`domain/model/DistanceUnit.kt:53-56`). The download covers the *square* box around the circle, `GeoDistance.boundingBox` (`domain/GeoDistance.kt:69-83`; `MapLibreOfflineMapRepository.kt:275-281`), so a 24 km area is a 48 x 48 km box.

**Where it is stored.** In MapLibre's own database, `files/mbgl-offline.db` under the app's files directory, observed on the S22 and the tablet (`map/MapLibreStorage.kt:8-10`, read). The app's Room table `offline_regions` holds the index: MapLibre's region id as primary key, name, centre, radius, zooms, created-at, `isEntryCapture` (`data/local/OfflineRegionEntity.kt:28-47`), written after the download completes (`MapLibreOfflineMapRepository.kt:155-166`). A copy of the same fields goes into the region's metadata blob (`map/MapLibreOfflineRegionMetadata.kt:29-42`). **No column, blob key or file refers to route data** (read: the entity, the metadata keys at `:102-108`, and the interface `domain/OfflineMapRepository.kt:32-70`).

**How the size shown is worked out.** Before download, only a *tile count* is shown and gated: `estimateServedOfflineTileCount` sums slippy-map tiles over the box for zooms 10 to 15 (`domain/EstimateOfflineTileCount.kt:44-57`), the confirmation dialog prints it (`ui/availability/AvailabilityOfflineMapsUi.kt:269`), and `onDownloadOfflineMaps` refuses when it exceeds the remaining 6,000-tile budget (`ui/availability/AvailabilityViewModel.kt:868-878`; `TILE_COUNT_LIMIT` at `OfflineMapRepository.kt:101`). No byte estimate exists before download. After it, the bytes are MapLibre's own `OfflineRegionStatus.completedResourceSize`, read live on every listing (`MapLibreOfflineMapRepository.kt:174-175`, `:202-210`; the interface promises this at `OfflineMapRepository.kt:49-55`), and the row prints `sizeBytes / 1,000,000` as "12.3 MB" (`ui/availability/OfflineRegionsList.kt:244`). The list also prints "Tile budget: used / 6000" (`:101`). So "the size shown includes the route data" means adding bytes the app downloads itself to a figure MapLibre computes, in one place (`:244`), and adding a count to the budget line or leaving routes outside it (a question for the owner; see Q5).

**How an area is deleted.** A swipe asks for a pending delete (`AvailabilityViewModel.kt:885`); when the Undo snackbar ends, `commitOfflineRegionDelete` calls `offlineMapRepository.deleteRegion(id)` (`ui/availability/AvailabilityOfflineRegionDeletes.kt:94-125`), which deletes MapLibre's region then the Room row (`MapLibreOfflineMapRepository.kt:188-191`). A delete still pending when the screen closes is committed from `onCleared` (`AvailabilityOfflineRegionDeletes.kt:131-139`). Route files would need their own delete step in `:188-191`, since nothing else touches the files directory.

## Q3. Can route data be cut to a user-drawn area?

### What the format is, from BRouter's source at v1.7.10 (all read)

- **A file is a 5-degree square, found by name.** `NodesCache.fileForSegment` derives `W125_N45` from a position's degree and opens `<segmentDir>/W125_N45.rd5`, falling back to a secondary directory (`brouter-mapaccess/.../NodesCache.java:347-375`). Nothing else names or finds files. BRouter's documentation says the same (`docs/users/download_segments.md:7-11`; `docs/developers/build_segments.md:9-10`).
- **Inside, 25 one-degree tiles, each 32 x 32 cells.** The file starts with 25 longs, one per one-degree tile (`PhysicalFile.java:19`, `:99-107`; written at `WayLinker.java:436-442`). Each tile has `divisor x divisor` cells with `divisor = 32` in the current format, 80 in the old (`WayLinker.java:63-64`; `PhysicalFile.java:131-134`); a cell is 1/32 degree on each axis, about 3.5 km by 2.4 km at 45 N. A tile's own index is 1,024 ints giving each cell's byte range (`OsmFile.java:48-50`, `:105-116`).
- **The router reads one cell at a time.** `getSegmentFor` opens the tile and decodes only the cell holding the position (`NodesCache.java:157-196`; `OsmFile.java:118-157`). Waypoint matching preloads a ring of cells around each waypoint, at 0.0125 degrees then at 1/32 degree (`NodesCache.java:292-345`).
- **Empty tiles and cells are legal.** A one-degree tile with no data has equal start and end offsets and is skipped (`OsmFile.java:56-58`, `hasData()` false at `:80-82`); a cell with zero bytes returns `MicroCache.emptyCache()` (`OsmFile.java:125-127`). WayLinker writes data only for tiles and cells that have nodes (`WayLinker.java:449`, `:468`), so every ocean-edge square the Pi builds is already sparse.
- **What happens past the data.** If the *first* file touched for a waypoint is missing, routing throws "datafile W125_N45.rd5 not found" (`NodesCache.java:305`, `:332`, `:385-386`). If a waypoint has no way within range, "position not mapped in existing datafile" (`RoutingEngine.java:1626-1630`). During the search, a node whose cell is absent or empty simply stays "hollow" and is never expanded (`NodesCache.java:213-235`, `obtainNonHollowNode` returns false): the search does not cross that edge, and if the target is beyond it the result is "no track found" (`RoutingEngine.java:1775`). Links across a 5-degree line work only because WayLinker writes both sides from a shared border-nodes file (`WayLinker.java:29-32`); when the neighbour square is absent the same hollow-node stop applies.
- **BRouter's own cell-level tool.** `Rd5DiffTool` reads a file tile by tile and cell by cell, copying the header and per-tile indexes, to make and apply `.df5` delta files (`Rd5DiffTool.java:2`, `:131-148`, `:259-277`). It does not cut, but it shows the format handled at cell level without the router.
- **Scale.** BRouter's own documentation puts its practical limit at about 150 km air distance (`docs/features/offline.md:28-29`), and the engine's dynamic waypoint range is 60 km (`RoutingEngine.java:60`).

### Answers

**Can a smaller file covering just an area be produced, and does BRouter route on one?** Yes to both, with a qualification. The file must still be named for its 5-degree square, but it may hold only the area's cells. The engine spike produced exactly that by clipping the OSM extract to a 60 x 60 km square and running the three creator steps on the clip: two `.rd5` files totalling **0.64 MB** (the square straddles 45 N), and routes r2 and r4 on them were identical to the routes on the full state files (`docs/navigation/2026-10-03-engine-spike-report.md:184-188`, read; the clip tool `tools/clip_region.py` is in the spike's branch, not in pre-main). That is a measured "routes on one". What **does not exist** in v1.7.10 is a tool that cuts an *existing* `.rd5` to an area; the planner's prediction that "neither exists" is right about tooling and wrong about the format and the engine.

## Q6. Credits, quoted at source

**OpenStreetMap data (ODbL).** From https://www.openstreetmap.org/copyright (read 2026-10-22; evidence `osm-copyright-extract.txt`): "OpenStreetMap is open data, licensed under the Open Data Commons Open Database License (ODbL) by the OpenStreetMap Foundation (OSMF)." From the OSMF attribution guidelines, https://osmfoundation.org/wiki/Licence/Attribution_Guidelines (read 2026-10-22; evidence `osmf-attribution-sections.txt`): "Attribution must be to “OpenStreetMap”. Attribution must also make it clear that the data is available under the Open Database License. This may be done by making the text “OpenStreetMap” a link to openstreetmap.org/copyright". "The historical forms of attribution “© OpenStreetMap contributors” or “© OpenStreetMap” are acceptable." For **routing engines**: "Routing engines that use OpenStreetMap data must credit OpenStreetMap. Applications that incorporate such a routing engine must credit OpenStreetMap. Routing instructions generated by such a routing engine need not maintain attribution attached to the instructions, as long as they do not form a Derivative Database." For **databases**: "You must include attribution to OpenStreetMap and either the text of the ODbL or a link to it as part of the database, derivative database, or database as part of a collective database. You must include the notices in a location (such as a relevant directory) where users would be likely to look for it, such as a readme file, or within the data or metadata."

What the app shows today: the credits page has "© OpenStreetMap contributors" linking to the copyright page (`ui/credits/DataSourceCredits.kt:31-32`), and the map caption reads "Protomaps © OpenStreetMap" (`map/OfflineStyle.kt:23-28`). The above copyright notice and this permission notice shall be included in all copies or substantial portions of the Software."
