## 3. Ideas

Each idea is a saving that keeps the same checks. None is recommended until the owner rules; none has been trialled (-1642).

**Idea 1. Replace in-conversation polling with one background wait (ruled in principle; new figures).**
- Pattern: Hazel's two long helper sessions issued 349 `sleep` commands (2,162 seconds asked) inside 191 turns. Those 191 turns cost 63,491,808 tokens: 34% of Hazel's 188.7M and 20% of the day. Each poll turn averages about 332,000 tokens, because each turn re-reads the whole context. Smaller counts: Rowan's sessions issued 11 turns with sleeps (3.2M); unassigned sessions 15 turns (3.4M).
- Change: the standing rule that long waits run outside the conversation (one background wait that wakes the helper once when the thing it waits for finishes). This is the owner's existing rule; these are the first figures for it.
- Saves: up to 63.5M a day (20%) if every poll turn were removed. Inferred: each avoided poll turn saves about 0.33M.
- Risk: none to the checks if the single wait runs the same check at its end. The risk is a missed wake-up if the wait is set up wrongly.

**Idea 2. Restart long helpers at a work-item boundary once their context passes about 200,000 tokens.**
- Pattern: 729 turns (74.7% of the day's tokens, 236,206,233) ran with more than 200,000 tokens of context. Hazel's helpers account for 459 of those turns. Helper contexts peaked at 524,342 and 481,954 tokens. Ten of the 17 sessions passed 200,000; no compaction record was found in the window.
- Change: at a natural boundary (after a report is committed and pushed), start a fresh helper with a short handoff file rather than letting one helper run 300-plus turns.
- Saves: the excess above 200,000 tokens in those turns is 90,305,902 (Hazel 71,306,060). This is an upper bound, not a saving: the fresh helper must write its own cache and read its handoff. Inferred net saving: not computable from the logs.
- Risk: a fresh helper does not hold what the old one read. That could change a result (a check that depends on something read earlier), so the handoff must carry the decision record, not a summary. Treat as "would change the result" until the owner rules.

**Idea 3. Name the role on each session so the next report can attribute it (measurement, saves nothing directly).**
- Pattern: 235 turns (39,053,666 tokens, 12.4%) could not be matched to a role: three files, including one main session with 164 turns and 29.8M tokens. Rowan's helper sessions were matched by the name in their opening text, which was not checked one by one.
- Change: each session's opening line names its role. This is the cheapest way to make the report exact.
- Saves: none directly. Risk: none.

**Finding, not an idea: repeated reads are negligible.** Of 68 Read calls in the window, two were repeats (Hazel 1, Sorrel 1). Opening prompts are small (session medians 1,300 to 2,900 characters; largest 3,969). No saving here.

## 4. Would change the result

Listed with their cost; not recommended.

- **Moving the reviewer off Fable.** Fable's 232 turns cost 35,442,873 tokens (11.2%). Sorrel's reviews run on Fable, which is the different-model rule (-1134). Moving them to the coder's model would break that rule and so change the result.
- **Cutting the checks (fail-first runs, revert checks, device checks, a second reviewer).** The logs cannot price these, and each removes a check the result depends on. Not priced; not recommended.

- Dollar cost: no price table was read; figures are tokens.
- The Restricted Object: this run read no log text. The script does not check for it and does not exclude any session on that basis. I cannot say whether any window session is it. The owner should check whether it appears in the window.

**Premises that were wrong:**
- "A task is a unit of work": a task cannot be read from the logs. The branch recorded on each turn changes mid-session (each of Hazel's two helper sessions carries two or more branch labels), so task totals are approximate.
- "The forecast team spent tokens today": its one log file has no turn timestamped 2026-10-25.

**Decided beyond scope:**
- The 200,000-token threshold in Idea 2 is my choice, not a figure from the profile or the record. It is a round number at about the median context (211,411) and should be ruled on by the owner before anyone sizes it.
- Two counts beyond the profile's list (turns that issued a sleep, turns above 200,000) were added because they measure the profile's own items (polled waits, context size).
